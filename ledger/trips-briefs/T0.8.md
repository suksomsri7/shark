## 5. ลิงก์กรอกเอง (CC §J.3 :946 · §J.3.2 :959–:965 · ใบสั่ง T0.6 §16 ข้อ 5 · §17)
- token = `signLink({ tenantId, purpose: "trips.pax-form", subjectId: passengerId, expMin })` (`core/signed-link.ts` :37 — HMAC-SHA256 ด้วย `SESSION_SECRET` ติดป้าย · nonce สุ่ม 128 บิต · ไม่มีกุญแจสำรอง) · `expiresAt` = `TripDeparture.endsAt` (จบทริป) · `expMin` = ⌈(expiresAt − now)/60000⌉ ตัดที่ `SIGNED_LINK_MAX_MIN` (90 วัน — ทริปที่ไกลกว่านั้นร้านออกลิงก์ใหม่ได้) · ไม่มี `SESSION_SECRET` ⇒ `BUSY SERVER_KEY_MISSING`
- **เก็บเฉพาะแฮช** = แถว `AuditLog` (แบบที่ T0.6 ใช้กับ `trips.approval.consumed`): `action "trips.passenger.link_issued"` · `targetType "TripPassenger"` · `targetId = passengerId` · `after = { bookingId, tokenHash: sha256hex(token), expiresAt }` · เพิกถอน = แถว `trips.passenger.link_revoked` · ออกใหม่ = เพิกถอนตัวเก่าโดยปริยาย (ลิงก์ที่ใช้ได้ = แถว issued ล่าสุดของผู้เดินทาง และไม่มี revoked หลังจากนั้น) · token ดิบคืนให้ผู้เรียก (พนักงาน) ครั้งเดียว ไม่บันทึกที่ใด
- ตรวจลิงก์ (ทุกบริการสาธารณะ · ลำดับบังคับ): (1) `verifyLink(token, "trips.pax-form")` (ไม่แตะฐาน) (2) อัตรา `checkRateLimitDb("trips:token:" + clientKey, { limit, windowMs: 3_600_000 })` — token ผิด ⇒ limit = 60 (เพดานใน schema ของ `tokenPerHourPerDevice` `defs/trips.ts:505`) · token ถูก ⇒ limit = ค่าตั้ง `trips.public.rateLimits.tokenPerHourPerDevice` ของหน่วย · เกิน ⇒ `RATE_LIMITED` (ก่อนอ่านข้อมูลใด) (3) ผู้เดินทางของร้านนั้น · หน่วย TRIPS (4) แถว issued ล่าสุด `tokenHash` ตรง · ไม่ถูกเพิกถอน · `now ≤ expiresAt` (5) การจอง `status ∉ {EXPIRED, CANCELLED}` · `piiPurgedAt` null · ผู้เดินทางยังไม่ถูกลบทั้งคน · `now < TripDeparture.endsAt` — ล้มข้อใด ⇒ `NOT_FOUND` ข้อความเดียว (ไม่บอกเหตุ)
- อินพุตสาธารณะ **ไม่มี** `passengerId`/`bookingId`/`tenantId` (strict ⇒ `VALIDATION`) ⇒ ลิงก์หนึ่งใบแตะได้ผู้เดินทางคนเดียว · มุมมองไม่เปิดชื่อ/ข้อมูลผู้เดินทางคนอื่น (บอกได้แค่ "คนที่ i จาก n")
- กันซ้ำของการส่ง: คีย์ `idempotencyKey` (`IDEM_KEY` ของ booking-core) · แถว audit ของการเขียน (`trips.passenger.updated` / `trips.waiver.signed` / `trips.document.uploaded` / `trips.passenger.consent_withdrawn`) มี `after.keyHash = sha256hex("pubform:" + tokenHash + ":" + key)` (ร้าน: `"st:" + userId + ":" + key`) และ `after.bodyHash` (sha256 ของคำขอ canonical ไม่รวม token) · คีย์เดิม+เนื้อเดิม ⇒ ผลเดิม `replayed: true` ไม่เขียนเพิ่ม · คีย์เดิม เนื้อต่าง ⇒ `IDEMPOTENCY_CONFLICT` · ค้นย้อนจาก `createdAt ≥ TripPassenger.createdAt` (หนี้ดัชนี AuditLog เดียวกับ T0.6)
- ทุกการเขียนแถวผู้เดินทาง = CAS: `UPDATE "TripPassenger" SET …, "answers" = <ใหม่ rev+1>, "updatedAt" = $now WHERE "id" = $id AND "tenantId" = $t AND "unitId" = $u AND COALESCE(("answers"->>'rev')::int, 0) = $expectedRev RETURNING "id"` · 0 แถว ⇒ ดูกันซ้ำก่อน (ผู้ชนะใช้คีย์เดียวกันและเนื้อเดียวกัน ⇒ ผลเดิม) ไม่งั้น `STATE_CONFLICT` + `details.rev` ปัจจุบัน
