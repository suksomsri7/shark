## 2. Auth model (recommendations)
1. **Scopes = existing POS permission keys** (house rule, no `pos:read` vocabulary). Read ops use `pos.sale.read` (exists `permissions.ts:144`; P0.2 D2 deferred it here, `wo-notes/pos-P0.2.md:51`); `POS_SCOPES` grows to every key used. Bundles in `scopes.ts` (one marked hunk, lane hot file): **`pos-read`** (`pos.sale.read`, `pos.report.view`) · **`pos-operate`** (+ `pos.sale.create`, `pos.order.accept`, `pos.shift.manage`, `pos.device.manage`) · **`pos-admin`** (+ `pos.sale.void`, `pos.sale.refund`, `pos.sale.priceOverride`, `pos.order.reject`, `pos.product.manage`, `pos.product.setPrice`, `pos.channel.manage`, `pos.taxinvoice.issue`, `pos.report.anomaly`). `POS_SCOPE_KEYS` like `:54–69`.
2. **System + unit**: `POS_API_CONFIG = {module:"pos", systemType:"POS", scopePrefix:"pos.", rateNs:"pos", makeActor: posApiKeyActor, messages: th/en "ระบบขายหน้าร้าน"}`. Keys always bound to one POS AppSystem (issuer rule, `wo-notes/HF-APIV1.md` §1). **Unit = `unitId` field** in query (GET) / body (POST), validated by `posUnitIsLinked` + facade `scopeOf`; optional = all permitted units where the facade supports it (reports `reports.ts:331–341`). Rejected: path `/units/{unitId}/…` (doubles every template, `matchOpIn` least-param rule `dispatch.ts:50–65`), header `X-Pos-Unit` (invisible in zod/OpenAPI, not in `POS-API.md`). Optional per-key restriction = pseudo-scope **`pos.filter.unit:<unitId>`** (CRM filter precedent `scopes.ts:22–50`) → actor `unitAccess` = those units, else `["*"]` (Q2).
3. **Actor**: `posApiKeyActor` → `ApiActor` + a synthetic `RegisterActor {userId: keyId, role:"STAFF", unitAccess:["*"]|filter, permissions: scopes}` passed to every facade (STAFF ⇒ `evaluate` checks the exact key `rbac.ts:31–38`; never MANAGER/OWNER). `userId = keyId` (not `createdById`: bills/shifts would be attributed to the owner who issued the key and keep working after they leave). Bills carry `sourceModule "API"` + `sourceId keyId` (as `sales.ts:134–135`); audit = `API_KEY` + keyId (`run.ts:100–102`). Staff report shows the key name for `soldByUserId = keyId` (one reader hunk, Q6). POS `userId` columns are plain strings (`pos.prisma:438, :469, :565, :610`), so no FK break.
4. **Catalog writes**: additive `CatalogCtx.actorMembership?: MembershipCtx` (used only when `actorUserId` starts with the key-actor prefix and the membership is built from scopes by `pos/api/actor.ts`), one marked hunk in `actorOf` `catalog.ts:257`; F15.1/F15.5 unchanged (still the only writer; no system actor). Alternative = IN-B products writes wait (Q3).
