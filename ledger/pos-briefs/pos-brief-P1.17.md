Index `@@index([tenantId, unitId, createdAt])` (`:68`) is the only time index. **There is no seller/cashier column**, and `submitRegisterSale` (`register.ts:1541`, its `createSale` call `:1616`) does not pass the actor anywhere into the sale.
- **Money identity in `createSale`** (`service.ts:330`): `grand = subtotal − discount + serviceCharge` (`:416`, `:569`); VAT is stored with `splitIncludedVat` (`service.ts:485`, `:579`; helper `src/lib/money/vat.ts:16`), so the stored column equals the ledger bridge (P1.6 R1). - **Lines** `pos.prisma:71-94`: `qty`, `unitPriceSatang`, `discountSatang`, `lineTotalSatang`, `itemId` (InvItem), `serviceId`, `productId` (loose PosProduct id), `weightGrams`, `components`. **No cost column on the line.**
- **Payments** `pos.prisma:115-131`: one row per method, `tenderedSatang`/`changeSatang` on the CASH row only (P1.6 §8.2).
- **Cost of goods**: `consumeSaleInventory` (`service.ts:718`) writes one `InvMovement` per consumed part with key `pos-consume-<saleId>-<lineId>` or `…-<lineId>-<invItemId>` for bundle parts (`lineConsumption` `service.ts:702-713`). The movement stores `costSatang` = the item's moving-average cost at that moment (`inventory/service.ts:722`). `InvMovement` has `@@unique([tenantId, idempotencyKey])` (`inventory.prisma:180`) but **no index on `refId`** (`:181` is `systemId, itemId, createdAt`).
- **Shifts** (P1.9): `PosShift` `pos.prisma:307-337`; the closed shift's `zReport` JSON is frozen (`ShiftReport` type `shift.ts:93-125`); the live X computation `computeReport` (`shift.ts:267`) is not exported.
- **Legacy reporting**: `closeDaySummary/closeDayBills/closeDayCsv` (`service.ts:927`, `:992`, `:1035`) = one BKK calendar day per POS system, filtered by `systemId` + `createdAt` (+ `unitId IN` when the user is branch-limited); `bkkDayRange` midnight BKK (`:902`); `PAY_TYPE_ORDER` + Thai labels (`:891-899`); CSV = BOM + `\n` lines + baht `toFixed(2)` (`:1027-1062`). `daySummary` (`:856`) and `listSales` (`:845`) are older per-unit helpers. API ops `api/ops/reports.ts` loop `closeDaySummary` per day with a 31-day cap (`:18`). The system home page shows "ยอดวันนี้" from `closeDaySummary` (`app/app/sys/[id]/page.tsx:143`). The tenant dashboard widgets read the **first** POS system of the tenant (`lib/dashboard/service.ts:28,53,109`).
- **Authz**: pos actions are `sale.create`, `product.setPrice`, `product.manage`, `sale.void`, `sale.priceOverride`, `shift.operate`, `shift.manage` (`core/permissions.ts:133-139`). No report key. `/pos/close` and the system page use `posSalesScope` = `pos.sale.create` (`modules/pos/access.ts:28-33`). `evaluate`: OWNER all · MANAGER all in accessible units · STAFF explicit key or `pos.*` (`core/rbac.ts:32-40`).
- **Refunds**: P1.8 is not built. No POS code sets `REFUNDED`; modules that "refund" call `voidSale` (bill → VOIDED). There is no `docType` column.

## 2. Contract (proposed rulings R1…R16 — controller; additive only)
R1 **Module.** New `src/lib/modules/pos/reports.ts` (read-only, no `"use server"`). Same pattern as `shift.ts`: `(ctx, actor, input, client?)`, refusals returned `{ok:false, code, message}`, never thrown. `ctx: ReportCtx = { tenantId, systemId, unitId? }` · `actor: RegisterActor` (`register-shared.ts:55`). Functions:
  - `reportDailySales` · `reportProducts` · `reportStaff` · `reportPayments` · `reportMargin` · `reportShifts` · `reportTax` — input `{ from, to, limit? }`, result `{ ok: true, report: { kind, from, to, unitId: string|null, generatedAt, rows: Row[], totals: Totals } }`.
  - `reportCsv(ctx, actor, { kind, from, to })` → `{ ok: true, filename, contentType, body }` (R11).
  - `posDashboardCard(ctx, actor, { now?: Date })` → `{ ok: true, card }` (R16).
  - Refusal codes: `VALIDATION` · `NOT_FOUND` · `PERMISSION_DENIED` (+ `INTERNAL` in actions only).
R2 **Range = Asia/Bangkok business days.** `from`/`to` are `YYYY-MM-DD` strings, both inclusive, real calendar dates, `from ≤ to`, span ≤ **92 days**; anything else (wrong format, 2026-02-30, numbers, missing, 93 days) is `VALIDATION`. A day is `[00:00, 24:00)` BKK = `[D−1 17:00Z, D 17:00Z)`, exactly `bkkDayRange`. The bill timestamp is `createdAt` (same as `closeDay` and P1.9 F1; `paidAt` = `createdAt` for every PAID-now bill). Rows of `reportDailySales` cover **every** day of the range, zero rows included, ascending.
R3 **Which bills count.** Sales = `status = 'PAID'`. `VOIDED` bills are excluded from sales and reported only in void columns (`voidCount`, `voidTotalSatang` = Σ grand). `REFUNDED` is unused today and is excluded. Refunds: fields `refundCount`/`refundTotalSatang` exist in daily rows and are 0 until P1.8; P1.8 must fill them from its refund documents (and subtract nothing from `netSalesSatang`; net-after-refunds is a P1.8 field). The tenant/system/unit scope of R13 applies to every query.
R4 **Money.** Integer satang everywhere. VAT = the stored `PosSale.vatSatang` summed; reports never recompute VAT (no `splitIncludedVat`/`posVatRateBp` in `reports.ts`). Service charge is revenue: it is inside `netSalesSatang`. Tip is **not** revenue: shown as `tipSatang` beside, never added to net/gross/VAT figures. Identities that must hold in every daily row and total: `netSalesSatang = grossSatang − discountSatang + serviceChargeSatang`, `netExVatSatang = netSalesSatang − vatSatang`, payments Σ = net + tip.
R5 **Daily + products.**
  - Daily row: `businessDate, billCount, grossSatang (Σ subtotal), discountSatang, serviceChargeSatang, netSalesSatang (Σ grand), vatSatang, netExVatSatang, tipSatang, voidCount, voidTotalSatang, refundCount, refundTotalSatang, avgBillSatang (floor(net/bills), 0 when none)`. Totals: the same sums; `avgBillSatang` from the totals.
  - Products: one row per key `p:<productId>` › `i:<itemId>` › `s:<serviceId>` › `n:<line name>` (first non-null wins). Fields `key, productId, itemId, serviceId, name (line name of the newest line), qty (Σ qty), weightGrams (Σ, 0 if none), lineCount, billCount (distinct bills), grossSatang (Σ unit×qty), lineDiscountSatang, salesSatang (Σ lineTotal)`. Sort `salesSatang` desc, then key asc. `limit` default 200, max 1000 (rows only; totals always over all). Σ `salesSatang` = Σ subtotal = daily `grossSatang` (bill-level discount is not spread onto products).
R6 **Staff + new column.** Add `PosSale.soldByUserId String?` (loose id like `shiftId`, no FK, no index; additive migration, nullable). `CreateSaleInput.soldByUserId?: string` is stored as given; `submitRegisterSale` passes `soldByUserId: actor.userId`. Other callers pass nothing (null; behaviour unchanged). Seller of a bill = `soldByUserId ?? (shift ? shift.openedByUserId : null) ?? null`. Row: `userId (null = "ไม่ระบุ"), name (User.name || User.email || null), billCount, netSalesSatang, discountSatang, tipSatang, voidCount, voidTotalSatang (voids are counted against the bill's seller — who voided is not stored), avgBillSatang`. Sort net desc, then userId asc, null last. (Q17.1)
R7 **Payments.** One row per `PosPayType` present, in `PAY_TYPE_ORDER` (CASH, PROMPTPAY, TRANSFER, CARD, DEPOSIT, ROOM_CHARGE): `type, label (Thai label of service.ts:892), count (payment rows), billCount (distinct bills), amountSatang`; the CASH row also carries `cashTenderedSatang = Σ(tendered ?? amount)` and `changeSatang = Σ(change ?? 0)`. Totals `totalPaidSatang, salesSatang (Σ grand), tipSatang, billCount`; `totalPaidSatang = salesSatang + tipSatang`. Tip is not split by method.
R8 **Margin / COGS.** Per PAID line, cost =
  1. **stored**: Σ |qtyDelta| × `costSatang` of the `InvMovement` rows whose keys are exactly the line's consumption keys (reuse/export `lineConsumption` from `service.ts:702`; look up by `(tenantId, idempotencyKey) IN (…)` — the unique index — never by `refId`);
  2. else, if the line has `itemId`: **estimate** = current `InvItem.costSatang × (weightGrams ?? qty)`;
  3. else uncosted (service/custom lines, or a bundle without movements).
  Row (same keys and order as products): `key, name, qty, revenueSatang (Σ lineTotal, VAT-inclusive, before bill discount), costSatang (null when no line is costed), estimatedCostSatang, uncostedLineCount, marginSatang (costed revenue − cost, null when uncosted), marginBp (floor(margin×10000/costed revenue), null when uncosted or revenue ≤ 0)`. Totals: `revenueSatang, costedRevenueSatang, costSatang, estimatedCostSatang, grossMarginSatang, uncostedRevenueSatang, uncostedLineCount, netExVatSatang (Σ grand − vat), netMarginSatang (netExVat − cost)`. Voided bills and their movements never count. (Q17.3)
R9 **Shifts.** Shifts whose `openedAt` BKK date is in the range, in the scope units, sorted by `openedAt`. CLOSED/FORCE_CLOSED rows read `billCount, salesTotalSatang, tipSatang` **from the frozen `zReport`** and `expectedCashSatang, countedCashSatang, overShortSatang, zNumber` from the row columns — never recomputed (P1.9 S10). OPEN rows are computed live with the X logic (export `computeReport` or a read-only twin; expected cash shown — the report permission is a manager-level right). Row: `shiftId, shiftNo, zNumber, unitId, deviceId, deviceLabel, status, openedByUserId, openedByName, openedAt, closedAt, billCount, salesTotalSatang, tipSatang, expectedCashSatang, countedCashSatang, overShortSatang, forced`. Totals `shiftCount, billCount, salesTotalSatang, overShortSatang (Σ non-null), shortCount, overCount, forcedCount, openCount`. Monthly over/short = this report over a month range. Reports never force-close anything.
R10 **Tax (ภาษีขาย · ใบกำกับอย่างย่อรายวัน).** One row per (business day, unit) that has any bill, sorted by date, then unit name, then unitId. Fields `businessDate, unitId, unitName, firstReceiptNo, lastReceiptNo (by createdAt over PAID + VOIDED — the day's number range incl. cancelled), billCount (PAID), grossSatang (Σ grand), vatSatang (Σ stored), baseSatang (gross − vat), vatableGrossSatang (bills with vat > 0), nonVatGrossSatang (vat = 0), voidCount, voidReceiptNos (by createdAt)`. Tip is never in these figures. Totals: sums.
R11 **CSV.** `reportCsv` with `kind ∈ daily|products|staff|payments|margin|shifts|tax` (other ⇒ `VALIDATION`). Same permission/scope/range rules as the report. `filename = pos-<kind>-<from>_<to>.csv` (ASCII), `contentType = "text/csv; charset=utf-8"`, `body` = `"﻿"` (BOM, for Thai Excel) + lines joined by `\n` (same as `closeDayCsv`; CRLF also accepted by the oracle). Escaping as `closeDayCsv` (`"` doubled, quote when `,` `"` or newline). Money in baht `toFixed(2)` (negative keeps the sign), counts as integers, percent `marginBp/100` `toFixed(2)` or empty, times BKK `YYYY-MM-DD HH:mm`. Header row (exact) + one line per report row + a last line whose first cell is `รวม`:
  - daily: `วันที่, จำนวนบิล, ยอดก่อนส่วนลด, ส่วนลด, ค่าบริการ, ยอดขายสุทธิ, VAT, ยอดก่อน VAT, ทิป, บิลยกเลิก, ยอดบิลยกเลิก, เฉลี่ยต่อบิล`
  - products: `รหัส, ชื่อ, จำนวน, น้ำหนัก (กรัม), จำนวนบิล, ยอดเต็ม, ส่วนลดรายการ, ยอดขาย`
  - staff: `รหัสผู้ใช้, ชื่อ, จำนวนบิล, ยอดขายสุทธิ, ส่วนลด, ทิป, บิลยกเลิก, ยอดบิลยกเลิก, เฉลี่ยต่อบิล`
  - payments: `วิธีชำระ, รหัส, จำนวนรายการ, จำนวนบิล, ยอดรับ`
  - margin: `รหัส, ชื่อ, จำนวน, ยอดขาย, ต้นทุน, ต้นทุนประมาณการ, กำไรขั้นต้น, อัตรากำไร (%)`
  - shifts: `กะที่, Z ที่, สาขา, เครื่อง, สถานะ, เปิดโดย, เวลาเปิด, เวลาปิด, จำนวนบิล, ยอดขาย, เงินที่ควรมี, เงินที่นับได้, ขาด/เกิน`
  - tax: `วันที่, สาขา, เลขที่เริ่ม, เลขที่สุดท้าย, จำนวนบิล, ยอดรวม VAT, ฐานภาษี, VAT, ยอดไม่มี VAT, บิลยกเลิก, เลขที่ยกเลิก` (void numbers joined by space)
  - The daily data cells are, in order: date, billCount, gross, discount, service, net, vat, netExVat, tip, voidCount, voidTotal, avg (the oracle checks these cell by cell).
R12 **Permission.** New key `pos.report.view` ("ดูรายงานขาย กำไร พนักงาน ภาษี และส่งออก CSV") in the pos module (`permissions.ts:133-139`, one marked line). All 7 reports and CSV require it at the unit(s) read; OWNER/MANAGER get it through `evaluate`. The dashboard card keeps today's rule (`pos.sale.create`, same as `posSalesScope` and the "ยอดวันนี้" block), because it shows only today's totals. `/pos/close` is unchanged. (Q17.4)
R13 **Scope.** The system must be an `AppSystem` of `ctx.tenantId` with `type POS`, else `NOT_FOUND` (other tenant, inventory system, unknown id). Units read = `ctx.unitId` if given (must be a `BusinessUnit` of the tenant the actor can access with the report permission, else `NOT_FOUND`), otherwise every tenant unit the actor can access with it (OWNER/`*` = all tenant units, including archived ones, so history never disappears after an unlink). Every PosSale query is `{ tenantId, systemId, unitId: { in: units }, createdAt: { gte, lt } }` (+ status). Restricted users silently see only their units.
R14 **Actions.** `src/lib/modules/pos/report-actions.ts` (`"use server"`, only `export async function`, no `throw`, thin shell like `shift-actions.ts`): `posReportAction({ systemId, unitId?, kind, from, to, limit? })` → the matching report; `posReportCsvAction({ systemId, unitId?, kind, from, to })` → the CSV result (the page turns it into a download); `posDashboardCardAction({ systemId, unitId? })`. Session → ctx/actor exactly as `shift-actions.ts:53-75`; unexpected errors → `{ok:false, code:"INTERNAL"}` with `unstable_rethrow`. No revalidate (read-only).
R15 **Performance.** ≤ 92 days per call. Each report is a constant number of queries independent of the day count: sales by `(tenantId, unitId IN, createdAt range)` (uses `PosSale_tenantId_unitId_createdAt_idx`), lines/payments by `saleId IN` in chunks ≤ 1000 (indexed), movements by `(tenantId, idempotencyKey) IN` chunks (unique index), users/units/items by id. No per-day loop of queries (unlike `api/ops/reports.ts`), no `include` of whole rows (select the needed columns), no writes. Optional SQL aggregation is fine if it keeps the same filters.
R16 **Dashboard card numbers.** `posDashboardCard(ctx, actor, { now? })` (now injectable for tests; default `new Date()`): `businessDate (BKK of now), netSalesSatang, billCount, avgBillSatang, voidCount, tipSatang, yesterdayNetSalesSatang, deltaBp (Math.round((today − yesterday) × 10000 / yesterday), null when yesterday = 0), openShiftCount (OPEN shifts in the scope units), topProduct ({key, name, qty, salesSatang} | null — first row of today's products)`. Scope as R13 with the `pos.sale.create` permission. It is per POS system; wiring the tenant dashboard widgets (`lib/dashboard/service.ts`, first-POS today) to it is builder U's call, not this round.

## 3. Owner questions (the oracle encodes the recommended default)
- **Q17.1 Who sold the bill.** Bills store no seller today. Recommended: add `soldByUserId` (R6) — new bills from the sales screen get it; old bills fall back to the shift opener, else "ไม่ระบุ". — *รายงานยอดต่อพนักงาน: ให้ระบบเริ่มเก็บ "คนขาย" ในบิลใหม่ (บิลเก่าใช้คนเปิดกะแทน / ไม่ระบุ) ใช่ไหม?* Default: yes.
- **Q17.2 When does a day end.** Recommended: midnight Bangkok, same as today's close-day page. Shops open past midnight (bars) would want e.g. 04:00 — a setting for P1.18. — *ตัดยอดวันตอนเที่ยงคืน (เหมือนหน้าปิดวันตอนนี้) หรือร้านต้องการตัดตอนตี 4?* Default: midnight.
- **Q17.3 Margin basis.** Recommended: per-product margin on line totals including VAT, before bill discounts (exact, no allocation guesswork), plus an exact shop-level "กำไรสุทธิก่อน VAT" in totals; cost = the cost recorded when stock was cut, else today's average cost marked "ประมาณ". — *กำไรต่อสินค้าคิดจากยอดรวม VAT ก่อนส่วนลดท้ายบิล และแสดงกำไรสุทธิก่อน VAT ทั้งร้านแยกไว้ — โอเคไหม?* Default: yes.
- **Q17.4 Who sees reports.** Recommended: new right "ดูรายงาน" (`pos.report.view`): owner and managers automatically, staff only if given; the today card and close-day page stay visible to anyone who can sell. — *แคชเชียร์ควรเห็นรายงานกำไร/ยอดพนักงานไหม? (แนะนำ: ไม่ เว้นเจ้าของให้สิทธิ์)* Default: as recommended.
