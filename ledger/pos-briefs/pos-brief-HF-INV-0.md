## In scope (fix)
- **D14** inventory pages (`src/app/app/sys/[id]/inventory/**` and any other route that renders inventory data): any member of the tenant can open them and see costs and suppliers; server actions in `src/lib/modules/inventory/actions.ts` accept ANY system id of the tenant without checking it is an INVENTORY system. Rule: house page guard (404-not-403: `requireTenant()` → system `findFirst({id, tenantId, type: "INVENTORY"})` → `notFound()` → actor → the module's read permission → `notFound()`); every action re-resolves the system by `{id, tenantId, type: "INVENTORY"}` before anything else; cost/supplier fields are shown only to roles that hold the permission the module already uses for cost (find it; if none exists, gate the whole page on the existing inventory read permission and note it). Use EXISTING permission keys only — do not edit `permissions.ts`.
- **D3** `transfer` (`inventory/actions.ts:~228` → `inventory/service.ts:~679-749`): `fromLocationId` / `toLocationId` from the client are not checked ⇒ transferring from a made-up location id creates stock in a real one. Rule: both locations must exist, belong to this tenant + this inventory system, be active; source must hold the quantity (follow the module's existing negative-stock policy — do not invent a new one; if the module allows negative stock elsewhere, at least the source location must be real). Same check for every other action that takes a location/lot/item/PO id from the client (receive, issue, adjust, count, lot, PO actions in `procurement.ts`) — audit all and list them.
- Any AI tool or route that returns inventory cost/stock without the module permission (the `/api/v1/inventory/items` key-scope hole is ALREADY fixed in another hotfix — do not touch that route; do not touch `src/lib/ai/proposals.ts`).
