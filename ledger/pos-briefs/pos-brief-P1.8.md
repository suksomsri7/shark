## 2. Contract (controller rulings — additive only, F15.2; COMMON 2 keeps `createSale/voidSale` signatures)
R1 **A refund is a new document, never a mutation.** New enum `PosSaleDocType { SALE, REFUND }` (new type, so no `ALTER TYPE … ADD VALUE`); `PosSale.docType` default `SALE`; `PosSale.refSaleId String?` (loose id, no FK, like `shiftId`; index deferred to P6.1 CONCURRENTLY); `PosSaleLine.refLineId String?`; `PosSaleLine.restock Boolean?` (REFUND lines only: true = goods came back, false = not restocked / damaged). Amounts on a REFUND document are **positive** and interpreted by `docType` (spec `:430`). `status` of a REFUND document is `PAID` (money moved); `VOIDED` is not allowed on it in P1.8 (refund of a refund = out of scope).
R2 **Original bill bookkeeping.** `PosSale.refundedSatang Int @default(0)` accumulates on the SALE document; `status` flips `PAID → REFUNDED` only when every line is fully refunded (Σ refunded qty = qty for all lines) — partial refunds keep `PAID`. Net revenue of a SALE document = `grandTotal − refundedSatang`.
R3 **Every reader of `PosSale` must become doc-type aware.** Builder greps every `posSale.findMany/findFirst/count/aggregate/$queryRaw` in `src/` and, per site, either adds `docType: "SALE"` (and subtracts `refundedSatang` where the number means net sales) or writes in the notes why the site is unaffected. Minimum set that the oracle asserts: `daySummary`, `listSales`, `closeDaySummary`, `computeReport` (X/Z), `offShiftCash`, P1.17 `reports.ts` + `report-overview.ts` ("ยอดสุทธิ หลังหักคืนเงินและยกเลิก" as the mockup header says), `posSalePaid` consumer (must ignore REFUND docs — they never emit `pos.sale.paid` anyway), CRM/member bridges. Positive control: one ฿85 refund of a ฿620 bill moves day net by **−85**, not +85, not 0.
R4 **Numbering (O2).** Sales keep `PosReceiptCounter` and `YYYYMM-NNNN` untouched. Refunds use a **new** table `PosDocCounter { unitId, docType, period YYYYMM, seq }` unique `[unitId, docType, period]`, number `CN${YYYYMM}-${NNNN}` (prefix from `settings.pos.receipt.refundPrefix`, default "CN"), reserved inside the refund tx with the same upsert-and-increment pattern. Migrating the SALE seq into `PosDocCounter` (plan §3) is **deferred** to P1.10/P6.1 — note the deviation. 🔔 Controller recaps O2 to the owner (sales unchanged, CN series separate) before the builder starts.
R5 **`refundSale(ctx, actor, input)` in `src/lib/modules/pos/refund.ts`** (new file; `service.ts` gets at most the shared helpers). Input: `{ saleId, lines: [{ lineId, qty, restock? }], payMethods: [{ type: CASH|TRANSFER|PROMPTPAY|CARD, amountSatang, reference? }], reasonCode: DAMAGED|WRONG_ITEM|CHANGED_MIND|OTHER, reason?: string ≤200, deviceId, idempotencyKey }`. Result `{ ok: true, refund: {…document, receiptNo, lines, payments}, sale: { status, refundedSatang } } | { ok: false, code, message }` — refusals as data, Thai messages, no throw across the action boundary.
   - Eligibility: SALE document, `status PAID`, not `giftCardId` (gift-card sales refund through the gift-card module), any `sourceModule` (register UI restricts to POS in P1.16); per line `qty ≤ qty − Σ already refunded (REFUND docs with `refLineId`)`, computed under `SELECT … FOR UPDATE` on the original sale row so two refunds of the same line cannot both pass; `lines` non-empty; `qty ≥ 1` integers; weighed lines (`weightGrams`) refund whole (qty 1).
   - Amount per line: pro-rata of the line's **net** value (`lineTotal − allocated bill/coupon/tier discount`, using the same `allocateBillDiscount` as the accounting bridge, moved into a shared pure helper) × `qtyRefund / qty`, half-up, the last refunded unit of a line takes the remainder so Σ over a line's refunds never exceeds its net. Service charge is refunded pro-rata to the refunded net; tip is never refunded. `vatSatang` of the refund = `splitIncludedVat(refundGross, rate)` (P1.6 helper); VAT at document level only (COMMON 1). `grandTotal(refund) = Σ line refunds + pro-rata service charge`; `Σ payMethods = grandTotal` exactly else `PAYMENT_MISMATCH`.
   - Shift binding: `shiftId` = OPEN shift of `deviceId` (P1.9 `currentShift`) if any, else null. A **CASH** refund with no OPEN shift is refused `SHIFT_REQUIRED` when the POS requires shifts for register sales (same rule `submitRegisterSale` applies, `register.ts:1685 shiftRequired`); when shifts are not required it is allowed and shows in `offShiftCash` as negative. Bills of a CLOSED shift are refundable (that is the point of refunds; `voidSale` keeps refusing them).
   - Actor: `soldByUserId` on the REFUND document = the refunding user; `note` = `reason`; `reasonCode` stored (new column `PosSale.reasonCode String?`). Permission key **`pos.sale.refund`** added to `core/permissions.ts` next to `pos.sale.void`, granted by default to OWNER/MANAGER roles only; cashier ⇒ `NO_PERMISSION` (P1.15 adds approval).
   - Idempotency (P1.6 R6 shape): same key + same payload ⇒ the stored refund; different payload ⇒ `IDEMPOTENCY_CONFLICT`. Key unique per tenant (`PosSale.idempotencyKey` already is).
   - Refusal codes: `NO_PERMISSION` `SALE_NOT_FOUND` `SALE_NOT_REFUNDABLE` `REFUND_EXCEEDS` `REFUND_EMPTY` `PAYMENT_MISMATCH` `REFUND_METHOD_INVALID` (DEPOSIT/ROOM_CHARGE) `SHIFT_REQUIRED` `REASON_REQUIRED` `IDEMPOTENCY_CONFLICT` `VALIDATION`.
R6 **Inside the refund tx**: insert REFUND document + lines + payments, reserve the CN number, update the original (`refundedSatang`, `status` per R2), release coupons **only on full refund** (spec `:913`: partial refunds do not release coupons), emit outbox **`pos.sale.refunded`** `{ saleId, refundSaleId, sourceModule, full: boolean, lines: [{ refLineId, qty, amountSatang, restock, itemId }], payMethods }` with key `PosSale#<refundSaleId>#REFUNDED`. Audit: write the central `AuditLog` row the way the platform does for money actions (builder finds the helper; if POS writes none today, add it for refund only and say so).
R7 **Consumer chain for `pos.sale.refunded`** (one registration line in `outbox-consumers.ts` — shared hot file, smallest hunk — handlers live in `src/lib/modules/pos/refund-consumer.ts` and the existing bridge files), wrapped with `withAutomation`, every step idempotent and replayable:
   1. **Account CN** — new facade `applyExternalRefund` in `account/index.ts` (REVIEW #6): unlinked book ⇒ `{posted:false, reason:"unlinked"}` never throw; otherwise create a `CREDIT_NOTE` document with `sourceDocId` = the bill's `TAX_INVOICE_ABB` document when it exists (`findDocByRef`), lines = the refunded lines (pro-rata discounts as in `bridgePosSalePaid`), `refType "PosSale"`, `refId` = **refundSaleId**, document number = the POS CN number, and post the pro-rata GL reversal (revenue 4000/4030, VAT, cash/bank by refund method via the same mapping `applyExternalSale` uses) — POS never sees an account code (D3). Idempotent: a second delivery finds the existing document/JV by ref and does nothing. `qc-account-cpa` 107 must stay identical; a new CPA-style check proves CN + JV balance for partial and full refunds.
   2. **Points** — new `point.reversePartialEarn(ctx, { refType:"PosSale", refId: saleId, amountSatang, grossSatang, idempotencyKey })` in `point/lots.ts`: reverses `floor(earned × amount / gross)` from the lot(s) the EARN created (negative remaining allowed, same as whole reverse) — the Point module computes, POS passes amounts only (D5). Full refund ⇒ `member.releaseOnVoid` path exactly as void (whole EARN+BURN reverse, vouchers released, gift-card uses refunded) so the remainder lands correctly. BURN (points used as discount) is **not** restored on a partial refund (the discount was pro-rated into the refund amount).
   3. **Member** — `member-bridges.ts#onPosSaleRefunded`: `recordSpend` negative by the refund amount (extend `recordSpendOnce` with kind `"REFUND"` + amount), then `evaluateAndApply`; stamps: full refund ⇒ `voidStampsForSale`, partial ⇒ untouched.
   4. **Inventory** — per refunded line with `restock === true` and an original OUT movement: `inventory.receive` qty at the **cost recorded on the original OUT movement** (`InvMovement.costSatang`, O12), key `pos-refund-<refundSaleId>-<refundLineId>` (contains `refund` ⇒ Dr1200/Cr5000 by the inventory bridge; distinct from void's `<saleId>-<movementId>` keys), bundles return their components the way P1.2 cut them, weighed lines return grams. `restock === false` ⇒ no movement (COGS stays, which is the loss). Failures log like HF-INV-1 R3.3 and the event retries (this is the retryable path REVIEW #10 asked for; `voidSale` is not changed).
   5. CRM/kanban bridges: **not** touched (CRM-hot files) — logged as follow-up for the CRM session.
R8 **Shift report (P1.9 follow-ups land here)**: `computeReport`/`offShiftCash` select SALE docs for sales and REFUND docs bound to the shift for refunds: `cashRefundsSatang` = Σ CASH payments of REFUND docs; new additive fields `refundCount`, `refundSatang`, `byMethod[].refundCount/refundSatang`; `expectedCash` subtracts cash refunds. `qc-pos-p1.9`/`p1.9b` stay green with no expectation change (they have no refunds); the P1.8 oracle adds the refund case (open shift → sale ฿620 cash → refund ฿85 cash → X expected = float + 620 − 85).
R9 **Read model for the UI (P1.16)**: `saleForRefund(ctx, actor, { saleId })` → lines with `refundableQty`, payments, prior refunds (CN numbers, amounts), member summary (points earned on this bill), accounting link (ABB doc number) — one composed read; plus thin actions `refundSaleAction` / `saleForRefundAction` in `src/lib/modules/pos/refund-actions.ts` ("use server", refusal as data, `revalidatePath` of the bills page).
R10 **Out of this card**: store credit (§6 Q1), gateway refunds (Beam/PromptPay dynamic — P1.7; "คืนเข้า PromptPay เดิม" = TRANSFER/PROMPTPAY with manual reference), approval/PIN (P1.15), refund of DEPOSIT/ROOM_CHARGE-paid bills beyond cash/transfer, printing the CN (P1.10), the bills page UI (P1.16), API v1 `POST /sales/:id/refund` (HF-APIV1 follow-up), AI tool (CRM-hot `ai/tools.ts`), migrating the SALE counter (R4).
