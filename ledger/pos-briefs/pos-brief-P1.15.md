## 2. Rules (server, oracle-tested)
- **R1 PIN store**: `PosStaffPin { id, tenantId, unitId, userId, pinHash, failedCount Int @default(0), lockedUntil DateTime?, setById, createdAt, updatedAt, @@unique([unitId, userId]), @@index([tenantId, unitId]) }`. PIN = 4–6 digits; hash = `scrypt` (node `crypto.scryptSync`, random 16-byte salt, stored `salt:hash` hex) — never plain, never `Math.random`. `setStaffPin(ctx, actor, { userId, pin })`: self (any member with `pos.sale.create` in the unit) or manager (`pos.staff.manage`, new key, OWNER/MANAGER) for anyone in the unit; weak PINs `0000 1234 1111 123456 000000` → `WEAK_PIN`. Only one row per (unit,user); setting again replaces and resets `failedCount/lockedUntil`.
- **R2 verify**: `verifyStaffPin(ctx, { unitId, deviceId, pin })` (no actor — the device is the caller; `deviceId` = the P1.9/P1.10 client id) → `{ ok:true, userId, role, staffToken, expiresAt }` | refusal `PIN_INVALID` (generic — never says which user) | `PIN_LOCKED` (after **5** consecutive failures per PIN row: `lockedUntil = now + 15 min`; manager `unlockStaffPin` clears it) | `DEVICE_REVOKED` (P1.10 guard). The PIN is matched against **all** active rows of the unit whose user still has a membership with `pos.sale.create` (a 6-digit space with ≤ 50 staff is fine; document the collision rule: two identical PINs in a unit ⇒ `setStaffPin` refuses `PIN_TAKEN`). `staffToken` = HMAC-SHA256 over `{tenantId, unitId, deviceId, userId, exp}` with `SESSION_SECRET`, **12 h**, verified by `staffFromToken(ctx, token)` → `{ userId } | null` (expired/foreign device ⇒ null). Audit `pos.staff.pin_verified` only on success (no PII beyond userId); failures counted on the row, not audited individually.
- **R3 who sells**: `submitRegisterSale`, `holdRegisterCart`, `recallHeldCart`, `openShift` accept optional `staffToken` (exact key); when valid, `soldByUserId` (sale) / `openedByUserId` (shift) / held-cart `byUserId` = the token's user; invalid/expired token ⇒ `STAFF_TOKEN_INVALID` (refusal, never silently falls back to the session user). Without a token: today's behaviour (session user). The token's user must still have `pos.sale.create` in that unit at submit time (membership revoked ⇒ `STAFF_TOKEN_INVALID`).
- **R4 discount cap**: `settings.pos.discount = { maxBpByRole: { CASHIER: 1000, MANAGER: 10000, OWNER: 10000 }, overrideRequiresPin: true }` (parse with defaults; additive to the settings parser used by `register.ts#regMaxDiscountBp` — replace the constant lookup with the role lookup, keeping `REGISTER_STAFF_MAX_DISCOUNT_BP` as the CASHIER default so `qc-pos-p1.3` stays green). Cap applies to line + bill discounts combined as `priceCart` computes today. Over cap ⇒ `DISCOUNT_EXCEEDS_LIMIT` **unless** the request carries `managerPin` (exact key; verified via R2 against a user whose role cap covers the discount) ⇒ allowed + `writeAudit("pos.discount.override", { saleId, byUserId: managerUserId, forUserId, discountBp })`; a wrong `managerPin` ⇒ `PIN_INVALID` and counts toward the lock-out. If the tenant has an approval policy for `POS_DISCOUNT_OVER` (R5) and no `managerPin` ⇒ `APPROVAL_REQUIRED` with `{ requestId }` (the cart is auto-held via `holdRegisterCart` under the request so the register can recall it when approved).
- **R5 approval core**: entity types `POS_VOID` (entityId = saleId), `POS_REFUND` (saleId; amount = refund total), `POS_DISCOUNT_OVER` (entityId = held cart id; amount = discount satang). `resolvePolicy({ entityType, unitId, systemId, amountSatang })` decides; **policy ⇒** `submitForApproval` (one open request per entity ⇒ second attempt `PENDING_APPROVAL`), the action itself does **not** run; `voidSaleByActor` / `refundSale` / `submitRegisterSale` return `{ ok:false, code:"APPROVAL_REQUIRED", requestId }`. **No policy ⇒** today's path. **Fallback on device**: any of the three with `managerPin` (R2, a user with `pos.sale.void`/`pos.sale.refund`/cap-covering role) executes immediately with audit `pos.approval.pin_override { requestId?: null, action, byUserId }` — even when a policy exists (C-9 "เร็ว ไม่ต้องรอ"), and cancels an open request for the same entity if one exists (`cancelRequest`).
- **R6 consumer**: `pos-approval-consumer.ts` on `approval.request.approved` / `.rejected` for `entityType` starting `POS_` (registered in `outbox-consumers.ts` next to the existing approval chain, smallest hunk): approved `POS_VOID` ⇒ `voidSale(tenantId, unitId, saleId, { audit:{ byUserId: deciderId, via:"approval", requestId } })`; `POS_REFUND` ⇒ `refundSale` with `idempotencyKey = "approval-" + requestId` and the payload stored at submit (lines/amount/method/reason snapshot in `ApprovalRequest`'s payload field — if the core has none, store the snapshot in a new `PosApprovalPayload { requestId @id, tenantId, kind, payload Json, createdAt }` and say so); `POS_DISCOUNT_OVER` ⇒ mark the held cart `approvedRequestId` so one recall+submit passes the cap once (consumed on submit; second use ⇒ `DISCOUNT_EXCEEDS_LIMIT` again). Rejected ⇒ nothing executes; the register reads `requestStatuses` and shows the reason. Consumer idempotent (replay creates no second void/refund — rely on `voidSale`'s already-voided guard and the refund idempotency key).
- **R7 permissions**: new keys `pos.staff.manage` (OWNER/MANAGER), `pos.approval.decide` is **not** new — deciding goes through the approval module's own UI/permissions. `voidSale` / `refundSale` callers unchanged otherwise. Page authz suite stays green.
- **R8 lock screen (server side)**: none — locking is client state (13B). Server contributes only `verifyStaffPin` + `listStaffForDevice(ctx, { unitId })` → unit members with `pos.sale.create` `{ userId, name, role, hasPin, shift?: { id, openedAt } }` (names allowed here: it is the staff list on a staff device).
- **R9 refusals as data**, Thai messages, keys `pos.staff.errors.*`, `pos.approval.errors.*`; `refusalMessageKey` covers `PIN_INVALID PIN_LOCKED PIN_TAKEN WEAK_PIN STAFF_TOKEN_INVALID APPROVAL_REQUIRED PENDING_APPROVAL`.

## 5. Rulings
CD1 PIN rows are per unit (a staff member working at two branches sets two PINs); no HR sync in this card.
CD2 `staffToken` is stateless HMAC (no table); revocation = membership change or `setStaffPin` (token carries `pinVersion = updatedAt epoch`, so a new PIN invalidates old tokens).
CD3 Approval entity types are strings on the existing `ApprovalPolicy.entityType` — no core schema change; if the core lacks a payload/title column, the additive `PosApprovalPayload` table is the only new table besides `PosStaffPin`.
CD4 Manager PIN on the device always wins over a pending request (C-9); it is audited with the manager's userId.
CD5 Migration additive only (`PosStaffPin`, maybe `PosApprovalPayload`, held-cart column `approvedRequestId String?`). Register in `core/scope.ts` + `scripts/pos-qc-env.mts`.
CD6 The approval module's hot files (`approval/service.ts`) are not edited; if a helper is missing, compose from existing exports or write CONTROLLER-DECISION.
