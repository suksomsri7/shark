## Why (facts, 24 Oct, perf smoke `smoke3-fix5b-20261024T101645Z` on QC5, build from a35fe494)
- P5.3 B3U "wedge scan → cart line rendered (register)" budget **p95 ≤ 100 ms** (W-next-6, `ledger/pos-briefs/pos-brief-P5.md:122`: "barcode < 100 ms on the **register (client)** path (server lookup reported)"). Measured: p50 161 · **p95 400 ms** (5 scans) and 645 ms in the run before — red twice.
- Cause = `ledger/wo-notes/pos-P5.3-oracle.md` §5 **F1**: the wedge path is not client-side. `onScannedCode` (`src/components/pos/register/RegisterScreen.tsx:1683–1697`) awaits `registerScanAction` for every scan (action p50 101 · p95 202 ms incl. Next server-action overhead; `registerScan` itself ≈ 11 queries). The client exact match exists only on the search-Enter path (`:1656–1664`, `products.filter(... barcode === lc)` on the loaded page).
- The loaded page (`products`, `registerCatalogAction` paged by cursor/category/q, `REGISTER_PAGE_MAX` 500) is partial, and the oracle scans products outside the first page on purpose (5,000-product tenant). So matching the loaded page is not enough: the register needs a **whole-unit barcode index** on the client.
- The offline snapshot (`use-offline-register.ts`, `POST /api/pos/sync/snapshot`, `issueOfflineSnapshot` in `offline-sync.ts`) already ships the unit's whole catalogue, but only when `settings.pos.offline.enabled` is on and it is bound to device+user+PIN secrets (fix1 F3 wipes it when the flag is off). Do **not** reuse it — build a small, separate, read-only index.

## Controller decision CD-P53-O14 (ruled · implement as written)
Scan = client hit when possible, server otherwise. Semantics of a client hit must equal what `registerScan` would return as `{ match: "one", product }` for a plain leaf product. Everything else (shared barcode → "choose", parent with variants → variant chooser, weighed-scale barcodes, member cards, misses) stays on the server exactly as today.
