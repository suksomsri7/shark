## 1. Scope
In: payment intents for the non-cash part of a bill before the sale exists · dynamic PromptPay QR (amount-locked EMVCo) from the branch's PromptPay ID · Beam charge creation + webhook confirmation when the platform has Beam keys **and** the shop enabled it · manual confirmation ("ยืนยันเองเมื่อเห็นเงินเข้า") with audit · expiry · `submitRegisterSale` consuming a PAID intent exactly once · polling read · card payments via Beam (same intent, kind CARD).
Out: Beam refunds (P1.8 refunds stay manual money-return; Beam refund API = follow-up) · QR for customer display (P2 11A) · PENDING_PAYMENT orders (P2.7) · bank transfer slip OCR · fees/commission accounting for card (follow-up to Account: note the MDR question) · PromptPay ID management UI (17A has no field — the ID comes from the linked book's business profile `promptpayId` as the legacy POS does; if missing ⇒ refusal).

## 2. Rules (server, oracle-tested)
- **R1 model** `PosPaymentIntent { id, tenantId, unitId, systemId, kind: "PROMPTPAY_STATIC"|"PROMPTPAY_BEAM"|"CARD_BEAM" (String), amountSatang Int, status: "PENDING"|"PAID"|"CONSUMED"|"EXPIRED"|"CANCELLED" (String), qrPayload String?, beamChargeId String?, beamRef String?, deviceId String, createdByUserId String, confirmedVia: "WEBHOOK"|"MANUAL"|null, confirmedByUserId String?, paidAt DateTime?, expiresAt DateTime, saleId String?, lateWebhook Boolean @default(false), idempotencyKey String, createdAt, updatedAt, @@unique([tenantId, idempotencyKey]), @@index([tenantId, unitId, status, createdAt]), @@index([beamChargeId]) }`. Additive migration; register in `core/scope.ts` + `scripts/pos-qc-env.mts`.
- **R2 create** `createPaymentIntent(ctx, actor, { method: "PROMPTPAY"|"CARD", amountSatang, idempotencyKey, deviceId }, deps?)` permission `pos.sale.create`; amount 1..`PRICE_MAX_SATANG`; same key ⇒ returns the existing intent (`{ ok:true, intent, reused:true }`), same key + different amount ⇒ `IDEMPOTENCY_CONFLICT`. Mode: Beam is used only when `beamEnabled()` (platform keys) **and** `settings.pos.payment.beam.enabled === true` (shop opt-in, default false — additive settings key with parser defaults); PROMPTPAY without Beam ⇒ `PROMPTPAY_STATIC` with `qrPayload = promptpayPayload({ id: <branch PromptPay ID>, amountSatang })`; no valid PromptPay ID ⇒ `PROMPTPAY_NOT_CONFIGURED` (Thai message tells the manager to set it in the account business profile). PROMPTPAY with Beam ⇒ `createCharge({ amountSatang, referenceId: "pos-" + intent.id, method: "promptpay" })` through an injectable `deps.beam` (same shape as the account module's `beamAdapter`) ⇒ `PROMPTPAY_BEAM` with `beamChargeId` + the QR payload Beam returns; Beam API failure ⇒ **fall back to STATIC** (polite close) and record an ops event `pos.payment.beam_fallback`. CARD ⇒ Beam only; otherwise `CARD_UNAVAILABLE`. `expiresAt = now + settings.pos.payment.qrExpiryMinutes (default 15, 5..60)`. DEVICE_REVOKED guard (P1.10) applies.
- **R3 confirm**: (a) webhook — the POS facade `onBeamWebhookEvent({ referenceId, chargeId, status, amountSatang, raw })` called from the route's `pos-` branch ⇒ `markIntentPaid(intentId, { via:"WEBHOOK", beamRef, amountSatang })`: PENDING ⇒ PAID (`paidAt`, `confirmedVia`), already PAID/CONSUMED ⇒ no-op `{ ok:true, idempotent:true }`, amount ≠ intent ⇒ `AMOUNT_MISMATCH` (status unchanged, ops event WARN), EXPIRED-but-PENDING-by-time ⇒ still PAID with `lateWebhook:true` (money arrived), CANCELLED ⇒ `INTENT_CANCELLED` (ops event: refund needed). The route returns 200 for unknown references (never leaks) and 401 on bad signature (existing behaviour). (b) manual — `confirmPaymentIntentManual(ctx, actor, { intentId })` permission `pos.sale.create`; `settings.pos.payment.manualConfirmRequiresManager` (default false) ⇒ when true needs `pos.shift.manage`; PENDING ⇒ PAID via MANUAL + `writeAudit("pos.payment.manual_confirm", { intentId, amountSatang })`; expired ⇒ `INTENT_EXPIRED`; PAID already ⇒ idempotent ok. (c) `cancelPaymentIntent(ctx, actor, { intentId })` PENDING ⇒ CANCELLED (audit); PAID ⇒ `INTENT_PAID` (cannot cancel money that arrived — must consume or refund manually).
- **R4 consume in the sale**: `submitRegisterSale` payMethod `{ type:"PROMPTPAY"|"CARD", amountSatang, reference }`: when `reference` matches `^pi_` (intent ids get the `pi_` prefix — oracle names it) ⇒ in the sale transaction lock the intent `FOR UPDATE`; require same tenant/unit, status PAID, amount equal (`INTENT_NOT_PAID` / `AMOUNT_MISMATCH` / `INTENT_CONSUMED` / `INTENT_NOT_FOUND`); set `status = CONSUMED`, `saleId`; `PosPayment.reference = intentId`, `note = "via WEBHOOK|MANUAL"`. Two submits racing on one intent ⇒ exactly one sale. Idempotent replay of the same submit (same sale key) ⇒ same sale, intent still CONSUMED by it. **Without** a `pi_` reference, PROMPTPAY behaves as P1.6 today (static QR + cashier's own confirmation) — unchanged, so `qc-pos-p1.6` stays green; CARD **requires** a PAID intent (`CARD_REQUIRES_INTENT`).
- **R5 expiry**: `expirePaymentIntents(tenantId?)` sweep PENDING past `expiresAt` ⇒ EXPIRED (idempotent, returns count); `paymentIntentStatus(ctx, actor, { intentId })` applies the same rule lazily (returns `EXPIRED` for a stale PENDING without writing, or writes — oracle writer picks and names it) and returns `{ status, amountSatang, kind, qrPayload, expiresAt, paidAt, confirmedVia }` for the 2-second register poll. Registered cron entry only if the repo has a cron registry for POS (P1.9 force-close used one — follow it; otherwise the sweep is called from `registerStatus`).
- **R6 events**: outbox `pos.payment.intent_paid { intentId, unitId, amountSatang, via }` on PAID (consumer: no-op registration; customer display P2 will use it). No event on CONSUMED (the sale's `pos.sale.paid` covers it).
- **R7 money**: `PosPayment.type` stays `PROMPTPAY` for both static and Beam PromptPay; CARD uses `PosPayType.CARD` if the enum has it, else the oracle writer writes CONTROLLER-DECISION (adding an enum value is additive and allowed). Account consumer `pos.sale.paid` already books by payment type — verify `qc-pos-account` unchanged; MDR fee = follow-up (note it).
- **R8 refusals as data**, Thai messages, keys `pos.payment.errors.*`, `refusalMessageKey` for the new codes; never throws; the webhook facade never throws (route must still answer).

## 5. Rulings
CD1 Beam opt-in is per shop (`settings.pos.payment.beam.enabled`); platform keys alone never route money through Beam.
CD2 Static PromptPay has no automatic confirmation — manual confirm is the honest path and is audited; no "assume paid".
CD3 Intents are created per attempt (cart key + method + amount) and expire; a changed amount = a new intent; the old one is cancelled by the client (not required by the server).
CD4 Late webhooks after expiry mark PAID (money is real) and the register may still consume within 24 h of `paidAt`; after that the manager handles it manually (follow-up for a report "เงินเข้าไม่มีบิล").
CD5 Migration additive only (`PosPaymentIntent`, optional `PosPayType.CARD` value). No change to `createSale`'s signature; the intent check lives in `register.ts`'s submit path with the sale tx client.
CD6 Account/MDR fees and Beam refunds are follow-ups; record them in the notes for the owner.
