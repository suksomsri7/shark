## 4. Transport — recommendation (a) server snapshot + short poll
- (a) **Recommended**: register → `publishDisplayState` (UPDATE one row) · display → `readDisplay` poll 1 s while `cart/paying`, 3 s `idle`, 1 s for 20 s after `done`; `changed:false` answers are ~60 bytes. Cost: writes ≤ 1/s only while the cashier edits (quote-settled), typical bill ≈ 5–15 writes; reads 1 Hz × open hours ≈ 40 k indexed selects/day/display — Neon compute is awake during trading anyway (register heartbeat 30 s, status 60 s). Intent PAID shows within 1 s even if the register lags (server reads intent status).
- (b) BroadcastChannel/same browser: zero server cost but requires the display on the same device — contradicts `DESIGN-POS.md:71`; keep only as an optional same-device fast path later.
- (c) SSE: a Vercel function per open display for hours (duration billing) and still needs DB polling server-side (no pub/sub; Ably is optional and keyless in QC `realtime/client.ts:5–13`). Reject for P2.10; Ably signal "display <id> changed" can be a later accelerator on top of (a) exactly like `useBoardLive.ts:4`.

5. **Pay hunk** → optional `onDisplayPay` prop on PayDialog (marked) vs reading intents only server-side (loses part-pay/cash change). Rec: prop.
