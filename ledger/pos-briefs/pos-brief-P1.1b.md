## Contract (rulings)
G1 **One writer.** After Part A the only files that write catalogue data are `src/lib/modules/pos/catalog.ts` and ONE new sibling `src/lib/modules/pos/catalog-legacy.ts` (F15.1 writer set = these two; ORACLE-EDIT for S2.19 wording approved). G2 **Legacy functions stay the public doors.** Every legacy exported function (`restaurant/menu.ts` createItem/updateItem/duplicateItem/archiveItem/setItemStock/resetDailyStock/createCategory/archiveCategory/createOptionGroup/archiveOptionGroup/setItemOptionGroups…, `shop/service.ts` createProduct/updateProduct, `account/product.ts` createProduct/updateProduct, `account/inventory-link.ts` link functions, `inventory/service.ts` createItem/updateItem, `booking/service.ts` importServicesToCatalog, `pos/register.ts` setItemSalePrice) keeps its signature, return shape, permission checks, audit rows, Thai messages and transaction boundaries. Only the WRITE statement moves: the body calls a function in `catalog-legacy.ts` with the caller's transaction client, which performs the legacy write (same data as today, byte-for-byte for every field not owned by the sync) AND the PosProduct side in the SAME transaction. No outbox, no after-commit sync, no background job.
G3 **One derivation.** The mapping "legacy row(s) → PosProduct fields" (kind, unitId, price precedence = what the till charges today as ratified in P1.1a R2/R4 incl. [C7] posPrice rule, tri-state trackStock, category, option groups, RecipeLine for menu→InvItem, archived state) must be ONE function used by both the backfill and the sync — refactor the backfill to call it; prove with the oracle that backfill-then-edit equals edit-then-backfill (same rows).
G4 **Direction rules.** (a) Legacy → catalogue: runs as the system caller (the legacy function already authorised the actor under its own module's rules; a restaurant manager does not need `pos.product.manage`). The marker may appear only in `catalog.ts` and `catalog-legacy.ts` (add the latter to `SYSTEM_MARKER_ALLOWLIST` with a reason) and `catalog-legacy.ts` must not be importable by request code directly: its exports take an already-open transaction client and are called only from the legacy service files (fitness: forbid imports of `catalog-legacy` from `src/app/**`, `src/lib/actions/**` and any `"use server"` file — extend F15.5). (b) Catalogue → legacy (S2.13–S2.16, S2.24): `catalog.setPrice/updateProduct/archive/restore` write the linked legacy row(s) in the same transaction under the CATALOGUE permission rules (D1 scope); price goes to exactly one legacy field per row kind (PRODUCT linked to AccountProduct → `salePrice`; SERVICE → `InvItem.priceSatang`; MENU → `MenuItem.basePrice`; web-only → `ShopProduct.priceSatang`; a PRODUCT with no AccountProduct → PosProduct only, never creates an AccountProduct — P1.1a X8.1). (c) No ping-pong: each door writes both sides once; a sync function never calls a door.
G5 **Shared rows.** One PosProduct fed by several legacy rows (InvItem + AccountProduct + ShopProduct): the R2 precedence decides; a lower-precedence writer must not overwrite the price (S2.9), but its own legacy field is still written. State the full table in the notes.
G6 **Archive/restore.** Legacy archive → `archive`; legacy un-archive (InvItem, MenuItem, ShopProduct, category, option group) → `restore`; `ensureForInvItem` never un-archives (pinned S3.48). First apply the P1.1a final-review fix N1: `restore` calls `requireRowWrite` on the LOCKED row (catalog.ts ~:1062).
G7 **Locks.** One lock order for both directions: tenant try-lock (only where P1.1a needs it: new barcode / new invItem link) → PosProduct row → legacy row(s) in a fixed table order (state it).
