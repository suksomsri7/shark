# Brief — P1.13 ใบกำกับภาษีเต็มรูปจากจอชำระ + DBD lookup (ปิดสุภาพ) · lane A · ⏮ P1.6, P1.11 S

## 1. Scope
S half (this brief): buyer snapshot on the sale, full tax invoice issued through the accounting facade (instead of the ABB) at pay time or later from a P1.11 request / the bills page, DBD juristic lookup facade (polite close when no key), remembered buyer profile per member, actions, migration, oracle. U half (P1.13U, later): 15A dialog on the pay screen, bills drawer "ออกใบกำกับเต็มรูป", 17A/accounting link.

## 2. Rules (server, oracle-tested)
- R1 **Snapshot**: `PosSale.taxInvoice Json?` = `{kind:"PERSON"|"JURISTIC", name, taxId (13 digits), branchCode ("00000" head office or 5 digits), address, email?: string|null, source:"MANUAL"|"DBD"|"PROFILE", requestedAt ISO}` validated by a pure `parseTaxInvoiceBuyer(input)` (trim; name ≤ 120; address ≤ 300; email RFC-light ≤ 120; taxId mod-11 checksum per Thai RD rule — reject bad checksum with `TAX_ID_INVALID`). Stored once; immutable after the document is issued (`taxInvoiceDocId` set).
- R2 **At pay time**: `submitRegisterSale` input gains optional `taxInvoice` (same shape); validation errors ⇒ `VALIDATION`/`TAX_ID_INVALID` before anything is written; the snapshot is written in `createSale` tx. Accounting consumer: when the sale carries `taxInvoice`, `applyExternalSale` is called with a new optional `buyer` field and creates **`TAX_INVOICE`** (not `TAX_INVOICE_ABB`) with the buyer on the document (contact resolved by taxId+name through the existing contact resolver: reuse a party with the same taxId at this tenant, else create one with `taxId`, `branchCode`, `address`); money/GL identical to the ABB path; `PosSale.taxInvoiceDocId` set from the consumer result; event `pos.sale.taxInvoiceIssued {saleId, docId}` emitted by the consumer (no-op consumer registered + label). Unlinked book ⇒ snapshot kept, `{posted:false, reason:"unlinked"}`, no docId (U shows "ยังไม่ผูกระบบบัญชี").
- R3 **Later issue**: `issueFullTaxInvoice(ctx, actor, {saleId, buyer, requestId?})` for a PAID/partially-refunded SALE within 7 days of `paidAt` (`TOO_LATE` after), not VOIDED (`SALE_VOIDED`), not already issued (`ALREADY_ISSUED`), VAT-registered book with ABB kind (`NOT_ELIGIBLE` for non-VAT/unlinked); permission `pos.sale.read` + `pos.taxinvoice.issue` (new key; OWNER/MANAGER default). Writes the snapshot, calls `account.convertAbbToTaxInvoice({docId of the ABB, buyer})` — a new facade function that marks the ABB document `CANCELLED`-by-supersede (`supersededByDocId`) and creates the `TAX_INVOICE` referencing it (same amounts, same date = original issue date, running number from the TAX_INVOICE series), GL untouched (same money) — if the book has no ABB document for the sale yet (consumer lag), refuse `ACCOUNT_PENDING` (retryable). Marks a linked `PosTaxInvoiceRequest` (P1.11) `ISSUED` with `issuedDocId` (additive column) and audit `pos.taxinvoice.issued`. Idempotent by saleId.
- R4 **From request**: `issueFromTaxInvoiceRequest(ctx, actor, {requestId})` = R3 with the buyer taken from the request row; `rejectTaxInvoiceRequest(ctx, actor, {requestId, reason})` ⇒ `REJECTED` + audit. Both only for requests of this unit.
- R5 **DBD lookup**: `lookupBuyerByTaxId(ctx, actor, {taxId})` → `{ok:true, found:true, buyer:{kind:"JURISTIC", name, taxId, branchCode:"00000", address, status}}` | `{ok:true, found:false}` | `{ok:false, code:"DBD_NOT_CONFIGURED"|"TAX_ID_INVALID"|"DBD_UNAVAILABLE"}` — wraps `account/dbd.ts#lookupJuristic` (injectable `deps.lookup` for tests; never calls the network in the oracle), rate-limited 30/min per unit by counting `AuditLog pos.taxinvoice.dbd_lookup` rows (audit on every call, masked taxId `xxxxxxxxx1234`). No key ⇒ `DBD_NOT_CONFIGURED` (polite close; U shows "กรอกเอง").
- R6 **Remember for member**: `PosBuyerProfile {id, tenantId, customerId @unique, kind, name, taxId, branchCode, address, email, updatedAt}`; `rememberBuyer` flag on submit/issue with `memberId` present ⇒ upsert; `buyerProfileForMember(ctx, {memberId})` read for prefill. Never on the CRM `Customer` model.
- R7 **Readers**: `publicReceipt.actions.taxInvoice` (P1.11) becomes `ISSUED` when `taxInvoiceDocId` is set; `receiptPayload.kind` switches to a "FULL" marker so the printed slip says "ออกใบกำกับภาษีเต็มรูปแล้ว เลขที่ <docNo>" instead of the ABB header (renderer text only; the 80-mm layout unchanged); bills `BillDetail` gains `taxInvoice {status: NONE|REQUESTED|ISSUED, docNo?, buyerName?}`.
- R8 **Refund after full invoice**: `refundSale` on a sale with `taxInvoiceDocId` ⇒ the credit note references the TAX_INVOICE doc (not the ABB) — `applyExternalRefund` already finds the doc by ref; make `findExternalSaleDoc` prefer the TAX_INVOICE when both exist. Oracle-tested.
- R9 **Messages**: keys `pos.taxInvoice.errors.*` th+en for every refusal code; `refusalMessageKey` extended.

## 3. Migration (QC4 only, additive — CD5 pattern)
`PosSale.taxInvoice Json?`, `PosSale.taxInvoiceDocId String?`, `PosTaxInvoiceRequest.issuedDocId String?`, table `PosBuyerProfile` (+ `@@index([tenantId, taxId])`), `AccountDocument.supersededByDocId String?` (account schema — one nullable column, additive; the account owner session is paused, record it in `POS-OWNER-PENDING.md`). Register in `core/scope.ts` + `scripts/pos-qc-env.mts`. Migration from a schema-to-schema diff, never from the DB.

## 4. Oracle plan (`scripts/qc-pos-p1.13.mts`, ~24 checks)
Fixtures: own temp tenant (prefix `posqc-p113-`) with a POS linked to a VAT book (ABB kind) + a POS unlinked, a member customer, a device + open shift; DBD via injected `deps.lookup` stub. `B1–B4` parser (checksum good/bad, branch, kinds, trims). `S1–S4` pay-time: submit with buyer ⇒ snapshot + consumer ⇒ `TAX_INVOICE` doc with buyer contact, no ABB, GL totals equal to an identical sale without buyer, `taxInvoiceDocId` set, event emitted once. `L1–L5` later issue: ABB → superseded + TAX_INVOICE with same amounts/date; idempotent; TOO_LATE (fixture paidAt −8 d); ALREADY_ISSUED; unlinked ⇒ NOT_ELIGIBLE. `Q1–Q3` from P1.11 request ⇒ ISSUED + `issuedDocId`; reject ⇒ REJECTED; other unit ⇒ NOT_FOUND. `D1–D3` DBD: stub found/not found; no key ⇒ DBD_NOT_CONFIGURED; rate limit 31st ⇒ RATE_LIMITED. `M1–M2` buyer profile upsert + prefill. `R1` refund after full invoice ⇒ credit note refs TAX_INVOICE. `P1–P2` public receipt action ISSUED; `receiptPayload` full-invoice marker. `Z1` residue 0 + money suites unchanged (run `qc-pos-account`, `qc-account-cpa` after).

## 5. Rulings
CD1 Full tax invoice **replaces** the ABB for that sale (Thai practice): supersede, never two live documents for one sale.
CD2 Document date of the later-issued TAX_INVOICE = original sale date; numbering from the TAX_INVOICE series of the book.
CD3 DBD is a facade with a stub in tests; the real key lives in env on prod only (`DBD_API_KEY`) — never read `.env`.
CD4 Buyer contact resolution reuses the account contact resolver; taxId match wins over name match.
CD5 Migration additive only; the `AccountDocument.supersededByDocId` column is the only touch outside POS tables.
CD6 Money suites COMMON §7 must be identical before/after.

## Hard rules
Money integer satang · never change `createSale`'s consumed signature (additive input only) · every new event has a consumer · POS imports only the `account` facade (`@/lib/modules/account`), never account internals · `"use server"` files export only async functions · fitness edges unchanged.
