## 2. Rules (server, oracle-tested)
- **R1 Channel/branch price rows** `PosProductChannelPrice {id, tenantId, systemId, productId, channelCode String?, unitId String?, priceSatang Int?, notSold Boolean @default(false), updatedByUserId, createdAt, updatedAt}`. Row kinds: (code, null) = channel price for all branches · (code, unit) = channel price at one branch · (null, unit) = branch price for every channel · (null, null) is forbidden (that is the base). `channelCode` rather than `channelId`: channels are per unit (P2.1 CD1) while products are per system, and cross-branch identity is `code` (P2.1 §9). Code must match `CHANNEL_CODE_RE` and be a builtin or a code of a non-archived SalesChannel in this system, else `VALIDATION` "ไม่รู้จักช่องทางนี้". `notSold=true` ⇒ `priceSatang` null. Price is an integer 0..`PRICE_MAX_SATANG` (`pricing-shared.ts:78`). Weighed products ⇒ `VALIDATION` (CD7). One row per (product, code, unit), NULLs equal (§3).
- **R2 Writer** `catalog.setChannelPrices(ctx, {productId, rows:[{channelCode|null, unitId|null, priceSatang|null, notSold?}]})` replaces the full row set of one product in one tx (exact keys; unknown key ⇒ `VALIDATION`; ≤ 60 rows; duplicate (code, unit) in the input ⇒ `VALIDATION`). Permission `pos.product.setPrice`, same `requireRowWrite` scope as `setPrice`: rows with `unitId` null need tenant-wide price rights (`access.ts:69–73` semantics), rows with a unit need that unit. Another tenant/system ⇒ `PRODUCT_NOT_FOUND` (404-not-403). Audit `pos.product.channelPrice {productId, before[], after[]}` with the real userId. Optional bulk tool (CD6): `catalog.bulkChannelMarkup(ctx, {channelCode, unitId|null, markupBp 1..20000, roundTo 1|100, productIds≤500 | categoryId})` writes **absolute** rows = `roundHalfUp(base × (10000+bp)/10000, roundTo)` and skips products without a base price. Channel prices never write back to AccountProduct (accounts keep the base).
- **R3 Price rules** `PosPriceRule {id, tenantId, systemId, name (1..60), kind HAPPY_HOUR|PROMO, active, priority Int 0..100, productIds String[] (≤500), categoryIds String[] (≤50), channelCodes String[] ([] = all), unitIds String[] ([] = all), adjust PRICE|PERCENT_OFF|AMOUNT_OFF, valueSatang Int?, valueBp Int?, startsAt?, endsAt?, weekdays Int[] (0=อา…6=ส, [] = every day), timeFrom "HH:MM"?, timeTo "HH:MM"?, archivedAt?, createdByUserId, updatedByUserId, createdAt, updatedAt}`. Validation: at least one of productIds/categoryIds; PRICE value 0..MAX; PERCENT_OFF bp 1..10000; AMOUNT_OFF 1..MAX; times both or neither, from < to (no overnight window, CD8); `startsAt < endsAt`. ≤ 100 non-archived rules per system ⇒ `PRICE_RULE_LIMIT`. Service `pos/price-rule.ts`: `listPriceRules(ctx, actor, {includeArchived?})` (needs `pos.sale.read`|`pos.sale.create`), `savePriceRule` (exact keys), `archivePriceRule`. Writes need the new key **`pos.price.rule`** "ตั้งโปรราคาและ happy hour" (OWNER/MANAGER by default). A rule with `unitIds=[]` needs every linked unit, else `PERMISSION_DENIED`. Another tenant/system ⇒ `PRICE_RULE_NOT_FOUND`. Audit `pos.priceRule.created|updated|archived {ruleId, before?, after}`.
- **R4 Resolution order (pure `resolveUnitPrice` in `price-shared.ts`, one `at` per call).** Input: product row (+ parent for a variant), channel code, unitId, price rows, active rules, `at`. Steps:
  - ① Open price ⇒ `OPEN`; custom line ⇒ `CUSTOM`; weighed ⇒ `WEIGHED`. Rules and channels are never applied to these.
  - ② `list` = base (variant → parent). Null ⇒ `PRICE_NOT_SET`, even when a rule exists.
  - ③ Branch row (null, unit) ⇒ `BRANCH`.
  - ④ Channel row (code, unit), else (code, null) ⇒ `CHANNEL`. A `notSold` row at the winning level ⇒ refusal `CHANNEL_NOT_SOLD` (line index). A variant looks up its own rows first, then the parent's.
  - ⑤ Matching rules: active, not archived, `at` in [startsAt, endsAt), Bangkok weekday ∈ weekdays, Bangkok time ∈ [timeFrom, timeTo), product ∈ productIds (own or parent id) or category ∈ categoryIds, code ∈ channelCodes, unit ∈ unitIds. Winner: highest `priority` → lowest resulting price → oldest `createdAt` → id asc. Its result is applied on the step-④ price p: PRICE ⇒ value; PERCENT_OFF ⇒ `p − halfUp(p × bp / 10000)`; AMOUNT_OFF ⇒ `max(0, p − value)` ⇒ `RULE` + ruleId.
  - ⑥ Unit = price + Σ option delta. Options are never scaled (CD5).
  - Precedence = rule > channel > branch > base (C-6 "campaign > channel > base" with the branch slotted under channel; CD2). Satang integers only; half-up on non-negative values (examples: 7 500 × 2 000 bp ⇒ 6 000; 7 550 × 1 500 bp ⇒ off 1 132.5 → 1 133 ⇒ 6 417).
- **R5 Register.** `regPrice` replaces the seam: one `at = new Date()` per call; price rows + candidate rules loaded once per call (2 queries, product-id scoped). The P2.1 seam comment text stays in place so `qc-pos-p2.1` ST3 is untouched (§8 Q8). Quote line gains additive `priceSource`, `listPriceSatang`, `priceRule {id, name} | null`. The cashier discount cap and line/bill discounts are computed on the resolved price: a rule price is a price, not a discount. Coupon, member tier, voucher and points run after it as today (P1.12 order unchanged, CD4). Service charge follows P2.1 CD8. Submit re-prices at submit time. A window flip between quote and submit ⇒ the existing `PRICE_CHANGED` with fresh totals, nothing written. Replay of a committed key still returns the original sale before any pricing (`:1945–1946`, unchanged).
- **R6 Catalog / tiles.** `registerCatalog`/`registerScan` products carry the **STORE effective price at `at`** in `priceSatang` (today it is the base) + `listPriceSatang`, `priceSource`, `priceRule {id, name, endsAt}|null`. The result gains `priceValidUntil` (earliest window edge in the next 24 h, or null) so the client refetches. `catalog.listForUnit` fills `channelPrices` with `{channelId (this unit's channel for the code, or null), channelCode, unitId, priceSatang, notSold}` (additive to the declared `{channelId, priceSatang}` shape).
- **R7 createSale (additive only, F15.2).** `lines[]` gains `priceSource?: "BASE"|"BRANCH"|"CHANNEL"|"RULE"|"OPEN"|"CUSTOM"|"WEIGHED"`, `priceRuleId?: string (≤ 40)`, `listPriceSatang?: int ≥ 0`. All are validated (bad ⇒ `VALIDATION`, nothing written) and written to `PosSaleLine`. They are **not** in `samePayload`; the price itself already is. Other callers omit them ⇒ null (read as BASE/unknown). createSale still never prices (CD3).
- **R8 Refund / void.** Refund lines keep using the stored `unitPriceSatang`. The oracle proves that a refund after the rule is archived and the base changed returns the original money. Refund docs leave the 3 snapshot columns null; readers join `refLineId`. Void: no change.
- **R9 Held carts.** Recall re-prices (existing H3). A happy-hour price that has ended ⇒ per-line `PRICE_CHANGED` notice (held 5 900 → now 7 500). Fix the probe at `held-cart.ts:292`: it carries the cart's `channelId` (and, when needed, the same `at` as the main quote).
- **R10 Exported resolver for later cards.** `pos/price.ts` `resolvePrices(db, {tenantId, systemId, unitId}, {channelId | channelCode, at, items:[{productId, optionDeltaSatang?}]}) → {ok, items:[{unitPriceSatang, listPriceSatang, source, ruleId}]} | refusal` = the C-6 `priceFor`, exposed on the POS facade. P2.2 does not edit restaurant/shop/QR callers.

## 5. Rulings proposed (controller decides)
- **CD1 POS owns the rules now.** `PosPriceRule` lives in POS (no marketing module has price rules, §0). A marketing facade `activePriceRules` plus a "create from campaign" link (`campaignId`) is P3. Until then the mockup's "จากระบบการตลาด · แคมเปญ" label reads "โปรราคา · <rule name>".
- **CD2 Branch sits under channel.** Order rule > (code, unit) > (code, all) > (all, unit) > base. A channel price is what the platform customer pays wherever it was set; a branch price is the base for that branch.
- **CD3 Price is decided by the caller, createSale only snapshots** (as today). The register uses the resolver. P2.4/P2.7/P2.8 call `resolvePrices` (R10). A server-side re-price inside createSale would change the meaning for 10 existing callers.
- **CD4 Rule price stacks with every discount** (line/bill, coupon, tier, voucher, points). It is the price, not a discount, so it sits outside the cashier cap. Alternative: a rule flag `exclusive` that blocks member/coupon benefits (needs wallet work, P3).
- **CD5 Channel/rule prices replace the base only; option deltas are added unchanged.** This keeps `unitPrice = price + Σ delta` and the weighed-label match (`register.ts:1817`).
- **CD6 Absolute per-product channel prices + an optional bulk "+X%, round to baht" writer** (mockup arithmetic, §0). There is no live markup column on SalesChannel.
- **CD7 Weighed products are out** of channel/rule pricing in P2.2 (price per kg + label prices; P1.2 R12/R14 invariants).
- **CD8 No overnight windows** (from < to, Bangkok fixed +7). The owner splits 22:00–02:00 into two rules.
- **CD9 Receipts unchanged** (no "ราคาปกติ" line); the bills drawer shows the source (R11). This avoids reopening P1.10/P1.11 receipt parity.
- **CD10 No test clock in server paths**; the oracle uses real `now` windows plus the pure boundary tests.
