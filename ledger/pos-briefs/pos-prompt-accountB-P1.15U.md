## Controller rulings (binding)
1. **Staff session on the device (client)**: the staff token lives in `sessionStorage` per `deviceId` (`pos-staff:<deviceId>` = `{userId, name, role, staffToken, expiresAt}`); never in a cookie, never in localStorage. The register page is **locked** (13B overlay, blocks the whole screen incl. keyboard shortcuts) when: no token / token expired / idle ≥ 2 min (`pos.register.autoLockMinutes` setting, default 2, 0 = off — read via the existing settings parser; add the key under `pos.register` if absent) / the user presses the lock button in the status bar / any action returns `STAFF_TOKEN_INVALID`. Unlock = `verifyStaffPinAction({deviceId, pin, userId})` with the **selected staff's userId always sent** (never without id); on `PIN_LOCKED` show "ล็อกชั่วคราว 15 นาที · ให้ผู้จัดการปลดล็อก" and a "ผู้จัดการปลดล็อก" path = manager picks self in the list, enters own PIN (verifies as manager), then `unlockStaffPinAction({userId})`. "ลืม PIN" = same manager path with text "ให้ผู้จัดการตั้ง PIN ใหม่ที่ ตั้งค่า → พนักงาน". No device registered (`deviceId` absent) ⇒ the lock screen says "ลงทะเบียนเครื่องนี้ก่อน" with a link to settings (17B) — no PIN flow.
2. **Every register call carries the token**: submit, hold, recall, open shift, and (new, server change allowed) `voidSaleAction`/`refundSaleAction` accept `staffToken` and resolve the requester as the token user exactly like submit (`staffFromToken` then `STAFF_TOKEN_INVALID`, never fallback) — add to `bills.ts`/`refund.ts` + actions with a ≤40-line hunk each, and extend `qc-pos-p1.15` with one check TK-U1 (void with a bad token ⇒ `STAFF_TOKEN_INVALID`; with a valid STAFF token the audit actor is the token user) in a separate `test(...)` commit (ORACLE-EDIT approved). Seller shown in the status bar = token user ("น้ำฝน · แคชเชียร์").
3. **Staff switch** (13B right column): `listStaffForDeviceAction()` → cards; "สลับพนักงาน" opens the PIN pad for the chosen user; a successful switch replaces the token, keeps the cart on screen but tags it as held? **No**: ruling = the current cart is auto-held under the previous user (`holdRegisterCartAction` label "สลับพนักงาน") before switching; if the cart is empty nothing is held. Shift ownership is unchanged by a switch (shift stays with its opener; "ขายในกะนี้ได้" when `pos.shift.operate`). Staff with `shift` = chip "ใช้งานอยู่" + "เจ้าของกะ #n · hh:mm–hh:mm" (hours from HR schedule only if an existing HR read exists in the page — otherwise omit hours, do not add an HR dependency).
4. **Discount cap UI**: page passes `await registerDiscountCaps(ctx)` into `registerSellerLimits(actor, unitId, caps)`; `BillDiscountDialog` shows the cap ("เพดานของคุณ 10%") and, when exceeded, the **discount-over sheet**: (a) "ใส่ PIN ผู้จัดการ" (manager picker from `listStaffForDeviceAction` filtered to MANAGER/OWNER + 4–6-digit pad; sends `managerPin` + `managerUserId` with the submit), or (b) "ส่งขออนุมัติ" ⇒ submit returns `APPROVAL_REQUIRED {requestId, heldCartId}` ⇒ the cart is now held server-side: clear the screen, open the 21B wait dialog. `PENDING_APPROVAL` on a retry ⇒ same dialog.
