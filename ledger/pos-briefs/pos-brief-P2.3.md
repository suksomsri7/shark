## 0. What exists (verified at b694aea0)

No unit, no waste, no yield, no option link. Writer `catalog.setRecipe` (`pos/catalog.ts:1813–1849`, `pos.product.manage` + `requireRowWrite`, exact keys, qty int 1..1 000 000, ≤ 50 lines `:1695`, no dup item, InvItem must be in an inventory sold through this POS (`loadSellableItem` `:1179`), not SERVICE, not archived; replace-all; audit `pos.product.recipe`) refuses every non-BUNDLE row: "ตั้งส่วนประกอบได้เฉพาะชุดสินค้า (สูตรเมนูมาในรอบถัดไป)" (`:1826`, `:1688` "BOM ของเมนู = P2.3"). Read side: `listForUnit` returns `recipe[]` per product (`:918–921, :993`; view type `:110`).
- 🔴 **Backfilled MENU recipes are inert today.** P1.1a/P1.1b create one `RecipeLine(menu, MenuItem.invItemId, qty 1)` per menu linked to an InvItem (backfill `catalog.ts:2154`; legacy door `catalog-legacy.ts:124`; pinned `qc-pos-p1.1.mts` S1.10/S1.12/S2.18 — QC fixture "เมนูโค้ก → โค้ก"). The register ignores them: `itemId` only for `PRODUCT && invItemId && trackStock`, `components` only for `BUNDLE` (`pos/register.ts:1372–1374`). Making MENU recipes "live" would silently start cutting stock (and, via the bundle visibility rule, could hide menus) for every existing linked menu ⇒ CD2 / Q1.
- **The per-line consumption machinery is already recipe-shaped (P1.2 bundles).** `PosSaleLine.components Json? [{invItemId, qty}]` per 1 unit, "ตัดสต็อก qty × line.qty คีย์ pos-consume-<sale>-<line>-<invItem>" (`pos.prisma:155`). createSale validates `components` (array ≤ 50 `service.ts:177`, int qty ≥ 1, unique item `:197–203`), requires every component in the unit's inventory else `VALIDATION` (`:548–553`), and `components` is **not** in `samePayload` (`:230–246`). One function decides consumption: `lineConsumption` (`:826–841`: itemId part key `pos-consume-<sale>-<line>`, component parts `…-<invItemId>`, qty `c.qty × line.qty`). It is reused by BLOCK-in-tx cutting (`:555–580, :731–745`), post-commit cutting `consumeSaleInventory` (`:843–871`), refund restock (`refund-consumer.ts:129–178`, pro-rata = `c.qty × refundQty`, cost/location/lot of the original OUT per O12), margin cost (`reports.ts:718–733, :744`), and the register "pending stock cuts" counter (`register.ts:2403–2414`). Void returns every POS OUT movement of the sale (`service.ts:965–1005`). The register already builds `components` from `RecipeLine` for bundles (`register.ts:1301–1312`) and hides a bundle whose components are not all in the unit's inventory (`regVisibleWhere` `:668–671`, quote re-check `bundleBlocked` `:1312`).

- Stock count applies variance as a delta on the locked current balance, so sales during a count (any OUT) are already included (`pos/stock-count.ts:649–652`).

## 2. Rules (server, oracle-tested)
- **R1 Which rows have a live recipe.** BUNDLE: as today (always live). MENU: live iff `PosProduct.bomEnabled = true` (new, default false). PRODUCT, SERVICE, `soldByWeight` rows ⇒ `setRecipe` `VALIDATION` (a PRODUCT already cuts its own InvItem 1:1; P1.2 B1 pin "บนสินค้า PRODUCT → VALIDATION" stays). A MENU variant (parentId) uses its own rows if it has any, else the parent's; choice adjustments are read from the same owner row.
- **R2 Writers (catalog.ts only, F15.1).** `setRecipe(ctx, productId, lines)` now accepts MENU; first non-empty save sets `bomEnabled=true`, `[]` sets it false (audit `pos.product.recipe` with `bomEnabled` before/after). New `setRecipeChoiceLines(ctx, productId, [{choiceId, invItemId, qtyDelta}])` replace-all: `qtyDelta` signed int, ≠ 0, |v| ≤ 1 000 000; ≤ 100 rows; no dup (choice, item); the choice must belong to a group linked to the owner row (`PosProductOptionGroup`) else `NOT_FOUND`; item rules as `setRecipe`; MENU/BUNDLE only. New `setBomEnabled(ctx, productId, on)` (MENU only; turning on with zero lines ⇒ `VALIDATION` "ยังไม่มีสูตร"). All: `pos.product.manage` + `requireRowWrite`, other tenant/system ⇒ `NOT_FOUND`, exact keys, validate-all-before-write, unchanged ⇒ no write/no audit.
- **R3 Expansion (pure `expandRecipe` in `recipe-shared.ts`).** Per unit: start from the base lines; add the `qtyDelta` rows of every picked choice; merge per invItemId (Σ); drop items whose net ≤ 0 (clamp, never negative); order by invItemId asc for determinism; > 50 items ⇒ register refusal `INVALID_LINE` "สูตรรวมตัวเลือกมีวัตถุดิบเกิน 50 รายการ". Result = the line's `components` (integers per unit). Consumption = `c.qty × line.qty` (existing `lineConsumption`), so totals and refunds are exact integers: no rounding anywhere, no remainder rule needed. Mixed carts: each line keeps its own keys; the same ingredient in two lines = two movements (Σ correct; per-line keys are what refund/margin/pending read).
- **R4 Register.** `regPrice` meta: `components = expandRecipe(...)` for BUNDLE and for MENU with `bomEnabled`; else `[]` (non-recipe lines byte-identical). Visibility/`bundleBlocked` (`register.ts:668–671, :1312`) extends to live MENU recipes: an ingredient (base or picked choice) outside the unit's inventory ⇒ hidden / `PRODUCT_NOT_FOUND` (Q4). Held carts re-quote on recall (existing H3) ⇒ the recipe in force at recall time is used. Replay of a committed key returns the original sale (components not in samePayload).
- **R5 One batch per sale (C-1).** New facade `inventory.consumeBatch(ctx, {sourceModule, refType, refId, parts:[{itemId, qty, idempotencyKey}]}) → {movementIds[], skipped:[{itemId, key, reason: "NOT_FOUND"|"SERVICE"}]}` in `inventory/service.ts` + `index.ts` (marked `// POS P2.3 ▸ … ◂`, owner note in `POS-OWNER-PENDING.md`): ONE tx, `lockItemsInTx` on the sorted distinct ids, skip parts whose item is missing in this system or SERVICE (today's per-part catch, made explicit), `consumeInTx` per part with its own key (same rows as today), `withStockRetry` once on the whole batch; after commit GL per movement + AccountProduct sync per distinct item. `consumeSaleInventory` calls it once for **every** sale (non-recipe sales produce identical movement rows; only the tx grouping changes). All-or-nothing per sale: a lock timeout leaves the whole sale "pending" (visible in `registerStatus`), never half-cut. BLOCK path unchanged (already one tx inside the sale).
- **R6 Negative stock.** `ALLOW_NEGATIVE`: cut anyway, `needsReview` on the ingredient movement. `BLOCK`: existing in-tx check over Σ parts per item ⇒ `STOCK_INSUFFICIENT` at **submit** with the ingredient name, nothing written; quote does not refuse (as today), it only shows `soldOutReason NO_STOCK` (R9).
- **R7 Void / refund.** Void returns every POS OUT movement of the sale (existing). Refund `restock=true` returns `c.qty × refundQty` per component at the original OUT cost/location/lot (existing). ⅓ then ⅔ ⇒ Σ returned = Σ cut. Replays (void twice, refund event replayed) ⇒ no extra movements (keys). See Q5 for the void cost gap.
- **R8 Cost read model (no new money column).** `recipeCost(ctx, productIds, {unitId, choiceIds?})` in `pos/recipe.ts`: Σ qty × `InvItem.costSatang` (current moving average) per line + total; `costComplete=false` when any ingredient has cost 0 or is archived/missing ("ยังไม่ใส่ต้นทุน"); `marginBp = floor((base − cost) × 10000 / base)` on the VAT-inclusive base price, the P1.17 formula (null when base null/0 or cost incomplete ⇒ "กำไรคำนวณไม่ได้"). Visible with `pos.product.manage` or `pos.report.view`; others get ingredients/qty without cost. **Sold cost = the OUT movements** (avg at cut time) already read by the margin report (stored kind) and usable by the bills drawer — CD4.
- **R9 Portions left.** Live recipe rows get `stockLeft = min over components ⌊onHand / qty⌋` (unit's inventory, base recipe only) ⇒ "เหลือ N" / `NO_STOCK` display on tiles and 06; `listForUnit.stock[unit]` filled the same way. No 86 automation (P2.6).
- **R10 Refusals & messages.** Existing codes only (`VALIDATION`, `NOT_FOUND`, `PERMISSION_DENIED`, `PRODUCT_NOT_FOUND`, `INVALID_LINE`, `STOCK_INSUFFICIENT`); th + en keys under `pos.recipe.*`. No new outbox event.

## 5. Rulings proposed (controller decides)
- **CD1 Reuse `RecipeLine` + `PosSaleLine.components`; no new sale-line or createSale field.** The P1.2 bundle path already gives per-line snapshot, keys, BLOCK, refund pro-rata, margin and pending counters; P2.3 only feeds it for MENU.

- **CD3 Integer quantities per unit in the item's own stock unit; options are signed deltas** (no multiplier, no waste %, no yield) ⇒ every cut/return is exact.
- **CD4 No `costSatang` snapshot column.** The OUT movement already stores the avg cost at cut time and drives GL + P1.17; the 06 drawer shows live recipe cost.
- **CD5 One `consumeBatch` per sale for all sales**, per-part keys kept (refund/margin/pending depend on them); Σ per item only for the BLOCK check.
- **CD6 86/availability from ingredients = display only in P2.3**; the event and channel push stay P2.6.
