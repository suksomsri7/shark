## Controller rulings (binding)
R1 **Scope of `PosProduct`**: `tenantId` + `systemId` (the POS `AppSystem`) + **nullable `unitId`** (null = sold at every branch of that POS system) + **nullable `invItemId`**, `@@unique([systemId, invItemId])` semantics for non-null (Postgres treats NULLs as distinct — verify the generated SQL does what is intended). `kind` on `PosProduct`: `PRODUCT | SERVICE | MENU | BUNDLE`. **Do not add MENU to `InvItemKind`; do not create InvItems for menu items.**
R2 **Which POS system does a row belong to?** Use the SAME resolution the selling path uses today, so that tomorrow's sale lines land in the system that sells them: InvItem → the POS system(s) whose register lists it today (trace `posCatalog`/`posServices` in `src/lib/modules/pos/register.ts` and the system-link tables); MenuItem → the POS system the restaurant checkout passes to `createSale` for that unit (trace `restaurant/order.ts`); ShopProduct → same for shop checkout (`shop/service.ts`). A source row whose unit/system resolves to NO POS system is **skipped and counted** in the report (`skippedNoPosSystem`), never guessed. Write the resolution as ONE exported function in `catalog.ts` and document it; the oracle writer's notes state what the oracle expects — if they differ from the traced code, code wins → ORACLE-EDIT request.
R3 **Variants**: no `PosVariant` table. `PosProduct.parentId` (nullable self-relation) is added now and left unused; P1.2 owns variants.
R4 **Price precedence in backfill** (never cost): `AccountProduct.posPrice` (>0) → `AccountProduct.salePrice` (>0) → `InvItem.priceSatang` (kind SERVICE, >0) → `MenuItem.basePrice` / `ShopProduct.priceSatang` for their own rows → else **null** ("price not set"). A genuine zero price that the shop set on purpose must stay 0, not become null — read how today's code distinguishes "0 on purpose" from "unset" per source (the QC seed has a zero-price item `PQC-CF-FREE` and a restaurant zero item); if today's data cannot distinguish them for a source, say so and follow what the oracle asserts, flagging it.
R5 **Column names**: `posProductId` (nullable) on `MenuItem`, `ShopProduct`, `ShopOrderLine`; `productId` (nullable) on `PosSaleLine`, `RestaurantOrderItem`. (`ShopOrderLine.productId` already exists → ShopProduct; do not touch it.) Loose ids or real FKs: follow the convention of the neighbouring columns in each model (many links in this schema are loose `String?` on purpose — cross-schema-file relations); new→new relations inside `pos.prisma` are real relations.
R6 **Other new tables in this migration** (all empty after migrate, filled by backfill where stated): `PosCategory` (backfilled from `MenuCategory` and from `InvCategory`/`AccountProduct.posCategory` only if the register really shows categories from them today — else only MenuCategory), `PosProductOptionGroup` (link PosProduct ↔ existing `MenuOptionGroup`; backfilled from `MenuItemOptionGroup`), `RecipeLine` (created empty; P2.3 fills it). Menu fields copied onto PosProduct as nullable columns: station link, `stockQty`/`dailyStockQty`/`isOutOfStock`-equivalents, availability window — COPY ONLY; the live source of truth stays `MenuItem` until P1.1b/P2.4 (say so in a schema comment).
R7 **Migration mechanics** (first prove the state: `prisma migrate status` on QC4 — read-only): generate SQL with `prisma migrate diff` (from the migrations/previous datamodel to the new datamodel, `--script`) or `migrate dev --create-only` ONLY if it does not ask for a reset; write ONE migration folder `<timestamp>_pos_v2_a` where `<timestamp>` sorts AFTER every migration on `origin/main`, `origin/session/crm` and every `origin/wip/crm-*` branch (list them with `git ls-tree`), plus a margin — the controller may rename it at merge time. Additive only: no DROP, no ALTER TYPE that rewrites, no NOT NULL without default, no unique index on a populated table that can contain duplicates, plain `CREATE INDEX` (no CONCURRENTLY). Read every line of the SQL and paste it into the notes. Apply to QC4 with `migrate deploy` (via `scripts/qc-prisma.sh`); if QC4's history contains migrations that are not in this tree, STOP and report the exact `migrate status` output (do not resolve/reset on your own).
R8 **Do NOT touch**: `src/lib/modules/pos/service.ts` (`createSale`/`voidSale`), `register.ts`, `register-ui.tsx`, anything in `restaurant/`, `shop/`, `inventory/`, `account/`, `booking/` modules, the AI tools, any page. ## Controller addendum 1 Oct ~12:20 UTC (after the catalogue oracle was delivered — binding, overrides R1/R4 where they differ)
