## 1. Scope
In: public receipt page by unguessable token · QR URL in the printed receipt payload · send receipt via LINE (chat module) or email · customer reports a problem with the bill → event → Kanban card + chat acknowledgement · customer requests a full tax invoice (stored as a request; P1.13 issues the document) · customer rates the shop (member review system, only when the sale has a member) · "ดูแต้มของฉัน" balance.
Out: issuing the full tax invoice (P1.13) · DBD lookup (P1.13) · e-Tax provider (P3) · customer-display (11A, P2) · marketing consent/journeys · any new chat adapter.

## 2. Rules (server, oracle-tested)
- **R1 token**: `PosSale.publicToken String? @unique` — 12 chars Crockford base32 from `crypto.randomBytes` (no `Math.random`), set inside the `createSale` transaction for new bills (both docTypes); old bills get one lazily through `ensureReceiptToken(tenantId, saleId)` (idempotent, returns the existing token). The token never changes. Only `SALE` docs are shareable; a `REFUND` doc's token resolves to its original sale's page (shows the refund in the status block).
- **R2 public read** `publicReceipt(token)` → `{ ok:true, receipt }` | `{ ok:false, code:"TOKEN_NOT_FOUND" }`. `receipt` = `{ shop:{ name, branchLabel, logoUrl }, receiptNo, abbNo (when kind TAX_INVOICE_ABB), paidAt, status:"PAID"|"VOIDED"|"REFUNDED_PARTIAL"|"REFUNDED", refundedSatang, lines:[{name, qty, unit?, options?, lineTotalSatang}], discountSatang (bill discount + coupons lumped — label "ส่วนลด + คูปอง"), vat:{ rateBp, satang, included:true } | null, grandTotalSatang, payments:[{method, satang}], points: { earned, balance } | null (only when memberId; balance from the point module read), actions:{ taxInvoice:"AVAILABLE"|"REQUESTED"|"ISSUED"|"NOT_AVAILABLE", review:boolean, report:true } }`. **No PII**: no member name/phone/email, no cashier name, no device id. Built on `receiptPayload` internals (reuse the same line/VAT shaping — do not re-derive money).
- **R3 QR**: `receiptPayload(...).footer.qrEReceiptUrl` = `${origin}/r/<token>` when `parseReceiptSettings().qrEReceipt` is true, else `null`; `origin` from `src/lib/core/origin.ts` (never `env.APP_URL` directly). The renderer already prints the QR slot.
- **R4 report issue** `reportReceiptIssue(token, { message, contact? })` (public, no actor): message 1–500 chars, contact ≤120 optional; stores `PosReceiptIssue { id, tenantId, unitId, saleId, message, contact?, status OPEN|RESOLVED, kanbanCardId?, createdAt }`, enqueues outbox `pos.receipt.issue_reported { tenantId, unitId, saleId, issueId, receiptNo, message }`. Limit **3 per token per 24 h** → `RATE_LIMITED` (count rows, no extra table). Consumer (registered in `outbox-consumers.ts`, `withAutomation`): Kanban card through the existing single gate `kanban/links.createCardFromExternal` (same gate the member review system uses) — if the tenant has no board for POS issues the consumer records `{posted:false, reason:"no-board"}` and does not throw; plus chat acknowledgement via `sendLineToParty` when the sale has a member with a LINE identity (ok:false ignored, never throws). Consumer is idempotent on `issueId` (second delivery creates no second card: `kanbanCardId` set ⇒ skip).
- **R5 tax invoice request** `requestFullTaxInvoice(token, { name, taxId, branchCode?, address, email? })` → `PosTaxInvoiceRequest { id, tenantId, unitId, saleId, name, taxId, branchCode, address, email?, status REQUESTED|ISSUED|REJECTED, accountDocId?, createdAt }` + outbox `pos.receipt.taxInvoiceRequested` (consumer registered as a no-op — P1.13 fills it). Eligible only when: sale `PAID` (not VOIDED; partial refund allowed — P1.13 decides the amount), `paidAt` within **7 days**, receipt kind `TAX_INVOICE_ABB` (VAT book) — else `NOT_ELIGIBLE`; one open request per sale → `ALREADY_REQUESTED`; `taxId` exactly 13 digits (format only; DBD = P1.13) else `VALIDATION`; `branchCode` 5 digits default `00000`.
- **R6 review** `submitReceiptReview(token, { rating 1–5, body? ≤500 })` — only when the sale has `memberId`; goes through the member module's review facade (the oracle writer names the exact function; if the member facade has no suitable entry, write a `CONTROLLER-DECISION` — do not write to `MemberReview` from the POS module directly). Second submit for the same sale → `ALREADY_REVIEWED`.
- **R7 send receipt** `sendReceipt(ctx, actor, { saleId, via:"LINE"|"EMAIL", email? })` permission `pos.sale.read`: LINE → `sendLineToParty` to the member's party with text `ใบเสร็จ <receiptNo> · ยอด ฿<net> — ดูใบเสร็จ: <url>` (no member/LINE identity → `NO_LINE_IDENTITY`); EMAIL → `sendEmailRich` (subject `ใบเสร็จ <receiptNo> · <shop>`, HTML = `renderReceiptHtml(payload,{paper:"80",locale})` + link; `email` input or the member's email → else `NO_EMAIL`; format check → `VALIDATION`); VOIDED → `SALE_VOIDED`; limit **5 per sale per 24 h** → `RATE_LIMITED`; `writeAudit("pos.receipt.sent", { via, to: masked })`. Refusals as data with Thai messages; never throws.
- **R8 readers**: the public page must reflect `voidSale`/`refundSale` outcomes without extra state (status derived from `status`, `docType`, `refundedSatang`, REFUND docs with `refSaleId`).
- **R9 security**: token lookups use the unique index only (no enumeration endpoints); public actions accept **only** the token (no saleId/tenantId from the client); no session is read on `/r/[token]`; page sends `X-Robots-Tag: noindex`/`<meta name="robots" content="noindex">`; all public writes rate-limited as above; message/body stored trimmed, rendered escaped.

## 5. Rulings
CD1 Public page is a Server Component reading only through `publicReceipt`; public writes are Server Actions that take the token — never ids.
CD2 Kanban card creation goes through `kanban/links.createCardFromExternal` only (single gate); no board = polite skip recorded in the event result.
CD3 Review rows belong to the member module; POS calls its facade. If no facade exists, the oracle writer writes CONTROLLER-DECISION and the builder adds the smallest additive export in `member/index.ts` (a composed call of existing internals) after the controller rules.
CD4 Rate limits count rows (`PosReceiptIssue` by saleId/24 h; `AuditLog pos.receipt.sent` by saleId/24 h) — no new counter tables.
CD5 Migration additive only: column `PosSale.publicToken` + unique index, tables `PosReceiptIssue`, `PosTaxInvoiceRequest` (+ their indexes). Register in `core/scope.ts` and `scripts/pos-qc-env.mts`.
CD6 "ส่วนลด + คูปอง" lumps bill discount, coupons, tier discount, vouchers, points on the public page (same as the printed receipt today — P1.8 reviewer follow-up stays open).
