# HF-HR-0 — HR personal-data / payroll exposure and leave-decision integrity (security hotfix · builder · worktree /root/projects/shark-hf3 · branch hotfix/hr-privacy off origin/main)

Lane rules `/root/projects/shark-pos/ledger/pos-briefs/pos-brief-LANE-RULES.md` are binding (QC4 only, iso.sh, no build/server, no prisma/schema change, typecheck once with the 5632 MB heap command).

## In scope (fix)
- **D3** payslip page `src/app/app/sys/[id]/payroll/[runId]/slip/[employeeId]/page.tsx`: any tenant member with the ids opens any colleague's payslip. Rule: allowed only for a payroll viewer (`canViewPayroll` / the house payroll-read permission) OR the employee themself (how is an HrEmployee linked to a user? trace it; if there is no reliable link, payroll viewers only and note it). Otherwise `notFound()`.
- **D4** employee profile page `src/app/app/sys/[id]/hr/employees/[employeeId]/page.tsx`: no permission check, and the FULL database row (national id, social-security no., bank account, kiosk PIN, document URLs) is passed to a client component even when hidden on screen. Rule: page guard with the HR read permission (404-not-403); build a whitelisted DTO on the server — sensitive fields are included ONLY when the viewer may see them (`canSeeSensitive`), the PIN is never sent to the client at all (show "set / not set"; changing it stays a server action). Apply the same DTO rule to EVERY HR page/list/action that ships employee rows to a client component or returns them from a server action (employees list, attendance, leave, payroll screens, exports) — audit all of them and list each in the notes.
- **D8** `src/lib/modules/hr/service.ts` (~:330): setting a duplicate PIN answers with the NAME of the employee who holds it ⇒ PIN enumeration. Rule: generic Thai message ("PIN นี้ใช้ไม่ได้ กรุณาเลือก PIN อื่น"), no name.
- **D9** leave page + AI tool `pending_leaves` (`src/lib/ai/tools.ts` ~:151-171 — smallest marked hunk `// HF-HR-0 ▸ … ◂`; do NOT touch `src/lib/ai/proposals.ts`): leave reasons (health data) shown without `hr.leave.read`. Rule: require the permission; without it the reason is omitted (or the page 404s, following how sibling HR pages behave).
- **D10** leave decision (`service.ts` ~:435-452): no status check (an approved leave can be flipped), bypasses a pending approval request, allows approving one's own leave. Rule: only PENDING → APPROVED/REJECTED (single conditional `updateMany`, race-safe); the decider must not be the leave's own employee; when an approval-core request is pending for that leave, the direct path refuses and points to the approval flow. Keep every legitimate flow working.
- Any other HR surface where a permission is checked without the needed scope or a client-supplied id is trusted — fix if it is the same class and a small hunk; otherwise report.
