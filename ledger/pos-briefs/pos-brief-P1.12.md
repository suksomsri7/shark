## 2. Rules (server, oracle-tested)
- **R1 Member system of the bill**: = `systemForUnit(unitId,"MEMBER")`. None ⇒ every member action refuses `MEMBER_SYSTEM_MISSING` (U hides the chip). A customer is attachable only if `tenantId` **and** `memberSystemId` match and `status = ACTIVE` (fix `register.ts:1207–1210`); other tenant / other member system / MERGED / erased ⇒ `MEMBER_NOT_FOUND` (404-not-403 — never reveal existence); SUSPENDED ⇒ `MEMBER_SUSPENDED`. Register always passes `memberSystemId` explicitly to `createSale`, so the `askedNothing` swallow (`service.ts:335–347`) never triggers from the new register.
- **R2 Lookup** `registerMemberLookup(ctx, actor, { q })` → `{ ok:true, items ≤ 8 }` sorted `-lastActivityAt`. `q` trimmed: starts with `SHARK-MC:` ⇒ `resolveCardToken` + R1 system check; digits only (≥ 3, dashes/spaces stripped) ⇒ phone; `^M?\d+$`-style member code ⇒ exact `memberCode`; else name (≥ 2 chars). Implemented via `listMembers` + `briefFor` with the delegated actor (CD2) — POS writes no Customer query of its own beyond R1's existence check. Item DTO `{ id, memberCode, name, phoneMasked, tier:{key,name,color}|null, points (unit's POINT system), lastPurchaseAt|null, purchaseCount, suspended }`. `q` < min length ⇒ `{ items: [] }` (not a refusal). Budget p95 ≤ 300 ms on 10 k members (Q4).
- **R3 Attach/detach**: the cart keeps `memberId` (exists: quote input, held carts `register.ts:1409`). Detach = omit. Held carts also keep `couponCode` (add to `REG_QUOTE_KEYS`, `register.ts:980`; held-cart parser). Benefit *choices* (points/voucher) are never held — chosen on the pay screen only (CD4).
- **R4 Quick register** `registerQuickMember(ctx, actor, { phone, name, birthDate?, marketingConsent, heardFrom, idempotencyKey })` (exact keys). `phone` normalised to digits (`party.normalizePartyPhone`), 9–10 digits else `PHONE_INVALID`; `name` 1–80 required; `birthDate` `YYYY-MM-DD` optional; `heardFrom ∈ WALK_IN|LINE|REFERRAL|ADS`. Calls `createMember` with `source:"POS"`, `sourceDetail:{ heardFrom, unitId }`, `homeUnitId: unitId`, `consents: [LINE, EMAIL, SMS].map(ch ⇒ {channel: ch, granted: marketingConsent, source:"STAFF"})`, `idempotencyKey`. Existing phone ⇒ `{ ok:true, created:false, member }` (attach the existing one; U says "มีสมาชิกเบอร์นี้แล้ว — ผูกกับบิลให้แล้ว"). Attribution FIRST/LAST rows come from `createMember` (staffUserId = actor, unitId). Audit `pos.member.registered { customerId, created, unitId }` (masked phone only). Replay with same key ⇒ same customer, one audit.
- **R5 Benefits** `registerMemberBenefits(ctx, actor, { memberId, cart })` → `{ ok:true, member: <R2 item>, tier:{ name, discountPct, discountFixedSatang, discountMaxSatang }|null, points:{ balance, burnRateSatang, burnMinPoints, burnMaxPct, balanceValueSatang, expiringSoon[] }|null (null = no POINT system), vouchers:[{ id, name, code, valueLabel, expiresAt, applicable, discountSatang, reason|null }], stamps:[{ cardId, name, stamps, slots }], giftCards:[{ numberMasked, balanceSatang, expiresAt }] (read-only, CD3), rewardsPending:[{ redemptionId, rewardName, expiresAt }] }`. Wraps `getWallet(…, { cart })` + `getPointSettings`; read-only (oracle: row counts unchanged).
- **R6 Quote with benefits**: `RegisterQuoteInput` gains `couponCode?: string` (lifts Q12) and `memberChoices?: { voucherId?: string; points?: int ≥ 0 }` (exact keys; `giftCard` key ⇒ `VALIDATION`). After `priceCart`, when `memberId` is set: coupon discount exactly as `createSale` (validate on `subtotal − bill`, `service.ts:410–427`, coupon system = `resolvePosLinks().couponSystemId`); then `member.quoteApply` with the wallet cart built by **one shared pure helper** extracted from `service.ts:556–570` (`saleWalletCart(lines, unitId, couponCode)`, used by both `createSale` and the quote — no behaviour change). Totals gain `tierDiscountSatang`, `memberDiscountSatang` (= quote total − coupon line, as `service.ts:583–584`), `memberLines[{kind, ref, label, discountSatang, note}]`, `pointsToEarn`, `stampsToAdd`, `memberConflicts[{kind, code, message}]` (codes per R14). Quote never refuses on a conflict; it reports it. `grandTotal = subtotal − bill − coupon + serviceCharge − memberDiscount`; `< 0` ⇒ `BENEFITS_EXCEED_TOTAL`. Delete the `MEMBER_RIGHTS_UNSUPPORTED` gate (keep the code/key for old clients). Coupon without member works too (walk-in coupon).
- **R7 Submit**: `submitRegisterSale` forwards `memberId`, `memberSystemId`, `memberChoices {voucherIds: voucherId ? [voucherId] : [], points}`, `couponSystemId + couponCode`, `memberSnapshot` (R9) into `createSale`. Before writing: re-run the R6 quote; any conflict on a **requested** benefit ⇒ its refusal code, nothing written; requested points ≠ points the quote would burn (cap trimming, `wallet.ts:545–558`) ⇒ `POINTS_CAPPED { allowedPoints }` (never burn a different number than the cashier saw); `expectedGrandTotalSatang` mismatch ⇒ `PRICE_CHANGED` (existing). Race inside the tx (voucher used by a parallel bill, balance moved): `MemberInputError`/`GiftCardStateError` ⇒ `MEMBER_RIGHTS_CHANGED` (retryable; tx rolled back, no sale, no burn). Result gains `member: { pointsBurned, pointsExpected (quote.pointsToEarn), pointsBalanceAfterBurn }` for 02b (real `pointEarned` arrives after drain).
- **R8 What runs where** (unchanged machinery, now reachable): **in the sale tx** = everything that changes the amount owed (coupon REDEEMED, voucher USED with `usedRef.saleId`, points BURN key `pos-burn-<saleId>`, tier discount). **Via outbox `pos.sale.paid`** = rewards that may lag (spend, earn excluding benefit-paid share, stamps, first-purchase attribution, tier upgrade). Reason: `service.ts:20–27` — a broken loyalty rule must never stop a sale, but a discount the customer was promised must be atomic with the payment.
- **R9 Snapshot**: `PosSale.memberSnapshot Json?` = `{ name, memberCode, phoneMasked, tierKey|null, tierName|null }` from `briefFor` at submit (caller-supplied additive `createSale` input; not in `samePayload`). `PosSale.memberBenefits Json?` = `applied.lines` (`[{kind, ref, label, discountSatang, note?}]`) + `{ pointsBurned }`, written by `createSale` itself whenever `applied` is non-null (all callers — additive column; legacy register benefits too). Both immutable after commit. PDPA: `member.erased` handler (POS, smallest hunk composed after the CRM handler, `outbox-consumers.ts:1256`) blanks `name`/`phoneMasked` to `null` on that customer's sales, keeps tier + money; idempotent.
- **R10 Points = discount** (CD1): value `points × burnRateSatang`, bounds `burnMinPoints`, balance, `burnMaxPct` — all from the wallet; GL: the sale document is posted net of points through the existing bill-discount allocation (`account-bridge.ts:107–120`); no points liability posting (point/voucher/stamp modules never import account). Mockup "10 แต้ม = ฿1" ⇔ `burnRateSatang = 10`.
- **R11 Vouchers & coupons**: ≤ 1 voucher per bill (`vouchersPerSale`); 2nd ⇒ `VOUCHER_LIMIT`; expired/used/other member's/min-spend/unit-restricted ⇒ `VOUCHER_INVALID` + wallet reason; voucher + coupon when the voucher's `stackWithCoupon ≠ true` ⇒ `VOUCHER_COUPON_CONFLICT`; coupon failure ⇒ `COUPON_INVALID` + `couponReasonText`. Stamp-card rewards are issued as vouchers by the stamp module ⇒ redeemed by this same path (no separate stamp-burn at POS).
- **R12 Stamps**: no new server code — earn post-commit (`stampFromSale` + `autoStampFromSale`, keyed), preview via `stampsToAdd`, void reverses (`stampVoidForSale`, `voidStampsForSale`), partial refund keeps stamps (P1.8 rule). Oracle proves the chain end-to-end through the new register.
- **R13 Rewards at the counter**: `registerFulfilReward(ctx, actor, { memberId, redemptionId })` → `reward.fulfilV2` (pending redemptions listed in R5); not a bill line, no money; idempotent (FULFILLED ⇒ ok). Audit `pos.member.reward_fulfilled`.
- **R14 Reversal completeness**: void ⇒ existing chain (coupon release in tx; voucher ACTIVE, burned points back, earn reversed, gift-card uses refunded, stamps voided, spend −). Full refund ⇒ same via `onPosSaleRefunded(full)` **plus coupon release** (new: one idempotent `coupon.release(refType "PosSale", refId saleId)` in `refund-consumer.ts` — today a fully refunded coupon stays REDEEMED while the voucher is returned; CD7). Partial refund ⇒ earn reduced pro-rata only; voucher stays USED, BURN stays (P1.8 CD). Every step replay-safe (drain twice ⇒ no double).
- **R15 Readers**: `receiptPayload` member block from `memberSnapshot` (fallback live Customer for older bills) and benefit lines from `memberBenefits` (tier / voucher / points shown separately; bill discount = `discountSatang − coupon − Σ memberBenefits`); points earned = `PosSale.pointEarned`; balance read **live** from the unit's POINT system (fix `receipt.ts:215–218`). Online receipt (P1.11) same block. `BillDetail` gains `member { name, tierName, benefits[], pointsEarned } | null`.
- **R16 Refusals & messages**: new codes `MEMBER_SYSTEM_MISSING MEMBER_SUSPENDED PHONE_INVALID VOUCHER_INVALID VOUCHER_LIMIT VOUCHER_COUPON_CONFLICT COUPON_INVALID POINTS_DISABLED POINTS_BELOW_MIN POINTS_INSUFFICIENT POINTS_CAPPED BENEFITS_EXCEED_TOTAL MEMBER_RIGHTS_CHANGED` (+ existing `MEMBER_NOT_FOUND`). `refusalMessageKey` (`register-shared.ts:605–677`) → `pos.register.errors.*`; UI strings `pos.member.*`; th + en in `src/messages/{th,en}/pos.json`. Conflict kind → code map: VOUCHER→`VOUCHER_INVALID|VOUCHER_LIMIT`, COUPON→`COUPON_INVALID|VOUCHER_COUPON_CONFLICT`, POINTS→`POINTS_*`.
- **R17 Permissions**: every action needs `pos.sale.create` at the unit (`core/permissions.ts:133`); lookup/benefits/register/fulfil call the member facade with the **delegated actor** of CD2. No new permission key.

## 5. Rulings (proposed — controller decides)
- **CD1 Points redeem = discount, not a pay method.** `createSale` already folds points into `discountSatang` (`service.ts:584`), the GL has no points-liability account and the point module never posts GL; a pay method would need a new channel + account + reversal rules for no customer-visible gain. DESIGN M2 says "ใช้แต้มเป็นส่วนลด". VAT is computed on the net (as with any discount).
- **CD2 Delegated member actor.** Cashiers usually hold `pos.sale.create` but no `member.*` key, and `getWallet/quoteApply/listMembers/createMember/fulfilV2` all check member permissions. POS builds, only inside `pos/register-member.ts` and only after `pos.sale.create` passes at that unit: `{ userId, role, unitAccess: [] , permissions: { "member.customer.read": true, "member.customer.create": true, "member.loyalty.fulfil": true } }` — members are shop-wide at the counter (a card works at every branch). Audited with the real userId. Alternative: new key `pos.member.register` (Q2).
- **CD3 Gift card tender is deferred to P2.9** ("ว่อชเชอร์เป็นวิธีชำระ · บัตรของขวัญ…", depends on P1.12; DESIGN M2 marks the tile P2). Doing it right needs `PosPayType.GIFT_CARD`, an account channel `GIFT_CARD → DEPOSIT_RECEIVED (2110)`, a `giftcard.use` flag to skip its own `postGiftCardUse` (Dr 2110 / Cr INCOME_SERVICE, `giftcard/service.ts:606–617`, `account/gl.ts:1753–1767`) and a wallet pass-through — four foreign modules. P1.12 shows balances read-only; the 02 tile renders "เร็ว ๆ นี้". The legacy path (gift card as discount) stays as is for `qc-member-m2.8` (Q1 explains its VAT gap).
- **CD4 Benefits are chosen at pay time only.** Tier is automatic; coupon may be entered at the cart (01 shows it) and is re-validated at pay; points/voucher are picked on 02. Held carts carry `memberId + couponCode`, never choices (re-price on recall, P1.5).
- **CD5 One voucher per bill** (existing `vouchersPerSale = 1`); coupon + voucher only when the voucher allows stacking; points after coupon (wallet order) — POS never reorders.
- **CD6 Tier and staff discounts stack**; the member base is Σ line nets *before* bill discount (as implemented in `wallet.ts:178–186` + `service.ts:556–570`); member benefits are outside the P1.15 cashier cap; `BENEFITS_EXCEED_TOTAL` guards negatives. Rewards are fulfilled at the counter, never as a 0-price bill line (`redeemV2` cuts its own stock, is not tx-aware).
- **CD7 Full refund releases the coupon** (parity with void and with the voucher). Partial refund keeps the P1.8 rules.
- **CD8 Phone is masked everywhere POS shows it** (member facade contract `profile.ts:50–51`); full phone only in the quick-register input the cashier typed (Q3).
- **CD9 Migration additive**: two nullable Json columns on `PosSale`. Money suites identical before/after.
