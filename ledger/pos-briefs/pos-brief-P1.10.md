## 2. Contract (controller rulings — additive only, F15.2)
R1 **`PosDevice`** (new table, spec sketch, loose ids like P1.9, no FKs): `{ id, tenantId, unitId, systemId, name, deviceCode, status ACTIVE|REVOKED, registeredByUserId, lastSeenAt?, posRegNo?, printerConfig Json?, revokedAt?, createdAt, updatedAt }`, `@@unique([unitId, deviceCode])`. **`deviceCode` = the P1.9 client id** (same regex) so shifts/bills already bound by that id keep their meaning — registering a device is "give this browser's id a name", not minting a new id. Registered in `core/scope.ts` (`sys()`), index on `[tenantId, unitId, status]` in the migration (new table ⇒ allowed).
R2 **Registry rules.** `registerDevice({name, deviceCode})`: name 1–60, code regex; same code again ⇒ returns the existing ACTIVE row (idempotent rename not implied); REVOKED code ⇒ `DEVICE_REVOKED`; ACTIVE count per unit ≥ `Tenant.limits.posDevices` (default **3**, helper `posDeviceLimit(tenant)`) ⇒ `DEVICE_LIMIT`. `updateDevice({id, name?, posRegNo?, printerConfig?})`, `revokeDevice({id})` (status REVOKED + `revokedAt`; its OPEN shift is left alone — manager closes it from the shifts page), `listDevices()` → rows with `online = lastSeenAt within 120 s`, the device's OPEN shift (shiftNo/openedAt) if any. `heartbeat({deviceCode})` sets `lastSeenAt` (throttled: no write if < 30 s old) — called by `registerStatus` when `ctx.deviceId` is given (one write per minute at most, inside the existing status read, no new polling).
   - **Unregistered devices keep selling** (today's behaviour; Q3). **Revoked devices are refused**: `submitRegisterSale`, `openShift`, `holdRegisterCart`, `recallHeldCart` refuse `DEVICE_REVOKED` when `ctx.deviceId` matches a REVOKED row of that unit. Permission `pos.device.manage` (new, OWNER/MANAGER) for register/update/revoke/list; heartbeat rides on `pos.sale.create`.
R3 **`printerConfig`** parsed/validated by a pure `parsePrinterConfig(json)` → `{ paper: "58" | "80" (default "80"), mode: "browser" | "escpos-usb" | "escpos-bt" (default "browser"), autoPrint: boolean (false), drawerKick: boolean (false), thaiText: "raster" | "tis620" (default "raster", Q1), copies: 1|2 (1) }`; unknown keys dropped, invalid values ⇒ `VALIDATION` with the field name.
R4 **Receipt settings** `settings.pos.receipt` on the POS `AppSystem` (pure parser `parseReceiptSettings` with defaults): `{ header: { name?: string ≤80, phone?: ≤30, address?: ≤200, logoUrl?: url|null }, footer: string ≤200 (default "ขอบคุณที่อุดหนุนค่ะ"), showPoints: true, showCashier: true, qrEReceipt: true }`; name/address/taxId fall back to the linked account book's business profile when empty; `posReceiptSettings(ctx)` / `updatePosReceiptSettings(ctx, actor, patch)` + thin actions, `pos.device.manage` to update. The receipt number format and the CN format are **not** settings (O2; P1.8 R4).
R5 **Receipt payload — the content contract** `receiptPayload(ctx, actor, { saleId, copy?: boolean })` (new `src/lib/modules/pos/receipt.ts`), permission `pos.sale.read`, bill must belong to the actor's unit scope (`posSaleWhere`). Returns exactly:
   ```
   { docType: "SALE"|"REFUND", kind: "TAX_INVOICE_ABB"|"RECEIPT", copy, paper: null,
     shop: { name, branchName, address, phone, taxId?, branchNo?, logoUrl? },
     device: { posRegNo? , name? },
     doc: { receiptNo, issuedAt (ISO), cashierName?, shiftNo?, refReceiptNo? },
     lines: [{ name, qty, unitPriceSatang, lineTotalSatang, discountSatang, options: string[], note?, weightGrams? }],
     totals: { subtotalSatang, lineDiscountSatang, billDiscountSatang, couponDiscountSatang, couponCode?, tierDiscountSatang, serviceChargeSatang, grandTotalSatang, vatBaseSatang, vatSatang, vatRateBp, tipSatang },
     payments: [{ type, amountSatang, tenderedSatang?, changeSatang?, reference? }],
     member?: { name, tierName?, pointEarned, pointBalance? },
     footer: { text, qrEReceiptUrl: null, fullTaxInvoiceHint: boolean },
     labels: { th: {...}, en: {...} }  // every caption used by renderers, both languages
   }
   ```
   `kind = "TAX_INVOICE_ABB"` iff the linked book is VAT-registered and `posAbbreviatedInvoice` is on (then `shop.taxId`/`branchNo` are mandatory in the payload and the title prints "ใบกำกับภาษีอย่างย่อ" — T2); otherwise `"RECEIPT"` with no VAT block. `vatBaseSatang + vatSatang = grandTotalSatang` (P1.6 helper). `copy: true` ⇒ renderers stamp "สำเนา" (T8) and the call writes `writeAudit({ action: "pos.receipt.reprint", targetType: "PosSale", targetId })`. `qrEReceiptUrl` is null until P1.11 (which owns `/r/[token]`). REFUND documents (P1.8) render with title "ใบลดหนี้ / ใบคืนเงิน" and `refReceiptNo` when the column exists; the oracle covers SALE only.
R6 **Renderers are pure and shared** (`src/lib/modules/pos/receipt-render.ts`, no prisma/server imports — a client bundle will import them in P1.10U):
   - `renderReceiptHtml(payload, { paper: "58"|"80", locale: "th"|"en" })` → HTML string with inline CSS (`@page` width 58/80 mm, monospace-free, tokens not required — paper is black on white), every section of mockup 11B in order: header (logo, shop, branch, address, phone, tax id, branch no, POS no) · title · doc no / date / cashier · lines (options indented, line discounts as "−") · totals (items count, discounts, coupon, grand total, VAT base, VAT) · payments (tendered/change) · member (points earned/balance) · footer (text, QR placeholder, "ขอใบกำกับเต็มรูปได้ภายใน 7 วัน" when `fullTaxInvoiceHint`) · "สำเนา" watermark on copies. `en` uses `labels.en`, no Thai letters.
   - `encodeEscPos(payload, { paper, drawerKick, thaiText, cut: true })` → `Uint8Array`: `ESC @` init first; columns **32** (58 mm) / **48** (80 mm); alignment `ESC a`; bold `ESC E` on title/grand total; double height `GS ! 0x11` on the grand total; `thaiText: "tis620"` encodes Thai via a built-in TIS-620 table (`ESC t` code page 255/CP874 selection byte configurable, default 255) and never emits bytes > 0xFF for Latin; `thaiText: "raster"` emits each Thai line as a `GS v 0` raster placeholder command whose bitmap the client supplies (the pure function returns `{ bytes, rasterSlots: [{ offset, text }] }` — the client rasterizes with canvas and splices); `GS V 66 0` partial cut at the end when `cut`; drawer pulse `ESC p 0 25 250` **only** when `drawerKick` and the bill has a CASH payment; copies get "สำเนา" line.
   - Both renderers take the payload only — no DB, no `Date.now()` (date comes from the payload) so output is deterministic for the oracle.
R7 **Refusals as data** (`{ok:false, code, message}` Thai, keys th+en): `DEVICE_REVOKED`, `DEVICE_LIMIT`, `DEVICE_NOT_FOUND`, `NO_PERMISSION`, `SALE_NOT_FOUND`, `VALIDATION`. Register refusal messages via `refusalMessageKey` as P1.9 did.
