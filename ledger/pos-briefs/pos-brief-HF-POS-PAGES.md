# HF-POS-PAGES — authorization gaps on today's POS pages (security hotfix · builder · worktree /root/projects/shark-hf2 · branch hotfix/pos-page-authz off origin/main)

Owner order 1 Oct: fix vulnerabilities when it can be done without affecting the CRM work in progress. Evidence: `/root/projects/shark-pos/ledger/REVIEW-POS-DESIGN-2026-10-01.md` §4 and §6 row 8 (read-only; verify every line in code yourself — the survey marked some PLAUSIBLE). Lane rules `/root/projects/shark-pos/ledger/pos-briefs/pos-brief-LANE-RULES.md` are binding (QC4 only, iso.sh, no build/server, no prisma, typecheck once with the 5632 MB heap command).

## In scope (controller verified none of these files is touched by any CRM branch)
`src/app/app/sys/[id]/pos/**` (register, sales, products, close pages + their components), `src/lib/actions/pos.ts`, `src/lib/modules/pos/{register.ts,service.ts read helpers}` ONLY where a guard is missing. Reported gaps:
1. `/pos/sales` (bill list) page: no permission check at all.
2. `/pos/close` page + its CSV export, `/pos/products` page and the price-setting action: `assertCan` called WITHOUT `unitId` ⇒ the branch check is skipped (`rbac.ts`: `canAccessUnit(m, undefined)` is true) ⇒ a user limited to branch A sees/exports/changes branch B.
3. Register page lists units not filtered by the actor's `unitAccess`.
4. Any other POS server action/page in scope that trusts a client-supplied `unitId`/`saleId`/`systemId` or checks permission without the unit — audit all of them and fix the same way.
Rule: follow the house page-guard pattern (404-not-403: `requireTenant()` → system `findFirst({id, tenantId, type: "POS"})` → `notFound()` → actor → permission WITH unit → `notFound()`); lists are filtered to the units the actor can access; a tenant-level action that truly is tenant-wide (e.g. setting an all-branch price) requires all-branch access. Use existing permission keys (`pos.sale.create`, `pos.sale.void`, `pos.product.setPrice`) — do NOT add a permission key (`permissions.ts` is a shared hot file; `pos.sale.read` comes in P1.15). No UI redesign, no behaviour change for users who have the right access; OWNER and all-branch users see exactly what they see today.
## OUT of scope (do not touch — CRM edits these files): `src/lib/ai/proposals.ts`, `src/lib/ai/tools.ts` (the AI `pos_create_sale` / `void_sale` gaps are handled in P1.6), `createSale`/`voidSale` signatures.
