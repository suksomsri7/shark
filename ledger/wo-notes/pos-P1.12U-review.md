**Findings**
- **F1 High: deviation 7, a dead end. Rejected as-is; blocks merge.** At `RegisterScreen.tsx:1391`, `localQuote` returns null for any cart with `memberId` or `couponCode`. Then `overrideQuote` (:894–901) is null, so `quoteFailed` stays `DISCOUNT_EXCEEDS_LIMIT`. The server quote prices with the cashier's cap (`register.ts` ~1365, priceCart refusal) and never sees the PIN. Case: member or coupon on the bill + a bill discount over the cashier's cap + a manager PIN, either armed from the discount sheet or the 21B PIN path (`approvalPin`, then `onRecallHeld(armPin)`). Pay stays disabled. The only way out is to detach the member and drop the coupon, which loses the tier discount, points and coupon. With no approval policy, PIN is the only path, so member bills with a manager discount can't be paid at all. The approved-held-cart path does pay, but it shows `discAuth.quote` (no choices), so applied points read as not applied and the due is stale until a `PRICE_CHANGED` round (see F9).
  - Smallest correct fix needs a controller ruling: `quoteRegisterCartAction` accepts `managerPin+managerUserId` and `heldCartId`, and runs `regDiscountOver` branches ②/① read-only (same `verifyManagerPin` counter as submit; no `cancelOpenPosRequest`, no audit) + an ORACLE-EDIT. This is more than 20 server lines.
  - UI-only stopgap (not recommended): allow a provisional `localQuote` for `discAuth.kind==="pin"` and rely on submit's `PRICE_CHANGED`. That breaks ruling 1.
- **F2 High: the cashier's points/voucher choices are silently dropped after a manager approval.** Path: pay dialog submit, then `APPROVAL_REQUIRED`/`PENDING_APPROVAL` (`RegisterScreen.tsx:1561`). The server holds `req.rawCart`, and `registerCanonicalCart` strips `memberChoices` (`register.ts:1480`). Then `approvalHandoff` → `resetBill` (:1663–1666), approve, and `onRecallHeld(viaApproval)` (:1128) rebuilds the cart with member + coupon but no choices, with no notice. Example: 500 points chosen, then approval → the customer pays ฿50 more unless the cashier re-enters them (nothing is burned, so no integrity loss). `memberId` and `couponCode` survive.
  - The other resubmit paths are OK: `retryPay` and sessionStorage restore resend the same bytes; P1.13U `TAX_ID_INVALID` keeps the pay layer and choices; `PRICE_CHANGED` and `MEMBER_RIGHTS_CHANGED` keep choices. `requestDiscountApproval` runs with the pay dialog closed, so it never has choices. Lock-screen auto-hold drops them, which ruling 12 accepts.
  - Fix: copy the `parkedTaxInv` pattern from :1665. Park `{heldCartId, choices}` in the handoff effect. On recall via approval, keep them in a ref. In `openPay`/`openPayPoints`, when `discAuth.kind==="approved" && heldCartId` matches, `setChoices(()=>parked)` and show a note. The re-quote clears anything invalid, and `PRICE_CHANGED` guards the total.
- **F3 Medium: the S-review follow-up "detach on recall" is not done.** There is no `MEMBER_SYSTEM_MISSING` handling anywhere in `RegisterScreen.tsx`. Case: a held bill with `memberId` recalled in a branch whose MEMBER system is gone. Every quote is refused; `memberSlot` is null because `memberEnabled` is false (:1967–1968), so there's no detach button. Removing the last line keeps `memberId` (:1448), so the bill is stuck until "clear bill". Fix: when `quoteErrNow==="MEMBER_SYSTEM_MISSING" && cart.memberId`, call `detachMember()` and show the `errors.memberSystemMissing` toast. Or strip `memberId` in `onRecallHeld` when `!memberEnabled`.
- **F4 Medium: a coupon that conflicts with the chosen voucher clears both.** On the same quote, the coupon wait (:950) reverts the coupon on `VOUCHER_COUPON_CONFLICT`, and the choices effect (:934–938) also clears the voucher. The cashier ends up with neither. Fix: in the choices effect, skip voucher clearing while `couponWait` is pending for that cart version.
- **F5 Low: quick-register key reused across different people.** The key rotates only on success or panel open. A network error on person A (actually created server-side) followed by typing person B's phone sends the same key; createMember's `pos-qr:<key>` replay can return A, who then gets attached ("existing" toast). Fix: rotate via a RegisterScreen callback when phone or name changes after a failed attempt (keeps S5.21: keys still created only in RegisterScreen).
- **F6 Low: Thai dates in the English UI.** `formatThaiDate` is used for voucher and reward expiry (`PayBenefits.tsx:245`, `MemberPanel.tsx:230`), so EN shows "5 ก.พ. 69". Pass the locale through.
- **F7 Low: tier colour has no fallback.** `tier.color` is used raw in the style (`MemberPanel.tsx:141`). There's no injection risk (React sets one CSS property; invalid values are dropped), but an empty or odd colour gives an unreadable badge. Guard with `/^#[0-9a-f]{3,8}$/i`, else use the grey "ทั่วไป" style.
- **F8 Low: restore path can close the pay dialog silently.** After a sessionStorage restore the cart is empty. A `POINTS_CAPPED` or `MEMBER_RIGHTS_CHANGED` response (:1545–1556) returns before `setPayError`; `setChoices` does nothing; the R4.1 effect then closes pay with no toast. Fix: auto-correct only when `cartRef.current.memberId===sale.memberId`, otherwise fall through to the normal error.
- **F9 Low: stale display on the approved path.** Folded into the F1 fix.
- **F10 Low: coupon wait treats any whole-quote refusal as a coupon failure** (UNKNOWN, `BENEFITS_EXCEED_TOTAL`, a PIN cart's `DISCOUNT_EXCEEDS_LIMIT`), so it reverts the code (:950). Acceptable; the toast text can be misleading.
