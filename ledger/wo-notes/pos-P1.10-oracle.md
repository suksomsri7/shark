## CONTROLLER-DECISION (read first)
**Rulings 7 Oct (controller):** CD1 = `PERMISSION_DENIED` only (oracle `PERM` tightened). CD2 = keep both openShift cases. CD3 = P1.10 adds `pos.sale.read`, granted to every role that has `pos.sale.create`; the test cashier keeps both keys. CD4/CD5 accepted as written. 1. **Permission refusal code.** Brief R7 names `NO_PERMISSION`. Every POS module today returns `PERMISSION_DENIED` (`register-shared.ts` RegisterRefusalCode, `shift.ts`, `payment-settings.ts`). The oracle accepts **either** (`PERM` constant). Please pick one. I recommend `PERMISSION_DENIED`, because it already maps to `errors.permissionDenied` and the UI handles it. After the ruling, the constant should be tightened through ORACLE-EDIT.
2. **openShift takes the device in `input.deviceId`**, not in `ctx.deviceId` (`shift.ts:467,478`). R2 says "when `ctx.deviceId` matches a REVOKED row". Following the intent ("revoked devices are refused"), V1 requires `DEVICE_REVOKED` in two cases: when ctx and input both carry the revoked code, and when only `input.deviceId` carries it (no ctx device). If you rule that ctx only is enough, drop the second case.
3. **`pos.sale.read` does not exist.** `core/permissions.ts:129-142` has no such key. `access.ts:25` says it "comes in P1.15", and `api/op.ts:20` says P2.13. Today bill reading is `posSalesScope` (`pos.sale.create`) + `posSaleWhere`. The oracle's cashier carries **both** `pos.sale.create` and `pos.sale.read`, so either gate passes. Receipts are therefore system-wide for all-unit actors and unit-filtered for scoped actors (A3 uses a cashier scoped to unit A reading a unit-B bill of the same POS). Decide whether P1.10 adds the `pos.sale.read` key or uses `posSalesScope`. The oracle is neutral.
4. **Tip cannot be sold today.** `payment-settings.ts:40 TIP_POSTING_READY = false` forces tip off, so the register refuses `tipSatang`. To cover `totals.tipSatang`, the fixture writes `tipSatang = 500` on its own bill and adds +500 to the PromptPay row, so that Σpay = grand + tip still holds. `pointEarned = 18` is also written directly, because the member bridge writes it only after the queue runs. Both writes stay inside the sandbox bill.
5. **No coupon on register bills.** `register-shared.ts:180` (ruling Q12) makes `couponCode` VALIDATION on the register. The bill has no coupon, so P3 asserts `couponDiscountSatang === 0` and `couponCode` absent or null. Coupon rendering is therefore not exercised (brief says "if the fixtures give one").
6. **Shared Prisma client was regenerated by another lane at 23:09:11 UTC.** The bind-mounted `node_modules/.pnpm/@prisma+client…/.prisma/client` now includes `model PosDocCounter` (P1.8 schema). This tree's `core/scope.ts` lacks it, so `db.ts` throws `[scope] … PosDocCounter` on import. Since then, **every** DB oracle in `shark-pos-c` (not only this one) crashes before running. My forced run finished before the regeneration. The final unforced re-run hit the crash (details below). I did not regenerate anything. The controller must reconcile the client with the trees. The same crash also makes the **pre-commit fitness hook fail** (`F10.1 … PosDocCounter`), so the safety commit of this oracle is blocked. The files are staged on `wip/pos-p1.10-oracle` and not committed; I did not use `--no-verify`.

## Encoding choices worth a second look
- The renderer tests take the real payload. The en checks swap the data strings for Latin (shop, lines, options, note, member, footer, cashier, device) and keep `labels`, so "en has no Thai" tests the captions, not the shop's Thai data.
- "Thai letter" means U+0E01–U+0E3A or U+0E40–U+0E5B. ฿ (U+0E3F) does not count.
- The ESC/POS text-line parser strips the known commands (ESC @ a E ! t - d J p, GS V v0 ( ! B). Column width ignores TIS-620 combining marks. The vatBase line is used for the 32/48 check because the grand total is double width.
- `encodeEscPos` has no locale. The oracle assumes Thai captions (`labels.th`) on paper.
- Tenant.limits is changed through raw SQL and restored together with the original `updatedAt`. Z2 fingerprints `Tenant(id, limits, updatedAt)`. DB suites serialize on `/tmp/shark-gate-qc4.lock`, so no other suite sees the temporary value.
