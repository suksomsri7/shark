## MAJOR-1 · v1 server actions (`crm/actions.ts`) work on uiVersion-2 systems ⇒ visibility bypass + v2 rules skipped — CONFIRMED (trace)
- Files: `src/lib/modules/crm/actions.ts:79-164` (6 actions, gate = `rbac.assertCan` only, `systemId` from FormData, **no uiVersion check**) → `service.ts:80/86/103/110/203` → `deals.ts:2038-2068` `createDealFromLegacy/moveDealFromLegacy/issueQuotationFromLegacy` (`who = null`) → `moveCore/createCore/quoteCore` read the row with `identityScope` (no `dealWhere`); `service.ts:99-120` `addActivity/completeActivity` = raw `tenantDb` writes (no `resolveTargets`, no `activityWhere`).
- Scenario: shop runs CRM v2; STAFF `thana` (default keys incl. `crm.deal.move`, `crm.deal.quote`, `crm.activity.complete`, TEAM visibility, team K) knows id `D` of a team-Q deal (ex-teammate after §11.6 move, a team-room digest link `/crm/deals/<id>`, a chat/email link). He POSTs the v1 action (server-action id is build-global, visible in any v1 CRM page/JS chunk) with `systemId=<v2 CRM>, dealId=D, stageId=<LOST stage>` ⇒ deal moved to LOST **without the mandatory lost reason**, or to WON ⇒ `crm.deal.won` fires (commissions, member DEAL_WON row, auto-invoice, team-room post) on a deal he cannot see. `issueQuotationAction` issues an accounting quotation for D; `completeActivityAction` closes any activity id; `createDealAction` opens a deal (legacy allows a non-OPEN stage, `deals.ts:626`) on an invisible contact; `addActivityAction` attaches to invisible deal/contact. MANAGER restricted by branch (`unitAccess`) passes `rbac.evaluate` everywhere.
- Why oracles miss it: `qc-crm-v1.mts` runs the six actions only as OWNER on uiVersion 1; `qc-crm-c1.11.mts` S6.10 static gate scan **explicitly exempts** `crm/actions.ts`; C1.7 visibility suites call v2 services only.
- Minimal fix: in `actions.ts` resolve `crmUiVersion({tenantId, systemId})` first and refuse (FORBIDDEN Thai / redirect to the v2 page) when it is 2 (mirror `assertCrmV2` → `assertCrmV1`); keep the legacy wrappers for v1 and bridges. Oracle: each of the 6 actions as a TEAM-scoped STAFF on a v2 system against an out-of-scope deal/contact/activity ⇒ refused, 0 rows changed.

## MAJOR-2 · Portal access survives "remove contact from company" (ex-employee keeps the company's portal) — CONFIRMED (reproduced QC2)
- Files: `member/customer-session.ts:648` `portalAccessUsable` checks `crmCompanyContact.findFirst({tenantId, companyId, contactId})` **without `endedAt: null`**; `companies.ts:1079-1088` `removeContact` only sets `endedAt` (row kept as history) and never touches `CrmPortalAccess`; same gap in `portal.ts:1006` `listContacts` and `portal.ts:1075` `invite` (link lookup ignores `endedAt`). Only `revoke`/PDPA erase ever revoke an access.
- Probe result (`probe-portal-ended-link.mts`): `link_endedAt_set:true` → old session still valid, `listQuotations` 1 → 1; a **new** session (what OTP/LINE login mints) still mints and reads 1 quotation; staff `listAccess` still says `ACTIVE`; `listContacts` still lists the ex-employee.
- Impact: contact who changed jobs (staff did the normal "remove from company" / move to new company) keeps reading invoices/quotations/contracts of the old company and, with role APPROVE, can **accept/reject quotations and create requests in its name**; the company contact list keeps exposing former contacts' e-mail/phone to other portal users.
- Why oracles miss it: `qc-crm-c3.5.mts` fixtures create links once and never end one; X8.4 covers archived/suspended contacts only.
- Minimal fix: `portalAccessUsable` + `invite` + `listContacts` require `endedAt: null`; additionally revoke accesses/sessions of `(companyId, contactId)` inside the `removeContact`/move-company tx (audit `crm.portal.revoke` reason "left company"). Oracle: end the link ⇒ `getPortalSession` null, `mintPortalSession` refused, OTP `isKnown` false, `listContacts` excludes.

## MINOR-1 · `crm.api.manage` holder can mint a `crm.admin` key (every CRM key, ALL visibility); key outlives its creator — CONFIRMED (trace)
`crm/settings/api/actions.ts:40-90` checks `crm.api.manage` + rbac `api.key.create` (MANAGER passes rbac), then lets the caller pick any bundle; `api-keys/scopes.ts:354` crm.admin = all keys incl. visibility/settings/portal/export; `visibility.ts:193` API actor = ALL. A MANAGER/STAFF the owner granted `crm.api.manage` escalates to owner-level CRM access. `verifyApiKeyDetailed` never re-checks the creator's membership ⇒ key keeps working after the creator is demoted/removed (records created by the key are owned by a departed user). Mitigation: `crm.api.manage` is owner-only by default. Fix: allow `crm.admin` only for OWNER (or bundle ⊆ creator's `crmCan` keys) and treat keys whose `createdById` has no accepted membership as revoked.

## MINOR-2 · Team/owner-filtered API keys (and branch-restricted MANAGERs) read the whole "unmatched" mailbox — CONFIRMED (trace)
`emails.ts:2079-2085` `assertUnmatchedGate` returns early for role MANAGER (admin keys map to MANAGER, `api/actor.ts:33`) and calls `visibility.resolve` which returns ALL for any API actor (`visibility.ts:193`), ignoring `crm.filter.team:`/`crm.filter.owner:` (R-C.3 "narrow only"). ## MINOR-3 · Inbound e-mail direction trusts a STAFF-editable "from" address and an unauthenticated verified domain — CONFIRMED (trace, staff part) / PLAUSIBLE (outsider part)
`emails.ts:1835-1860`: `staffByOverride` = any `CrmEmailUserSetting.fromAddr` of the system; `setUserSetting` (`emails.ts:572`, key `crm.email.send`, STAFF default) accepts **any** syntactically valid address (`cleanAddrPatch:466`, no domain/verification). A STAFF sets his fromAddr = a customer's gmail ⇒ that customer's real replies (gmail DKIM passes `authResultPass`) are stored as direction OUT "sent by thana", contact unmatched (OUT matches by To only), reply handling/sequence stop skipped. Separately `fromAuthenticated` accepts `From` on the shop's VERIFIED sending domain without any DKIM/SPF evidence ⇒ an outsider mailing the public `crm+<key>@` reply address with `From: owner@shopdomain` plants an "outgoing e-mail by the owner" on a customer's timeline (blocked only if the MX enforces DMARC reject). Fix: override address must be on a VERIFIED domain and never equal a CRM contact's e-mail; drop the "verified domain ⇒ authenticated" shortcut (require `authResultPass`).

## Checked and found sound
- REST core: key → tenant only from the key row; `X-Shark-System` must be a CRM system of that tenant; v1 409 before body/idempotency (incl. teams path and unbound keys); revoked/expired keys; READONLY cannot write/export; exports = admin key only (`contacts.export`, `records.export`, `reports.export.start`); idempotency unique `(keyId, idemKey)` — no cross-key replay; service-level `convertContact` key is scoped by contact id; key filters enforced on reads (`visibleWhere`, `recordVisibilitySql`, reports) and on writes (`api/filters.ts`).
- `crmCan` matrix (OWNER/MANAGER-excluded 5 keys/STAFF implicit read/API scope-only/CUSTOMER none); `visibleWhere` OWN/TEAM/ALL, per-pipeline policies, lead ≥ TEAM, branch `unitTeams`, orphan activities cap; `canSee`/`visibleIdsAmong`/`visibleIdsForViewer` (kanban cards).
- v2 services spot-checked end to end: contacts (mutate/assign/bulkAssign/convert/import update-mode), deals 360/move/quote, activities `resolveTargets` + mention filter, files attach/list/remove, calls recording, emails threads/attachment/attachToContact (row-level filter), consents, scoring explain, web timeline, objects timeline/export, commissions (own-row rule, cap of key creator), reports scope + scheduled reports per recipient, home KPIs, widgets on `/p`, notifications `notifyStaff`, AI assist facts + proposal confirm (visibility re-check of every id), chat CRM panel, mobile routes, POS open-deal picker, unfurl.

- Public lanes: `/t/e` `/t/consent` identify only via AES-GCM ticket bound to tenant+system; `/l/<code>` target from DB; inbound route secret + per-system inbound key; thread join scoped by system.
- Teams (`/app/settings/teams`, `/teams` ops) gated by OWNER/`crm.team.manage`; visibility policies by `crm.visibility.manage`; uiVersion switch OWNER + env allowlist.
