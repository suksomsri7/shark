## CONTROLLER-DECISION (read first — the oracle encodes my proposal for each; rule before the builder starts)
1. **CD-A: `CARD_REQUIRES_INTENT` conflicts with P1.6.** R4 says "CARD **requires** a PAID intent (`CARD_REQUIRES_INTENT`)". But P1.6 already ships `PosPayType.CARD` as an EDC card with a manual reference (`schema pos.prisma:17` "บัตร (EDC/อ้างอิงมือ · ไม่มีเกตเวย์ — P1.7)"). `qc-pos-p1.6` T2/T5/T6/T7 submit `CARD` + `reference "EDC-…"` with no intent and expect PAID. The brief also says `qc-pos-p1.6` must stay green. Enforcing the rule breaks P1.6 and removes EDC cards for every shop without Beam (prod has no Beam keys). **Oracle proposal:** a CARD with a `pi_` reference = Beam card intent (consumed like PROMPTPAY). A CARD with any other reference or none = the P1.6 EDC path, unchanged. S6 asserts `CARD + "EDC-778899"` → PAID with the reference stored. `CARD_REQUIRES_INTENT` is **not** asserted and is not in the 13 required codes. If you rule strict, S6's CARD half flips (ORACLE-EDIT) and `qc-pos-p1.6` T2/T5/T6/T7 need edits too.
2. **CD-B: there is no "business profile `promptpayId` of the linked book".** The schema has two sources: (a) `PaymentProfile.promptpayId`, one per **tenant** (`payment.prisma`). The legacy POS uses it (`actions/pos.ts:321 getPaymentProfile({tenantId})`). (b) `AccountFinance.promptpayId`, one per **finance channel** of a book (`account_gl.prisma:279`). The account module's `payment-request.ts` reads it first, then falls back to (a). Nothing exists per branch/unit. **Oracle proposal:** use (a) `PaymentProfile.promptpayId` (legacy parity, one ID per shop). A fallback to a channel of the linked book is allowed. The fixture sets **both** to `0812345678`, and C3 clears/corrupts **both**, so either rule passes. Per-branch IDs are a follow-up. Note that the brief's "branch's PromptPay ID" does not exist.
3. **CD-C: real Beam has no PromptPay QR in `beam.ts`.** `createCharge` today posts `paymentMethod: {paymentMethodType: "CARD"}`, needs `description` + `returnUrl`, has no `method` input, and returns only `{url, chargeId}`. R2 needs `createCharge({amountSatang, referenceId, method: "promptpay"})` and a QR payload. The builder must extend `beam.ts` additively (a `method` input, plus the QR field Beam returns). The real Beam PromptPay response shape cannot be checked without docs or keys. The oracle uses only its fake `deps.beam`. **The oracle's adapter contract:** `deps.beam = { enabled(): boolean; createCharge(input: { amountSatang; referenceId; method: "promptpay"|"card"; description?; returnUrl? }): Promise<{ chargeId; url?; qrPayload? } | { error }> }`. `PROMPTPAY_BEAM.qrPayload = result.qrPayload`, and `CARD_BEAM.qrPayload = result.url` (QR of the hosted card page). The default adapter = `{ enabled: beamEnabled, createCharge }` of `lib/payment/beam` (same pattern as the account `beamAdapter`, not imported from account).
4. **CD-D: exercising the route.** `verifyWebhook` → `beamConfig()` needs **all three** `BEAM_MERCHANT_ID/BEAM_API_KEY/BEAM_WEBHOOK_SECRET`, not only the secret. Inside W5 the oracle sets three fake values in its own process (never printed), imports the route, POSTs signed and unsigned bodies, and restores the previous values in `finally`. No other check runs while they are set. If the route cannot be imported in script context, W5 reports `route import ไม่ได้…` and checks the facade only. The red run shows that the route imports fine today.
5. **CD-E: lazy status writes.** R5 lets the oracle writer choose. **Chosen: `paymentIntentStatus` writes** `EXPIRED` (a guarded update `WHERE status='PENDING' AND expiresAt < now`), so the screen and DB never disagree. A late webhook after that is still accepted (W4 → PAID `lateWebhook:true`). E2 asserts that the row is `EXPIRED` after the read.
6. **CD-F: 24 h consume window applies to every PAID intent.** CD4 states it for late webhooks. The oracle applies it to any PAID intent: `paidAt` older than 24 h → `submitRegisterSale` refuses `INTENT_EXPIRED` (S2), and the manager handles it manually. Say so if it should apply to late ones only.
7. **CD-G: untested safety gaps (please rule; I recommend refusing both).** (a) The intent kind does not match the pay type (a `CARD_BEAM` intent submitted as `PROMPTPAY`, or the reverse). Suggest `INTENT_NOT_FOUND` or `VALIDATION`. (b) The webhook `chargeId` ≠ `intent.beamChargeId`. Suggest ignore + ops WARN. (c) A webhook for a `PROMPTPAY_STATIC` intent (no Beam charge). Suggest ignore. The oracle always sends the matching chargeId and only Beam intents, so it constrains none of these.
8. **CD-H: settings writer.** No setter for `settings.pos.payment.*` is in scope (17A/P1.18 UI). The oracle writes `AppSystem(POS).settings.pos.payment` JSON directly. Parser defaults: `beam.enabled` true only when `=== true`. `qrExpiryMinutes` is an integer 5..60; anything else (4, 61, `"20"`, missing) = **15** (default, not clamped; C7). `manualConfirmRequiresManager` true only when `=== true`. Note: `updatePosPaymentSettings` (P1.6) rebuilds `pos` from `{...pos, serviceCharge, tip}`, so it keeps `pos.payment`. Keep it that way.
9. **CD-I: outbox drain after the sale tx.** CD5 puts the intent lock in `register.ts` "with the sale tx client", meaning `createSale(input, tx)`. `createSale` skips its own post-commit drain when called inside someone else's tx (`service.ts:340`), so `pos.sale.paid` (account posting, stamps, CRM) would wait for the cron. The builder should `scheduleDrain()` after its own tx commits. This is not asserted (consumers are covered by `qc-pos-account`).
10. **CD-J: ops-event naming.** `logOps(level, source, message, {detail, tenantId})` has no "event type" column. The oracle finds an ops event when its row has **`tenantId` = the shop** and the literal name (`pos.payment.beam_fallback` / `pos.payment.amount_mismatch` / `pos.payment.refund_needed`) appears in `source`, `message` or `detail`. `amount_mismatch` must be `WARN`. `refund_needed` may be WARN or ERROR (ERROR mails `OPS_ALERT_EMAIL` when set; QC4 has none).
11. **CD-K (CD6, for the owner): follow-ups.** Card MDR fee accounting (the `pos.sale.paid` account consumer books CARD at gross, so a Beam fee needs an expense line later). Beam refunds (P1.8 refunds stay a manual money return; Beam refund API = follow-up). A "เงินเข้าไม่มีบิล" report for PAID intents never consumed after 24 h.
12. **Hourly cron.** The POS cron registry exists: `src/app/api/cron/hourly/route.ts` runs `forceCloseStaleShifts` (P1.9). E1 requires that file to call `expirePaymentIntents(…)` as well. Hourly lags the 15-minute expiry, which is fine because the lazy status (CD-E) covers the register.

## Drift (brief vs code on 1c7bb5c5)
- `PosPayType.CARD` **already exists** (P1.6). R7's "add CARD if missing" is a no-op, and no enum migration is needed.
- `REGISTER_PAY_TYPES = CASH|PROMPTPAY|TRANSFER|CARD`. `regParseSubmit` today **refuses `reference` on PROMPTPAY** ("เลขอ้างอิงใส่ได้เฉพาะบัตรและโอน"). P1.7 must allow it on PROMPTPAY **only** when it matches `^pi_`. Any other PROMPTPAY reference stays VALIDATION (S6). `REGISTER_REFERENCE_MAX` = 100, so intent ids must fit.
- `createSale` payMethods has no `note` field (`{type, amountSatang, refSaleId?, cashTenderedSatang?, reference?}`). `PosPayment.note = "via WEBHOOK|MANUAL"` needs an **additive optional `note?`** on the pay-method input (allowed: COMMON-2 "add fields"), or a post-create update inside the same tx.
- `createSale(input, client)` already accepts a tx client. The intent lock + CONSUME + createSale can share one `prisma.$transaction` in `register.ts` with no signature change (CD5 holds).
- Webhook route prefix style: the account branch uses `"acc:"` (colon). POS uses `"pos-"` (hyphen) per the brief, so `referenceId = "pos-pi_…"`. Today a `pos-…` reference falls through to `creditFromCharge` (AI top-up) → `bad_reference`, logged as an **ERROR OpsEvent without tenant** (seen in the red run, cleaned by Z1).
- The route's 401 path writes an OpsEvent with `tenantId = null` (sha256 fingerprint of the body). Z1 deletes this run's tenant-less OpsEvent rows by marker (RAND / body fingerprint / reference) and requires 0 left.
- `PaymentProfile` has `tenantId @unique` (no unit). `AccountFinance` has `promptpayId` per channel (CD-B).
- Message files are `src/messages/{th,en}/pos.json` (namespace files), not `src/messages/*.json`. `pos.payment.errors.*` = key `payment.errors.<camelCase>` in those files. The register's `refusalMessageKey(code)` returns keys relative to `pos.register` (`errors.x`). C10 accepts a key that resolves under `register.` **or** from the `pos` root (e.g. `payment.errors.intentNotPaid`).
- `deviceId` appears both in `createPaymentIntent` input (R2) and in `ctx` (RegisterCtx P1.9). The oracle sends the same value in both. Shift device codes are `[A-Za-z0-9_-]{8,64}`, so `"x"` is VALIDATION.
- §4 says "C1–C6". The oracle adds C7 (expiry setting), C8 (permission/device guard), C9 (static schema/registration) and C10 (R8 refusals-as-data + message keys), keeping the `C*` family named in the prompt.
