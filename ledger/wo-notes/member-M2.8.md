## 2. ข้อตัดสิน (จุดที่สัญญาไม่ชัด แล้วผมตัดสินเอง)

### 2.1 เขียนบิลก่อน แล้วค่อยตัดสิทธิ์ แล้วค่อยแก้ยอด — ทั้งหมดใน tx เดียว
`applyOnSale` ต้องผูก voucher/แต้ม/บัตรกำนัลกับ `saleId` ที่ **มีอยู่จริง** (ร่องรอยย้อนกลับได้) แต่ยอดที่ต้องจ่ายต้องรู้หลังจากนั้น
⇒ ลำดับในtx: ตรวจคูปอง → สร้าง `PosSale` (ยอดชั่วคราว = ก่อนหักสิทธิ์) + บรรทัด → `applyOnSale` → คิดยอดจริง → **ตรวจยอดชำระ** → อัปเดตบิล (ยอด + คอลัมน์สมาชิก) → payment → redeem คูปอง → outbox
ล้มข้อไหนก็ rollback ทั้งใบ (ข้อสอบ S1.6 ยืนยัน: throw 3 แบบแล้วไม่มี `PosSale` ของคีย์นั้นเลย · ตัวนับเลขใบเสร็จก็ย้อนกลับด้วยเพราะอยู่ในtx เดียวกัน)
**บิลที่ไม่มีสมาชิก**: ตรวจยอดชำระที่จุดเดิม (ก่อนแตะตัวนับเลขใบเสร็จ) และไม่ยิง query ระบบสมาชิกเลยแม้แต่ครั้งเดียว ⇒ เส้นทางเดิมเป๊ะ

### 2.2 หนี้ M2.7 ปิดแล้ว: `cart` บังคับ · ลบตะกร้าในหน่วยความจำทิ้ง
`ApplyOnSaleInput.cart` เปลี่ยนเป็นของบังคับ · `CART_MEMO`/`rememberCart`/`recallCart` ถูกลบออกจาก `wallet.ts`
เหลือทางสำรองทางเดียว: บรรทัดว่าง → อ่านจากแถว `PosSale` ของ `saleId` (ทางที่ POS ใช้จริงคือส่ง `cart` มาเสมอ)

### 2.3 🔴 คูปองยังเป็นของ POS — กระเป๋าสิทธิ์แค่ "ตัดสินกติกากันซ้อน" ให้
`createSale` ส่ง `cart.couponCode` เข้า `applyOnSale` ด้วย (ไม่งั้นกติกา "voucher ใบนี้ใช้ร่วมกับคูปองไม่ได้" ไม่มีทางทำงาน เพราะกระเป๋าไม่รู้ว่าบิลนี้มีคูปอง)
แล้ว **หักบรรทัด `COUPON` ออกจากยอดสิทธิ์** ก่อนเอาไปลบยอดบิล — ส่วนลดคูปองยังคิดที่เส้นเดิมของ POS ที่เดียว (ไม่นับซ้ำ)
`applyOnSale` ไม่โยนเมื่อคูปองชนกติกา (คูปองไม่ใช่ของกระเป๋า) จึงเพิ่ม `conflicts` ในผลลัพธ์ แล้วให้ POS ตัดสิน:
**โยนเมื่อ "มีคูปอง + มี conflict COUPON + มี voucher ที่ถูกใช้ไปแล้ว"** เท่านั้น
เหตุผลที่ไม่โยนทุก conflict: conflict คูปองที่เกิดจากเหตุอื่น (เช่นยอดหลังหักส่วนลดระดับต่ำกว่าขั้นต่ำของคูปอง) ไม่ควรทำให้บิลที่เคยขายได้กลายเป็นขายไม่ได้ — เส้นคูปองเดิมของ POS ยังตัดสินตามเดิม

### 2.4 idempotency ของ "ยอดใช้จ่ายสะสม" ใช้แถวไทม์ไลน์เป็นธง — เขียนคู่กันใน tx เดียว
`member.recordSpend` บวกยอดตรง ๆ ไม่มีคีย์กันซ้ำของตัวเอง (drain ซ้ำ = ยอดเบิ้ล = เลื่อนระดับผิด)
⇒ เช็ค `MemberActivity {module:"pos", type:"PURCHASE"|"VOID", refType:"PosSale", refId}` ก่อน แล้วเขียน `recordSpend` + `logActivity` ใน `$transaction` เดียว
**ต่างจากลำดับในหัวข้อสอบเล็กน้อย** (สัญญาเขียนว่า activity อยู่ท้ายสุด): ถ้าเขียน activity ท้ายสุดแล้วขั้นกลางล้ม retry จะบวกยอดสะสมซ้ำ — ผลปลายทางที่ข้อสอบวัดเหมือนกันทุกข้อ
ตารางไทม์ไลน์ไม่มี unique index ให้พึ่ง (ใบนี้ไม่มี migration) → ตรวจซ้ำอีกครั้งในtx เพื่อกันสองคิวเข้าพร้อมกัน

### 2.5 `paidBy` ของ `computeEarn` อ่านจาก "รอยที่ applyOnSale เขียนไว้"
ไม่มีคอลัมน์เก็บ "จ่ายด้วย voucher/แต้ม/บัตรกี่บาท" บนบิล ⇒ สะพานอ่านเอง:
voucher = `Voucher.usedRef.discountSatang` ของ `PosSale.voucherUseIds` · บัตรกำนัล = `GiftCardTxn.satang` ของ `PosSale.giftCardTxnId` · แต้ม = |ledger BURN ของบิลนั้น| × `burnRateSatang`
(แต้มคูณอัตราได้ค่าเป๊ะเสมอ เพราะ `applyOnSale` ตัดจำนวนแต้มลงให้พอดีเพดานก่อนแล้ว — `usePoints × rate ≤ cap ≤ remaining` ทุกกรณี)
**หนี้**: ถ้าวันหน้าอยากได้ตัวเลขนี้ตรง ๆ ควรเพิ่ม 3 คอลัมน์บน `PosSale` (migration) แทนการอ่านย้อน

### 2.6 สะพานสมาชิกโยน error ได้ (ไม่กลืน) — คนที่ครอบคือ consumer
สมาชิกของบิลหายไปจากระบบ = ข้อมูลไม่สอดคล้อง ต้องเห็นใน OpsLog ไม่ใช่เงียบ ⇒ `assertMemberAlive` โยน
`outbox-consumers.ts` ครอบ try/catch เอง (ไม่พึ่ง `compose` ชั้นนอก เพื่อให้ข้อความ WARN บอกได้ว่าเป็น "สะพานสมาชิก" ไม่ใช่ "สะพานบอร์ดงาน") → event ยัง DONE · บิล/บัญชีไม่กระทบ (S4.1 ยืนยัน)
ขา void ผ่อนกว่า: คืนสิทธิ์/ยกเลิกตราให้ก่อน แล้วถ้าสมาชิกถูกลบไปแล้วค่อย return เงียบ (ของที่คืนได้คืนไปแล้ว)

### 2.7 dynamic import 2 จุด (กันวงจรโมดูล)
`pos/service.ts` → `await import("@/lib/modules/member")` และ `outbox-consumers.ts` → `await import("@/lib/member-bridges")`
เส้นวงกลมจริง: `pos/service → member/index → wallet → giftcard/index → giftcard/service → pos/index → pos/service` และ `member-bridges → member/index → … → pos/service → scheduleDrain → outbox-consumers`
(แพตเทิร์นเดียวกับ `kanbanBridge`/`stampFromSale` ที่ไฟล์นั้นใช้อยู่แล้ว · ผลพลอยได้: บิล walk-in ไม่ต้องโหลดกราฟโมดูลสมาชิกทั้งชุด)
เส้น `pos→member` / `pos→point` อยู่ใน allowlist ของ fitness อยู่แล้ว — ใบนี้ทำให้ **น้อยลง** ไม่ได้เพิ่ม

### 2.8 สแตมป์ถูกเรียกซ้ำโดยตั้งใจ
consumer เดิมของ M2.3 (`stampFromSale`/`stampVoidForSale`) ยังอยู่เหมือนเดิม และสะพานสมาชิกเรียก `stamp.autoStampFromSale`/`voidStampsForSale` อีกครั้งตามสัญญาใบนี้
ทั้งคู่ idempotent ด้วยคีย์ `sale:<saleId>:<cardId>` ⇒ ตราไม่เบิ้ล (S3.1 drain ×3 ยืนยัน) · เก็บของเดิมไว้เพื่อไม่แตะพฤติกรรมของ M2.3

### 2.9 `posServices` ได้ทางสำรองอ่าน `BookingService` ของสาขา
`registerSaleAction` ตรวจ `serviceId` ที่ client ส่งมากับตาราง **BookingService ของสาขานั้น** อยู่แล้ว (โค้ดเดิม) แต่หน้าขายดึงรายการบริการจาก **แคตตาล็อกกลาง (InvItem)** เท่านั้น
⇒ ร้านที่ยังไม่เปิดระบบคลัง (รวมถึงร้าน QC ของชุดสมาชิก) หน้าขาย "ว่างเปล่า" ต้องพิมพ์รายการเองทุกบิล และยอดไม่เข้ารายงานฝั่งบริการ
เพิ่มพารามิเตอร์ที่ 3 (`unitId?`) แบบไม่บังคับ: มีบริการในแคตตาล็อกกลาง = ใช้ของเดิมทุกประการ · ไม่มีเลย **และ** ผู้เรียกส่งสาขามา = อ่าน `BookingService` ของสาขานั้น
ผู้เรียกเดิมที่ส่ง 2 พารามิเตอร์ (หน้า "สินค้า/ราคา" · ข้อสอบ `qc-catalog-services` ที่ยืนยันว่า `posServices(tid, null) = []`) ได้พฤติกรรมเดิมเป๊ะ

### 2.11 บิลที่ "แนบชื่อลูกค้าไว้เฉย ๆ" ต้องไม่ล้มเพราะคนนั้นอยู่คนละระบบสมาชิก
`applyOnSale` โยน `MemberNotFoundError` เมื่อ `memberId` ไม่ได้อยู่ในระบบสมาชิกของสาขานั้น
บิลเดิมจำนวนมาก (โรงแรม/ร้านอาหาร/คลินิก/ร้านที่เพิ่งเปิดระบบสมาชิกทีหลัง) แนบ `memberId` แบบนั้นอยู่ — ก่อน M2.8 ขายผ่าน
⇒ `applyMemberRights()` กลืน `MemberNotFoundError` **เฉพาะเมื่อไม่ได้สั่งใช้สิทธิ์อะไรเลย** (ไม่มี voucher/แต้ม/บัตรกำนัลใน `memberChoices`) → บิลเดินเส้นทางเดิม
ถ้าพนักงานสั่งใช้สิทธิ์มาจริง = โยนเสมอ (เงียบ = ลูกค้าจ่ายเต็มทั้งที่หน้าจอบอกว่าได้ส่วนลด)
กลืนเฉพาะ error ชนิดนี้เท่านั้น — error อื่น (voucher ใช้ไม่ได้ · แต้มไม่พอ · PIN ผิด) ยังล้มบิลตามเดิม

### 2.10 แผงสิทธิ์เรียก 2 เส้น (กระเป๋า 1 ครั้งต่อคน · ใบเสนอราคาทุกครั้งที่ตะกร้าเปลี่ยน)
`posMemberRightsAction` = ของที่ไม่เปลี่ยนตามตะกร้า (ระดับ · รายการ voucher · แต้มคงเหลือ · บัตรกำนัล · ใบสะสม) โหลดตอนเลือกคน

### 3.1 🔴 `M2.8-S2.3` — `progress.stamps` หลัง void บิล s1 ต้องเป็น **1** ไม่ใช่ 0 (ข้อสอบไม่ได้นับบิลคูปอง)
ข้อสอบเปิดบิลให้สมาชิก X **สองใบ** ที่เข้าเกณฑ์ใบสะสมเดียวกัน (`PER_SALE_MIN` ขั้นต่ำ ฿1,000 · `perDayMax` 3):
`s1` = ฿2,695 (บรรทัด 102) และ `sC` = ฿3,895 (บรรทัด 165 · ดrain ที่ 167) ⇒ ตอนถึง S2.3 ตราสะสม = **2** ไม่ใช่ 1
void `s1` คืนตราของบิลนั้นใบเดียว ⇒ เหลือ 1 (ข้อสอบคาด 0)
**หลักฐานที่วัดเอง** (สคริปต์ชั่วคราว ลบทิ้งแล้ว · เปิดบิล 2 ใบให้สมาชิกใหม่บนใบสะสมใหม่ แล้ว void ใบแรก):
```
PROBE stamps: หลังบิล1=1 หลังบิล2=2 หลัง void บิล1=1
```
ส่วนอีก 3 เงื่อนไขของข้อเดียวกันผ่านหมด: `StampEvent type VOID = 1` · `recordSpend −269,500` · `MemberActivity VOID 1 แถว refId = s1`
เป็นพฤติกรรมของ M2.3 (ตราสะสมข้ามบิล) ไม่ใช่ของใหม่ในใบนี้ — **ขอให้ Fable เคาะ**: เปลี่ยนเป็น `progV.stamps === 1` หรือให้ `sC` เป็นบิลที่ต่ำกว่าขั้นต่ำ
