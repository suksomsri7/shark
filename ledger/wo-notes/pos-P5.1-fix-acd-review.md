## Findings
- **F1 MED: the MA3 price gate can be bypassed with a bill discount.** At `actions/pos.ts:135` (computeTotals) the bill discount is only clamped to ≤ subtotal. At `:481` it goes straight into createSale. There is no seller discount cap, unlike V2, where `registerSellerLimits`/`regMaxDiscountBp` gives STAFF 1000 bp by default (`register.ts:1373-1402`, `pricing-shared.ts:196-201`). Input: STAFF (pos.sale.create only, V2 off = the default screen) sells the 12,000 catalogue item at 12,000 (it passes `legacyUncataloguedLines` as catalogue) with billDiscountSatang 11,900. Result: a PAID bill for 100 satang. This is the hunt's own F3 scenario ("STAFF sells 12,000 at 100"; the hunt also lists "no discount cap"). MA3 stays green only because the oracle tests the unit price alone. Smallest fix: in registerSaleAction, after computeTotals, `caps = await registerDiscountCaps({tenantId, systemId})`, take `lim = registerSellerLimits(actor, unitId, caps)`, and refuse with the V2 text "ส่วนลดเกินสิทธิ์ของบัญชีนี้" when `lim.maxDiscountBp !== null && billDiscount*10000 > lim.maxDiscountBp*subtotal + 5000`. The S5.12 sha then changes again, so the ORACLE-EDIT has to use the post-fix sha. The other option is to log it as a P5.1 debt row with an owner ruling, since shops may rely on staff discounts on the legacy screen today.
- **F2 LOW: MA8 now refuses one legacy restaurant shape.** `restaurant/order.ts:615` (and `:572`) sets the line price to `unitPrice + optionsTotal`. Option deltas may be negative and are not sign-checked (`actions/restaurant.ts:121`, `menu.ts:158`). Example: base 2,000 with the option "|-30" (−3,000) gives a line price of −1,000. Before this batch the table closed with a negative line. Now checkout returns `{ok:false}` with "ราคาต่อหน่วย…ไม่ติดลบ" and the table cannot close until the menu is fixed. V2 `priceCart` already refuses this (`pricing-shared.ts:173`), so the new rule matches V2. No money is wrong. Smallest fix (batch B or debt): refuse a negative effective price at order time / menu save.
- **F3 INFO: CD-P51-O4 names the code `REGISTER_V2_ON`.** The legacy action has no code field (`RegisterSaleState`), so it returns a Thai message only (`actions/pos.ts:54-55`). No new code was added and the contract is unchanged. Controller to accept the wording. The legacy UI is Thai-only (no i18n), so a missing en string is not a regression.
