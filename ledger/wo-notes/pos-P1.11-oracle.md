## CONTROLLER-DECISION (read first — the oracle encodes my proposal for each; rule before the builder starts)
1. **Module boundary (F2) — POS cannot import chat or kanban.** `scripts/fitness.mts` ALLOWED_EDGES has `pos→member/point/system/account/coupon/crm/inventory` only. No `pos→chat` and no `pos→kanban`. So `sendLineToParty` (chat) and `createCardFromExternal` (kanban) cannot be called from `src/lib/modules/pos/**`. The oracle assumes the member-module pattern (`src/lib/member-journey-senders.ts`): a **composition-root file `src/lib/pos-receipt-bridges.ts`** that (a) exports `onReceiptIssueReported(evt)` (the issue consumer body: board lookup, `createCardFromExternal`, `sendLineToParty` ack, writes `PosReceiptIssue.kanbanCardId`), registered in `outbox-consumers.ts`, and (b) provides the real LINE sender that `sendReceiptAction` injects into `sendReceipt(…, {deps})`. The alternative is adding `pos→chat` and `pos→kanban` edges to fitness (hot file). ST5 fails if any pos file imports `@/lib/modules/chat|kanban`. The oracle also accepts `onReceiptIssueReported` exported from `receipt-issue.ts`, but that file then cannot reach kanban.
2. **`sendLineToParty` has no dependency injection** and makes a network call through `pushToContact → adapter` whenever a CONNECTED `ChatChannelConnection` exists. As the prompt allows, I made LINE injectable on the POS side: `sendReceipt(ctx, actor, input, opts?: { deps?: { line?: (ctx: ChatPartyCtx, input: SendLineToPartyInput) => Promise<SendLineToPartyResult>; fetch?: typeof fetch } })`. S1 (success and audit) uses a fake `deps.line`. S2 runs the **real** path with no deps: a member who has a party but no LINE ChatContact, in a temp tenant with no ChatChannelConnection. That path never reaches the network. It must return `NO_LINE_IDENTITY`. A global `fetch` guard (503, counted) is installed for the whole DB phase as a second safety net.
3. **Mapping the chat refusal to `NO_LINE_IDENTITY`.** `party-bridge.ts` returns only a Thai `reason`, and its `NO_LINE_IDENTITY` string is a non-exported `const`. To return the code in S2(c), the builder must either export that constant or add an additive `code?: "NO_LINE_IDENTITY"` to `SendLineToPartyResult` (that is the chat module, not on the hot-file list). The POS side alone can only check "no member" and "member without partyId" (S2 a/b). Please pick one.
4. **Q1 lazy token on an old bill.** R1 says old bills get a token "lazily through `ensureReceiptToken`", but it does not say when. The oracle requires that `receiptPayload` (with `qrEReceipt` on) on a token-less bill calls `ensureReceiptToken` and prints that URL, which means a write inside `receiptPayload` (P1.10 R8 called it read-only apart from audit). If you rule that lazy creation happens only on send/copy-link, drop the `bOld2` sub-assertion of Q1 by ORACLE-EDIT.
5. **Issue board: where it comes from.** The brief says "if the tenant has no board for POS issues", but no setting exists. The oracle sets `AppSystem(POS).settings.pos.receipt.issueBoardId = <boardId>` before I3. If there is no setting, the issue is skipped as `no-board`. A builder that falls back to "first ACTIVE board" (the member `escalate()` rule) also passes I3, because the temp tenant has exactly that one board. I2 runs before any board exists, so both rules pass it too. Note: `parseReceiptSettings` (P1.10) drops unknown keys, so the key needs adding there or must be read raw. Also, I recommend **no fallback**, so the first board of a shop does not silently receive customer complaints.
6. **`KanbanCardSourceType` has no POS value** (MANUAL TEMPLATE CHAT FORM EMAIL AUTOMATION AI REVIEW). Either add `POS` to the enum (an additive enum value; CD5 lists only the column and the two tables) or reuse `AUTOMATION`. The oracle does not check `sourceType`. It checks `sourceKey` ⊇ issueId, the board, and that the title contains the receipt no.
7. **"Recorded in the event result" — OutboxEvent has no result column** (only `status/lastError`), and `withAutomation` drops handler return values. The oracle reads the result from a direct call of `onReceiptIssueReported(evt)`, which returns `{posted:false, reason:"no-board"}` or, on a replay with a card, `{posted:false, reason:"already-posted"}`. It also requires the drained event to be `DONE`. If you want a persisted trace (OpsEvent INFO / AuditLog), say so and I will add a check.
8. **Review facade (CD3).** `member/index.ts` exports `requestReview(ctx,{customerId, refType:"PosSale", refId}) → {token}` and `submitReview({token, rating, body})`. A composed call `requestReview → submitReview` works for a fresh bill. It **cannot** handle a bill whose review the member journey already requested: `requestReview` returns `alreadyRequested` with `token:null`, and the raw token is not stored. V1 requires that case to work (REQUESTED row → NEW, same row). So the builder needs the "smallest additive export" in `member/index.ts`, e.g. `submitReviewForRef(ctx, {customerId, refType, refId, rating, body})`, composed of existing internals. If you rule that a journey-requested bill may answer `ALREADY_REVIEWED`/another code instead, drop that half of V1.
9. **Unknown input keys → `VALIDATION`** (R9 "accept only the token"). Public writes given `{…, saleId}` must refuse with VALIDATION, the same as `receiptPayload`'s strict key check, and must never write to another bill.
10. **Permission code for `sendReceipt` = `PERMISSION_DENIED`** (same as `receipt.ts`, P1.10 CD1). Note P1.16 bills use `NO_PERMISSION`, so the codebase now has both.
11. **Point balance**: `points.balance` must equal `point.getBalance(resolvePointSystemIds(tenantId, memberSystemId)[0], memberId)`. `receipt.ts` today reads `pointBalance` with prisma directly. The brief says "from the point module read". The values agree in the fixture, so the oracle does not police the path.
