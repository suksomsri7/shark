## Findings
- **F1 (Medium · PDPA/UI)** `use-display-publish.ts:166`: keepalive resends every non-idle state including `done`. PayDone stays open until "ขายบิลถัดไป" (`RegisterScreen.tsx:2228`), so every 60 s a new seq rewrites `stateAt` and the display jumps back to "ขอบคุณคุณ<name> · ได้ N แต้ม + receipt QR" for 20 s (`display-shared.ts:174`). This repeats until the next sale and stops showing the QR only after 15 min. The next customer in line can scan the previous customer's `/r/<token>`. Fix: `st.phase !== "idle" && st.phase !== "done"` at :166.
- **F2 (Medium · ruling 3)** `use-display-publish.ts:49` sends the first token of `RegisterMemberItem.name`. The member brief falls back to the memberCode when there is no name/firstName/lastName (`member/profile.ts:566`), so the display shows "สวัสดีคุณM000123". CT2 misses this because its fixture member has a name. Fix: when `name === member.memberCode`, send `firstName: ""`, and have `DisplayScreen` (:123, :200) use the no-name greeting/thanks when `firstName` is empty.
- **F3 (Medium · ruling 13.7 UI)** `DeviceSettings.tsx:814` shows the code only when `!st?.paired`, and `:729` clears `code` when `paired`. "ขอรหัสใหม่" (:834) on a paired device rotates the code but the owner never sees it, so swapping a tablet means revoking first. Fix: render the panel whenever `code && left > 0`, and clear `code` only when `!pendingCodeExpiresAt`.
- **F4 (Low · ruling 3)** `totals.member[].label` is copied as-is (`use-display-publish.ts:64` → `display.ts:416`). The POINTS label "ใช้ 1,240 แต้ม" (`member/wallet.ts:564`) still shows with `showPoints=false`. The VOUCHER label falls back to `res.code` (`wallet.ts:483`), which is a voucher code. Fix: the hook sends `kind`; the server shows a generic label for POINTS when showPoints is off and for VOUCHER when there is no name.
- **F5 (Low · controller note, 13.1)** No code path ever increments `pairFailCount` (wrong codes can't be tied to a row). The "lock at 5" exists only as a check, and the oracle reaches it by setting it directly. `pairLocked` in the UI can never be true in prod. Real protection = 10/min/IP + 10-min TTL + 32⁸ code space. Fine by me, but it should be recorded as accepted rather than "implemented".
- **F6 (Low · perf)** `display.ts:462` runs an `UPDATE … WHERE lastPolledAt < now−30 s` on every poll (usually 0 rows). `r.lastPolledAt` is already loaded, so gate it in JS to skip the statement on 29 of 30 polls.
- **F7 (Low)** `d/page.tsx:33`: if the SSR read returns INTERNAL/throws with a valid cookie, `initial=null`, so the pair form shows and polling never starts. Treat a non-`DISPLAY_NOT_PAIRED` refusal as paired+offline (start the poll).
