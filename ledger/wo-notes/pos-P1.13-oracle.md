## CONTROLLER-DECISION (read first — the oracle encodes my proposal for each; rule before the builder starts)
1. **Contact resolver call (CD4).** `account/service.findOrCreateCustomerContact(ctx, {name, phone?, email?, taxId?, branchCode?, partyId?})` matches partyId FIRST, then taxId+branchCode. It has **no `address` field**. Proposal: for a buyer, the account facade calls it with `{name, taxId, branchCode, email}` and **without partyId** (otherwise the member's party contact, which has no taxId, wins over the buyer — against CD4 "taxId match wins"), and writes `address` on create (an additive `address?` param on the resolver, or a follow-up update inside the account module). S2 asserts: TAX_INVOICE contact has buyer taxId/branchCode/name and `address` containing the buyer address; a second sale with the same taxId but a different name reuses the same contact; exactly one AccountContact with that taxId. The member's partyId is not linked to the buyer contact (if you want it linked, say so — the oracle does not check it).
2. **`findExternalSaleDoc` preference (R8).** Today it filters `docType = TAX_INVOICE_ABB`. Proposal: query `docType IN (TAX_INVOICE, TAX_INVOICE_ABB)`, `refType "PosSale"`, `refId`, `status NOT IN (CANCELLED, VOIDED)`, ordered TAX_INVOICE first. This requires **the TAX_INVOICE doc to carry `refType "PosSale"` + `refId saleId`** (both at pay time and later issue) — the oracle asserts that (S2, L1, Q1 read docs by refType/refId). `posSaleAccountingRef` and `billDetail.accounting` then point at the TAX_INVOICE (R1, P1). ST3 statically requires the word `TAX_INVOICE` (not only `_ABB`) inside `findExternalSaleDoc`.
3. **TAX_INVOICE numbering series.** The account module numbers TAX_INVOICE with `nextDocNo(tx, tenantId, systemId, "TAX_INVOICE", issueDate)` (prefix `TX` by default, `settings-schema REVENUE_DOC_PREFIX`). Proposal: both the pay-time doc and the later-issued doc take `nextDocNo(…"TAX_INVOICE", issueDate)` with `issueDate` = sale paidAt (CD2). The oracle asserts `docNo` starts with `TX` and differs from the ABB docNo (the ABB reuses the POS receipt no). It does **not** pin the exact running number. Note the existing partial unique index `(systemId, sourceDocId) WHERE docType='TAX_INVOICE' AND sourcePaymentId IS NULL` — a later-issued TAX_INVOICE with `sourceDocId = ABB.id` is therefore unique per ABB (good: a DB-level double-issue guard).
4. **Superseded ABB status = `CANCELLED`** (brief wording). `AccountDocStatus` comments say CANCELLED = "cancelled before it had effect (DRAFT)" and VOIDED = "had effect + cancelled". The oracle requires `CANCELLED` + `supersededByDocId`. If you prefer `VOIDED`, ORACLE-EDIT L1 (one literal) — the "live docs" count already excludes both.
5. **Idempotency vs ALREADY_ISSUED (R3).** Proposal: a repeat call with the **same saleId and the same buyer** (kind/name/taxId/branchCode/address/email after parsing) → `{ok:true, docId, docNo}` of the existing doc, no new audit/doc (L2). A call with **a different buyer** on an issued sale → `ALREADY_ISSUED` and nothing changes (L2, L4 — also for sales issued at pay time).
6. **Tax-id errors are all `TAX_ID_INVALID`** — wrong checksum, wrong length, letters and empty (B2, D2, L5). Other buyer field problems are `VALIDATION`. Request rows from P1.11 were validated only as `^\d{13}$`; an existing request with a bad checksum gets `TAX_ID_INVALID` from `issueFromTaxInvoiceRequest`.
7. **Buyer from a P1.11 request row (R4).** Request rows have no `kind`/`source`. Proposal: `kind = taxId starts with "0" ? "JURISTIC" : "PERSON"` (Thai juristic ids start with 0), `source "MANUAL"`, branchCode/email as stored. Q1 asserts kind JURISTIC for a `0…` id; source is not asserted for Q1.
8. **`issuedDocId` vs the existing `accountDocId`.** P1.11 already has `PosTaxInvoiceRequest.accountDocId String?` (always null today). The brief adds `issuedDocId`. The oracle requires `issuedDocId = docId` and accepts `accountDocId` null **or** equal to docId. Recommendation: either keep the brief (add the column, leave accountDocId unused) or ORACLE-EDIT Q1/ST1 to use `accountDocId` and drop the new column.
9. **Where `rememberBuyer` lives.** Top-level input key: `submitRegisterSale(ctx, actor, {…, taxInvoice, rememberBuyer: true})` and `issueFullTaxInvoice(ctx, actor, {saleId, buyer, rememberBuyer?})` / `issueFromTaxInvoiceRequest(…, {requestId, rememberBuyer?})`. Not inside the buyer object (the parser rejects unknown keys).
10. **DBD facade mapping (R5, CD3).** `lookupJuristic` returns `{ok:false, reason}` with Thai strings only. Proposal: `lookupBuyerByTaxId` maps by comparing `reason` to `DBD_REASON` (re-export it from the facade) — `noKey → DBD_NOT_CONFIGURED`, `notFound → {ok:true, found:false}`, `badTaxId → TAX_ID_INVALID`, anything else / throw → `DBD_UNAVAILABLE` — or the account module adds an additive `code` to the failure branch. Stub signature: `deps.lookup(taxId: string) => Promise<DbdLookupResult>` (same as `lookupJuristic`'s first arg). The oracle sets a fake `DBD_API_KEY` while it uses the stub (D1/D3) and unsets it for D2, so both "pre-check env" and "delegate to lookup" implementations pass. `buyer.address` = one string composed from `addressLine, subdistrict, district, province, postcode` (format free; D1 checks it contains the line, the province and the postcode).
11. **DBD permission + rate-limit row.** `lookupBuyerByTaxId` is used by the cashier at pay time → proposal: `pos.sale.create` or `pos.sale.read` (the oracle uses the owner only). Rate limit: 30 calls per rolling minute **per unit**, counted from `AuditLog action pos.taxinvoice.dbd_lookup` (store unitId in the row so it can be counted). Whether the refused 31st call writes an audit row is open — the oracle does not count it. D3 proves per-unit (A2 saturated, A still passes) and the 1-minute window (rows moved back 2 min).
12. **Event on later issue.** The brief says the consumer emits `pos.sale.taxInvoiceIssued` (pay-time path). For later issue / from-request the brief is silent. The oracle asserts exactly one event for the pay-time sale only; it does not assert presence/absence for later issue. Recommendation: emit it on every first issue (same payload) so automations see both.
13. **Refusal message mapper (R9).** The brief says "`refusalMessageKey` extended", but that function returns keys relative to `pos.register` (`errors.pinInvalid`). Proposal: a new pure `taxInvoiceRefusalKey(code) → "taxInvoice.errors.<camelCode>"` (unknown → `taxInvoice.errors.unknown`) in `tax-invoice-shared.ts`; messages in `src/messages/{th,en}/pos.json` top-level `taxInvoice.errors` (the file is the `pos` namespace). `receipt.taxInvoice` (P1.11) stays as is.
14. **`buyerProfileForMember(ctx, {memberId})` has no actor** (brief signature kept). The action wrapper (`buyerProfileForMemberAction`) must check permission (fitness F6.1). Another tenant's member → `{ok:true, profile:null}` or `NOT_FOUND` (both accepted).
15. **Later issue on a partially refunded sale.** R3 allows it; the brief does not say whether the TAX_INVOICE carries the original amounts (CN already references the ABB). Not tested. Recommendation: original amounts, and re-point existing credit notes? — rule before U.
