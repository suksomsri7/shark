## บั๊ก/ช่องโหว่ที่ตรวจแล้ว (ตามกติกา BLUEPRINT §1 "หาบั๊กทุก WO")
- auth: ทุก action ใหม่ผ่าน `loadAccountSystem` + `assertAccountCan(auth, "account.finance.manage")` ก่อนแตะ DB (`finance/actions.ts` ทุกฟังก์ชัน) — ตรวจแล้วด้วย FN11 (guard)
- tenant/system scope: ทุก query ใน finance.ts กรอง `tenantId`+`systemId` ทั้งคู่ — ตรวจแล้วด้วย FN12 (tenant isolation) 2 ทิศทาง
- IDOR: `getFinanceAccountById`/`removeFinanceOpeningEntry`/`updateFinanceOpeningEntry` ทุกตัวเช็ค `financeId` เป็นของ `tenantId+systemId` ก่อนแก้เสมอ (ไม่เชื่อ id เปล่าจาก client)
- เงิน satang integer: ทุกจุด `Math.round()` ก่อนเข้า DB · `MoneyInput`/ฟอร์ม client ส่งสตางค์ล้วนผ่าน hidden field
- idempotency: opening entry (financeId+seq+version) + transfer (transferId) — ปิดช่องโหว่ postManualJV เดิมที่สุ่ม refId ทุกครั้ง (ไม่ idempotent) ที่ transferBetweenFinance เคยมี
- race: FN10 พิสูจน์ code generation ไม่ชนกันเมื่อยิงพร้อมกัน 5 คำขอ (retry บน P2002 ผ่าน partial unique index)
- ห้าม log ข้อมูลลูกค้า: ไม่มี `console.log` ที่พิมพ์ชื่อ/เบอร์/เลขบัญชีลูกค้าในโค้ดใหม่ (log มีแค่ code/ยอดเงินระดับ debug ของ seed)
- input ยาว/ไทย/emoji: จำกัดความยาวช่องด้วย `maxLength` ฝั่ง client + validate ฝั่ง server (`saveFinanceAction`'s `MAXLEN`) — ยังไม่ได้เขียนเทสยิง emoji/ไทยยาวเกินโดยเฉพาะ (จุดที่ยังไม่ครอบคลุมเต็ม — เป็นข้อสังเกตส่งต่อ 9.2)
- migration additive เท่านั้น: ตรวจแล้ว (เพิ่มคอลัมน์ nullable/default + ตารางใหม่ 2 ตาราง + partial unique index เดียว ไม่มี DROP/RENAME)

## จุดสำคัญที่ต้องระวัง (อ่าน gl.ts แล้วพบ)
- 🔴 **`gl.postOpening` เป็น idempotent ต่อ "งวด" ทั้งระบบ** (`AccountOpening#<periodKey>#OPENING`) — ไม่ใช่ต่อบัญชี! ถ้าสร้างบัญชีเงิน 2 บัญชีในเดือนเดียวกันพร้อมยอดยกมา เรียก `postOpening` ซ้ำจะ throw "มียอดยกมาของงวด ... แล้ว" ⇒ **WO นี้จะไม่ใช้ `postOpening` สำหรับ AccountFinanceOpening หลายรายการ** เขียนฟังก์ชันใหม่ใน gl.ts (`postFinanceOpening`) idempotent ต่อ (financeId, seq, version) แทน ตามแบบ `postStockDocument`/`postInventoryGl`
- 🔴 **`alreadyPosted` เช็คแค่ "มีแถวไหน idempotencyKey นี้อยู่ไหม" ไม่สนสถานะ** — ถ้า reverse แล้ว post ซ้ำด้วย refType/refId/event **เดิม** จะโดนเข้าใจผิดว่า "โพสต์แล้ว" (ทั้งที่ REVERSED) ⇒ แก้ไขรายการ = ต้อง bump `version` แล้วโพสต์ด้วย refId ใหม่ (`<financeId>:<seq>:v<version>`) ไม่ใช่ refId เดิม
- `transferBetweenFinance` เดิมใช้ `postManualJV` (สุ่ม refId ทุกครั้ง = ไม่ idempotent) — WO นี้เปลี่ยนไปเรียก `gl.postFinanceTransfer` (ใหม่) แทน โดยผ่าน `transferId` ที่ caller เป็นคนคุม (uuid สร้างครั้งเดียวฝั่ง service ตอนเริ่ม transaction แล้วเก็บใน `AccountFinanceTransfer` ก่อนโพสต์ — กันโพสต์ซ้ำถ้า request ซ้ำ)
- `archiveFinanceAccount` ปัจจุบันไม่เช็คยอด/payments เดือนนี้เลย — SPEC ต้องการปฏิเสธถ้ายอด≠0 หรือมีรายการชำระเดือนนี้
