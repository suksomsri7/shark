## F1 — MAJOR · publish re-checks candidates by `id + published=false` only, so it publishes rows that moved out of the range or out of the publisher's scope (`roster.ts:797-818`)
- Probe `race2.mts` P1b (scope) + `race1.mts` P1 (range).
- Steps: rows A (น้ำฝน, D, morning, huahin) and B (น้ำฝน, D+1, morning, huahin), both unpublished. A side tx holds the key (น้ำฝน, D). manager-branch (unitAccess [huahin]) calls `publishRoster({from:D, to:D+1})`. It picks the candidates outside the tx, then blocks in `lockKeys` on (น้ำฝน, D) (`pg_blocking_pids` shows it). While it waits, owner calls `moveEntry(B, {employeeId: ปุ้ย})`. That call locks (น้ำฝน,D+1)+(ปุ้ย,D+1), so it is not blocked, and it commits with unitId = suanphueng. Then the side tx is released.
- Observed: `{ok:true, published:2}`. B is now **ปุ้ย / suanphueng / published=true**: a huahin manager announced a row of another branch. The event payload says `employeeIds:["น้ำฝน"]` but lists B's id. manager-branch's `listRoster` no longer shows B. In `race1.mts` the same thing happened with `moveEntry(C, {date: D+25})`: C was published at 2027-01-15, outside `[from,to]`, and the payload kept `from/to = D..D+1`. The publish tx also never took the lock on the row's new key (น้ำฝน, D+25) or (ปุ้ย, D+1).
- Expected (R10 "re-select under lock", ruling 4 all-or-nothing, R2 range ops touch only in-scope rows): refuse with `ROSTER_TEXT.publishRace` and roll back, or at least not publish B or C.
- Positive control (same run): the same manager publishing D+1 without the race left the suanphueng row Z unpublished (`published:2` = B and C only). So the normal scope filter works, and only the stale re-check leaks.
- Smallest fix: under the lock, re-count with the full candidate filter: `count({ where: { id: { in: ids }, published: false, date: { gte, lte }, ...entryScopeWhere(scope, unitId) } })`. Use the same `where` in the guarded `updateMany`. A mismatch then rolls back with `publishRace`. This also restores the R11 lock/key invariant, because a row that matches is still on a key we hold.

## F2 — MAJOR · `moveEntry` reads the row before taking the lock and re-checks only `employeeId`/`date`, so concurrent moves lose updates (`roster.ts:499-527`)
- Probe `race1.mts` P2.
- Steps: row R (น้ำฝน, D+5, morning). A side tx holds (น้ำฝน, D+5). M1 = `moveEntry(R, {shiftId: กะบ่าย})` blocks. Then M2 = `moveEntry(R, {date: D+6})` blocks too (2 backends blocked). Both read R as "morning" in `ownEntry` before locking. The side tx is released. M1 gets the lock first (FIFO) and commits afternoon. M2 gets the lock: `cur.employeeId/date` are unchanged, so it passes and writes `shiftId = row.shiftId` (morning) plus the morning `times` taken from its stale read.
- Observed: both return `{ok:true}`. Final row = D+6 **morning 07:00**: M1's shift change is silently reverted. The audit trail shows `move → afternoon` then `move → morning`, which no user asked for.
- Expected (R11 "every write path … takes the keys it touches before reading"): M2 refused with `ROSTER_TEXT.entryChanged`, or M2 keeps M1's shift.
- Smallest fix: inside the tx, re-read the full `ENTRY_SELECT` row under the lock. Refuse `entryChanged` if `shiftId/startMin/endMin/breakMin/crossesMidnight/unitId/published` differ from the pre-lock `row` (simplest: compare all of them). Or recompute `times`/`shiftId` from `cur`. `removeEntry` is safe (its delete is keyed on id + employee + date, and a stale `wasPublished` only affects the audit).

## F3 — MEDIUM · "แก้ N จุด" removed-count is reset by any publish of the system, not of the unit (`roster.ts:750`)
- From reading the code (no probe). `removedSinceLastPublish` takes the latest `hr.roster.publish` audit filtered by `systemId` only. A huahin manager's publish therefore zeroes the suanphueng board's count of removed-after-publish rows, although those removals were never announced. R7 says "since the last `hr.roster.publish` audit of that system/unit".
- A second, smaller issue: the publish audit is written after the commit (`:830`). A remove that lands in that gap gets `createdAt` < the publish audit and is never counted.
- Fix: the publish audit already stores `unitId`. Pick the last publish whose `unitId` is null (all units) or equals the board's unit, and compare per row. Write the publish audit timestamp from `at` (the publish time), not from `now()`.

## F4 — MINOR · copyWeek drops the source row's own time override (`roster.ts:658`)
- R6 says "snapshot = current shift times (Q6; source override times are kept when Q7 allows overrides)", and Q7 allows overrides. The code always uses the shift's current times, so a 14:00–20:00 override on a 07:00–15:00 shift is copied as 07:00–15:00. The §9 Q6 wording ("times re-taken from the current shift") conflicts with R6, and no oracle check covers it. **Controller to rule.** If overrides should be kept: when the source times ≠ the shift snapshot, copy the source times and derive `crossesMidnight`.
