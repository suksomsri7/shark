## ข้อสมมติ/deviation ที่ตัดสินใจเอง (ไม่มีใน spec ชัดเจน)
1. **"ไม่อ้างอิงเอกสารเดิม" ของ CN/DN เดิมถูกบล็อกไว้ทั้งหมด** (`issueDocument` มี `if (!doc.sourceDocId) throw`) — spec §5.2 J ต้องการ radio 2 ตัวเลือกชัดเจน จึงผ่อนกติกาเดิม (คงเหตุผลบังคับไว้) แทนที่จะคงบล็อกไว้แล้วทำ radio ให้กดไม่ได้จริง — เพิ่งพบว่ากฎเดิมขัดกับ spec ตอนอ่านโค้ดละเอียด (ไม่ใช่สิ่งที่ WO บอกไว้ล่วงหน้า)
2. **"IV outstanding" หลังออก CN** — `issueDocument` ของ CN ไม่แตะ `paidTotal`/`status` ของเอกสารต้นทางเลย (ของเดิม เจตนา) ⇒ `doc.grandTotal-doc.paidTotal` ไม่ขยับ ตัวเลข "52,250" ในโจทย์ WO ตรงกับ `creditAvailable()` (เพดานคงเหลือสำหรับ CN ใบถัดไป) ไม่ใช่ `remain` ทั่วไป — ใช้ตัวนี้เป็นเฉลยในข้อสอบ (`qc-acc-v2-adjust.mts` AJ3.11) เพราะเป็นค่าเดียวที่มีความหมาย "ลดได้อีกเท่าไร" จริงในระบบตอนนี้
3. **RPR ไม่มีหน้ารายการ/หน้ารายละเอียดของตัวเอง** (WO 1.5 บันทึกไว้แล้วว่า GOODS_ISSUE_RETURN ไม่มี `[docId]` page) — "สร้างใบส่งคืน" บน PRR จึงเป็น row action ในหน้ารายการใบเบิก (`goods-issue/page.tsx`) แทนปุ่มบนหน้ารายละเอียด (ไม่มีหน้าให้ใส่) · ref-chip ของ RPR ชี้กลับไปหน้ารายการใบเบิก (ไม่มีหน้าเดี่ยวของ PRR ให้ลิงก์)
4. **RPR ไม่มีเพดานยอดเงิน (cap-line)** — PRR/RPR ไม่มีมูลค่า (unitPrice=0 เจตนา ตาม comment เดิม "inventory valuation 🔜") เพดานที่แท้จริงคือ "จำนวนคงเหลือที่คืนได้ต่อสินค้า" (แสดงในตาราง step② คอลัมน์ "คืนได้ไม่เกิน" แทน cap-line บาท)
5. **เหตุผลของ RPR ไม่บังคับ** (ต่างจาก CN/DN/CNR/DNR ที่ ม.86/10 บังคับตามกฎหมาย) — RPR เป็นการเคลื่อนไหวสต็อกภายใน ไม่ใช่เอกสารภาษี จึงเก็บเหตุผลไว้เป็นข้อมูลเสริมเท่านั้น
6. **ไม่ได้ทำ error ปรากฏ inline บนฟอร์มหลังกด "อนุมัติ" ล้มเหลว (server redirect ?err= ที่ DocEditorPage ยังไม่อ่าน)** — เป็นช่องโหว่เดิมของทุกชนิดเอกสาร (ไม่ใช่แค่ CN/DN) ที่มีมาก่อน WO นี้ · แก้เฉพาะจุดที่จำเป็นสำหรับ WO นี้แทน: ป้องกัน "เกินเพดาน" ด้วย client-side guard (`capExceeded` บล็อกปุ่มอนุมัติ + toast) ก่อนจะไปชน server เสมอ ส่วน server ยัง reject จริงเป็นด่านสุดท้าย (ยืนยันด้วย `qc-acc-v2-adjust.mts`) — เสนอแก้ `?err=` แบบทั่วระบบเป็น WO แยก (กระทบทุกชนิดเอกสาร ไม่ใช่แค่ adjust)
