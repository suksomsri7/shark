## 🔴 เหตุการณ์ที่ต้องรายงาน Fable ก่อนอย่างอื่น — migration ถูก apply ลง **prod** โดยไม่ตั้งใจ 1 ครั้ง

**เกิดอะไร**: คำสั่งที่ใบสั่งงานให้ใช้
`set -a; . ./.env.qc; set +a; pnpm prisma migrate deploy`
**ไม่ได้ตั้งค่า env จริง** เพราะ `.env.qc` เก็บ URL แบบ **ไม่ใส่เครื่องหมายคำพูด** และ URL มี `&`
(`…?channel_binding=require&sslmode=require`) ⇒ ตอน `.` (source) bash ตีความ `&` เป็น
"สั่งงานเบื้องหลัง" → บรรทัดถูกหั่นเป็น 2 คำสั่ง (เห็นได้จากข้อความ `[1]- Done DATABASE_URL=…`
ที่ bash พิมพ์ออกมา) ⇒ `DATABASE_URL`/`DIRECT_URL` ไม่ได้ถูก export
⇒ `prisma.config.ts` เลย fallback ไปโหลด `.env` = **branch production (`ep-royal-night…`)**
⇒ `migrate deploy` ลง prod สำเร็จ 1 ครั้ง (ตัว migration ตัวนี้ตัวเดียว)

**ผลกระทบที่ประเมินแล้ว**: migration นี้ additive 100% (ADD COLUMN แบบ NULL/มี DEFAULT · CREATE TYPE ·
CREATE TABLE · CREATE INDEX) ⇒ **โค้ดเก่าที่เสิร์ฟ prod อยู่ไม่พัง** (Prisma ระบุคอลัมน์เองทุก query
คอลัมน์ที่ DB มีเกินไม่มีผล — ตรงข้ามกับเหตุการณ์ 1 ก.ย. ที่ *client* รู้จักคอลัมน์ที่ *DB ไม่มี*)
สิ่งที่ "เริ่มมีผลบน prod แล้วจริง ๆ" มีข้อเดียว: **partial unique index ผู้ติดต่อ** — ตั้งแต่นาทีนี้
prod จะปฏิเสธการสร้างผู้ติดต่อ active ที่มี `(systemId, taxId, branchCode)` ซ้ำ (เดิมสร้างซ้ำได้)
👉 ข้อดีที่ได้ฟรี: index สร้างผ่าน = **prod ไม่มีคู่ซ้ำค้างอยู่เลย** (ไม่งั้นคำสั่งจะล้ม)
   ⇒ ตัด risk "deploy แล้ว build แดงเพราะข้อมูลซ้ำ" ทิ้งได้เลย
👉 `_prisma_migrations` ของ prod บันทึกว่า applied แล้ว ⇒ ตอน deploy จริง `migrate deploy` จะข้ามให้เอง (idempotent)

**ตัดสินใจ**: **ไม่ rollback** — การถอย = DROP COLUMN/TABLE/INDEX บน prod ซึ่งอันตรายกว่าการปล่อยไว้มาก
และของชุดนี้จะขึ้น prod อยู่แล้วตอน deploy · ขอให้ Fable รับทราบและตัดสินอีกชั้น

## A. Enum สถานะ "ยกเลิก" — **ไม่เพิ่ม `VOID`** (ข้อค้นพบ)
ของเดิม `AccountDocStatus` มีครบสองความหมายอยู่แล้ว และโค้ดใช้จริงทั้งคู่:
| ค่า | ความหมาย | หลักฐานในโค้ด |
|---|---|---|
| `CANCELLED` | ยกเลิก **ก่อน** มีผล (ยกเลิกร่าง) | `expense.ts:806` `doc.status === "DRAFT" ? "CANCELLED" : "VOIDED"` |
| `VOIDED` | **เคยมีผล** แล้วถูกยกเลิก (+ reversal JV) | `expense.ts:767` · `service.ts:1649` · คู่กับคอลัมน์ `voidedAt` / `voidReason` |

ป้ายไทยของทั้งคู่ = "ยกเลิก" (`service.ts:65-66`) · ตัวกรอง/posting rule ทั้งระบบเช็คเป็นคู่
`{ notIn: ["VOIDED","CANCELLED"] }` อยู่ **9 จุด**
⇒ เพิ่ม `VOID` = ค่าที่สามที่แปลว่าเรื่องเดียวกัน → ทุกจุดต้องเช็ค 3 ค่าไปตลอด และ `ALTER TYPE … ADD VALUE`
**ถอนคืนไม่ได้** ⇒ จงใจไม่เพิ่ม · บันทึกเหตุผลไว้หัวไฟล์ migration ด้วย
มีข้อสอบเฝ้าไว้แล้ว: `qc-acc-v2-schema.mts` ตรวจว่า enum **ไม่มี** `VOID` (ถ้าใครเผลอเพิ่ม = แดง)

### partial unique index (จุดที่ต้องระวังที่สุดของ WO นี้)
```sql
CREATE UNIQUE INDEX "AccountContact_systemId_taxId_branchCode_active_key"
  ON "AccountContact" ("systemId","taxId","branchCode")
  WHERE "taxId" IS NOT NULL AND "archivedAt" IS NULL;
```
- Prisma `@@unique` ไม่มี `where` ⇒ ถ้าประกาศใน schema จะกลายเป็น unique **เต็มตาราง** = ผู้ติดต่อที่เก็บเข้ากรุแล้ว
  จะกันไม่ให้สร้างรายใหม่ด้วยเลขภาษีเดิม (ผิดเจตนา) ⇒ schema ประกาศแค่ `@@index` + คอมเมนต์ชี้มาที่ migration
- 🔴 **`prisma migrate diff` มองไม่เห็น partial index นี้** (พิสูจน์แล้ว: ลบ index ทิ้งจาก DB → `pnpm drift` ยัง "No difference detected")
  ⇒ ห้ามลบบรรทัดนี้เวลา regenerate diff ในอนาคต · มีข้อสอบเฝ้าแทน (`qc-acc-v2-schema.mts` อ่าน `pg_indexes` ตรง ๆ)
- มีของแบบเดียวกันอยู่ก่อนแล้วในรีโป (`AccountDocument_taxinvoice_source_uniq`) — ไม่ใช่ของแปลกใหม่

### Positive control ของ partial unique index (รันจริง 2 รอบบน DB QC · คืนสภาพแล้ว)
| การกลายพันธุ์ | ผลที่ได้ | แปลว่า |
|---|---|---|
| `DROP INDEX` ตัว partial ทิ้ง | **ผ่าน 59 · ไม่ผ่าน 2** — ข้อ "ดัชนีมีจริง" + ข้อ "DB ปฏิเสธผู้ติดต่อซ้ำ" แดง | ข้อสอบจับได้ว่าดัชนีหาย · และพิสูจน์ว่าคนกันซ้ำคือ DB ไม่ใช่โค้ด |
| เปลี่ยนเป็น unique **เต็มตาราง** (ไม่มี WHERE) | **ผ่าน 58 · ไม่ผ่าน 3** — เพิ่มข้อ "เก็บของเก่าเข้ากรุแล้วใช้เลขภาษีเดิมสร้างใหม่ได้" แดง (+ `pnpm drift` แดง exit 2 เพราะ prisma **เห็น** unique เต็มตาราง แต่ไม่เห็น partial) | เงื่อนไข `archivedAt IS NULL` ถูกทดสอบจริง ไม่ใช่ผ่านฟรี |
คืนดัชนีตัวถูกต้องแล้ว · รันซ้ำได้ **61/61**

## ความเสี่ยง / ของที่ต้องให้ Fable ตัดสิน
1. **🔴 migration ถูก apply ลง prod แล้ว 1 ครั้ง** (ดูบล็อกบนสุด) — ไม่ rollback · ขอการรับทราบ
2. **partial unique index มีผลกับ prod ตั้งแต่ตอนนี้**: การสร้างผู้ติดต่อ active ที่เลขภาษี+สาขาซ้ำจะโยน
   Prisma `P2002` ขึ้นมาที่ `createContactAction` แบบ **ไม่มีข้อความไทย** (หน้าปัจจุบันไม่ได้ดัก) ⇒ ผู้ใช้เห็น error ดิบ
   👉 เสนอ WO ตามเก็บ (เฟส 1 หน้า "ผู้ติดต่อ"): ดัก P2002 → "เลขผู้เสียภาษีนี้มีอยู่แล้ว (สาขา …) — เปิดรายการเดิม?"
   (ข้อดี: index สร้างผ่านบน prod = ยืนยันว่า **ไม่มีคู่ซ้ำค้างอยู่** ⇒ ไม่มีความเสี่ยง build แดงตอน deploy)
3. **`.env.qc` เก็บค่าไม่ใส่ quote** ⇒ `. ./.env.qc` ใช้ไม่ได้ (นี่คือต้นเหตุข้อ 1) — ไฟล์เป็นของ WO 0.1 ไม่แตะ
   👉 เสนอให้ WO ถัดไปใส่ quote + เพิ่มกฎ fitness "สคริปต์ `*acc-v2*` ต้องไม่ลงเอยที่ host prod"
4. **ทางสำรอง `findContactByPhoneLegacyScan` ยังเหลือเพดาน 5000 แถว** — มีชีวิตเฉพาะช่วง "deploy แล้วยังไม่ backfill"
   👉 ลบทิ้งได้เลยหลัง Fable รัน backfill บน prod (จดไว้เป็นหนี้ 1 บรรทัด)
5. **`account.approve.limit` ยังไม่มีโค้ดอ่าน** (ของจริงวันนี้คือ `_maxApproveSatang`) — ตั้งใจ ตามใบสั่งงาน
