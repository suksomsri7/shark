## Findings
- **H1 (Low) `kdsRecall` reads the online order's status before taking the round lock.** `roundVoidedInTx` runs first in the recall transaction (`kds.ts:426`); it reads PosOrder with a plain read (`:453-455`), and only then does `kitchenMoveInTx` take the round lock (`kitchen.ts:301`). Walk:
  - (a) Cancel commits before the read → refused. ✓
  - (b) Cancel commits after the read, and the cancel consumer reaches `lockRoundInTx` while recall holds or is queued for the round → the consumer waits. It then re-reads under the lock, finds the recalled COOKING items and cancels them. ✓ Self-correcting.
  - (c) The cancel commits **and its consumer finishes** in the microseconds between the plain read and recall's round lock → recall then moves SERVED → COOKING on a cancelled order and nothing corrects it. The window is negligible.

  The register path is safe: PosSale FOR SHARE (`:449-450`) holds off the void. Smallest safe alternative: take the round lock first. Expose `kitchenLockRoundInTx` on the facade, call it at the top of the recall transaction, then do the plain PosOrder read. Under the round lock, two recalls on the same round are already serialised, so the plain read cannot deadlock, and any later consumer must queue behind us. K14 covers only the register path. Add an online variant if this is touched.
- **H2 (Low) Two new mark readers decide before they lock MenuItem.** `restoreMenuStockKeep86InTx` (`catalog-legacy.ts:351-354`) and `resetMenuItemDailyStock` (`:201`) both read the mark, then write `isOutOfStock`. Neither locks MenuItem first. Input: table-mode cancel reads "no mark"; a concurrent KDS `setAvailability(false)` (PosProduct → MenuItem FOR UPDATE → mark) commits; the cancel's update then writes `isOutOfStock:false` while the mark remains, so the item stays sellable with a stale "ครัวแจ้ง" mark. Smallest fix: `SELECT … FROM "MenuItem" WHERE id=… FOR UPDATE` before `heldBy86Mark`, the same pattern as H6 and `restoreMenuStockFloorInTx`. Lock order stays ROI/PosProduct → MenuItem.
- **H3 (Low, residual) Heal ghost via a variant link.** The non-MENU branch with `p.stationId` NULL uses the parent's `coalesce(stationSetAt, createdAt)` (`kds.ts:311-312`). Linking a product as a variant of a station-routed parent after the sale (the variant link writer near `catalog.ts:1419-1461`) does not stamp `stationSetAt`, so the next board read can raise one ghost ticket for that earlier sale within 12 h. This is the same class as the "station moved/un-archived" residual in the owner line. Either add "or linked as a variant" to that line, or stamp `stationSetAt` on the row when `parentId` changes.
- **H4 (Nit)** `roundVoidedInTx` refuses whenever status ≠ PAID (`kds.ts:450`), so a fully REFUNDED sale also gets `TICKET_VOIDED` with the message "บิลนี้ถูกยกเลิกแล้ว". That is defensible (nobody is paying for it), but outside ruling 4's letter; it needs a one-line note for P2.6U copy. The `items` parameter is unused (`void items`). The fix2 owner lines (`POS-OWNER-PENDING.md:141-143`) sit under the HF-PP2 heading instead of the P2.6 sections (cosmetic). red3's header says `dirty=0` although `src/`+`prisma/` were checked out at 7d5339c8.
