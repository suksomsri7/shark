## 1. สรุปแนวคิด (ตัดสินใจแล้ว — อ่านก่อนแก้ต่อ)

**เอกสารกลุ่ม = ใบสรุปยอด ไม่ใช่รายการบัญชีใหม่**

| | BN (ใบวางบิล) | CP (ใบรวมจ่าย) |
|---|---|---|
| ฝั่ง / direction | รายรับ · OUT | รายจ่าย · IN |
| relation | `BILL` (กลุ่ม → ใบลูก) | `PAY_GROUP` (กลุ่ม → ใบลูก) |
| ชนิดใบลูก | `INVOICE` | `PURCHASE` · `EXPENSE` · `DEBIT_NOTE_RECEIVED` · `DEPOSIT_PAYMENT` |
| JV ตอนออกเอกสาร | **ไม่มี** (AR ตั้งที่ IV แล้ว) | **ไม่มี** (AP ตั้งที่บิลลูกแล้ว) |
| JV ตอนชำระ | เกิดที่ **ใบลูกทีละใบ**: Dr เงิน / Cr 1100 (แยกตาม IV) | เกิดที่ **บิลลูกทีละใบ**: Dr 2100 / Cr เงิน + Cr 2130 |
| status | derived จากใบลูก | derived จากใบลูก |

### ตัดสินใจที่ต้องรู้
1. **CP โพสต์ JV แบบ "ต่อใบลูก" ไม่ใช่ JV ก้อนเดียว** (WO ให้เลือกได้ 2 ทาง) — เหตุผล:
   ยอดรวมออกมาเท่ากันเป๊ะ (Dr 2100 Σ / Cr เงิน / Cr 2130) แต่ได้เพิ่มมาฟรี ๆ คือ
   (ก) ใบลูกแต่ละใบมีสถานะ/ยอดคงค้าง/50 ทวิ ของตัวเองถูกต้องอัตโนมัติ
   (ข) ใช้ `expense.recordVendorPayment` ตัวเดิม ⇒ ไม่ต้องเขียน posting rule ใหม่ (ลดพื้นที่พลาด)
   (ค) idempotency/void/ภ.ง.ด. ทำงานตามกลไกเดิมทั้งหมด
2. **การจัดสรร = FIFO ตามวันครบกำหนด** (ใบครบกำหนดก่อนได้เงินก่อนจนเต็มยอดค้าง แล้วไหลไปใบถัดไป)
   ไม่ใช่เฉลี่ยตามสัดส่วน เพราะตรงกับวิธีตัดหนี้จริงของ AR/AP · ปิดใบเก่าเป็น "ชำระแล้ว" ได้จริง ไม่ค้างเศษทุกใบ · ตรวจย้อนหลังง่าย
   (ใบที่ไม่มีวันครบกำหนดใช้วันที่ออก · เสมอกันเรียงตามเลขที่ = deterministic)
3. **สถานะกลุ่มเป็นค่าที่คำนวณจากใบลูกเสมอ** (`updateGroupProgress`) ไม่ใช่ตัวนับแยก
   ⇒ จ่ายใบลูกตรง ๆ นอกกลุ่ม / ยกเลิกการชำระ / ออกใบลดหนี้ สถานะกลุ่มก็ตามทันเอง
4. **`ISSUE_STATUS.BILLING_NOTE` เปลี่ยนจาก `ISSUED` → `AWAITING_PAYMENT`** — ตรงกับชุดแท็บ §3 ของ BN
   (รอรับชำระ · เกินเวลารับชำระ · รับชำระแล้ว) และทำให้ปุ่ม "รับชำระ" ใช้ได้จริง (เดิมสถานะ ISSUED ทำให้กดไม่ได้เลย)
5. **ถอด `BILLING_NOTE` / `COMBINED_PAYMENT` ออกจาก `PAYABLE_DOC_TYPES`** ของ `payment.ts`
   🔴 ถ้าไม่ถอด แผงชำระเงินเดี่ยว (WO 1.4) จะรับชำระที่ตัวกลุ่มได้ → `postPayment` สร้าง JV ลอย
   (Dr 2100 ที่ไม่เคยมี Cr 2100 / Cr 1100 ที่ไม่เคยมี Dr 1100) · ตอนนี้เด้ง error ภาษาคนพร้อมบอกทางที่ถูก

## 4. คีย์กันซ้ำของการชำระกลุ่ม

`GRP#<groupId>#<clientKey>#<childDocId>` — ผูกไว้ที่ `AccountDocumentPayment.idempotencyKey` ของ **ใบลูก**
- ประวัติการชำระของกลุ่ม = จัดกลุ่ม payment ตาม prefix `GRP#<groupId>#<clientKey>` (1 กลุ่ม = "ครั้งที่ n" 1 ครั้ง)
- ยกเลิก 1 ครั้ง = void payment ของใบลูกทุกใบใน batch นั้น
- 🔴 **ด่าน idempotency ต้องมาก่อนด่านสถานะ** (บทเรียน WO 1.4 ซ้ำ) — ยิงชุดเดิมหลังกลุ่มปิดแล้วต้องคืนผลเดิมเงียบ ๆ

2. **ยังไม่รองรับในรอบนี้ (จงใจ)**
   - เช็คในการชำระกลุ่ม: รองรับแล้วแต่ผูกทะเบียนเช็ค 1 ใบกับ payment ของ **ใบลูกใบแรก** (ยอดเช็ค = เงินสดรวมของครั้งนั้น) — ยังไม่มีข้อสอบครอบ
   - ค่าธรรมเนียมธนาคารลงที่ **ใบลูกใบแรกใบเดียว** (ค่าธรรมเนียมเกิดครั้งเดียวต่อการโอน 1 ครั้ง) — จดไว้ให้ชัดว่าเป็นการตัดสินใจ ไม่ใช่บั๊ก
   - เอกสารกลุ่มไม่มี "ร่าง": ฟอร์มกด "ออกใบวางบิล/ออกใบรวมจ่าย" = สร้าง+ออกในจังหวะเดียว (บรรทัด = ใบลูกที่ติ๊กไว้แล้ว ไม่มีอะไรให้แก้ต่อ) ⇒ แท็บ "ร่าง"/"รออนุมัติ" ของ BN/CP นับ 0 เสมอ (เหมือนกรณีอื่นที่ WO 1.1 ประกาศไว้)
   - แก้ไขกลุ่มหลังออกแล้ว (เพิ่ม/เอาใบลูกออก) — ยังไม่ทำ · วิธีวันนี้ = ยกเลิกเอกสารกลุ่มแล้วออกใหม่ (ใบลูกกลับมาว่างทันที เพราะเกณฑ์ "กลุ่มที่เปิดอยู่" นับเฉพาะสถานะที่ไม่ใช่ VOIDED/CANCELLED) — มีข้อสอบครอบแล้ว (G13)
   - ปุ่ม "แก้ไข" บนหน้าเอกสารกลุ่มชี้ `…/[docId]/edit` ซึ่งไม่มีจริง **แต่ปุ่มโผล่เฉพาะสถานะ DRAFT** และกลุ่มไม่มี DRAFT ⇒ ไปไม่ถึงลิงก์ตาย
   - **การชำระบางส่วนของกลุ่มไม่มี UI ให้แก้การจัดสรรเอง** — FIFO เท่านั้น (แผงโชว์ตารางจัดสรรให้เห็นก่อนกดบันทึก)

3. **ข้อสังเกตสำหรับ WO ถัดไป**
