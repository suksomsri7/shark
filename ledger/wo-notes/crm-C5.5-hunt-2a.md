### H55-2a-1 · MEDIUM (needs a shop admin setting; platform-wide blast radius) · inbound copy → mail loop through the CRM's own inbound box
- `src/lib/modules/crm/emails.ts:2326-2336` (copyIn send) · `:524` + `:614` (`cleanAddrPatch` for `copyToAddr`, system + per-user) · `:486-490`.
- Sequence: a shop admin (KEY_SETTINGS) saves `copyMode=IN|BOTH`, `copyToAddr=crm+<own key>@shark.in.th` (or another shop's `crm+<key>@`, which is public in every CRM Reply-To). One inbound mail → `ingestInbound` stores it → `transport({to:[copyIn], subject:"[สำเนาจดหมายเข้า] …"})` from `env.EMAIL_FROM` with NO `Auto-Submitted`/loop header → provider delivers to shark.in.th MX → `/api/email/inbound` → new provider Message-ID (dedupe by Message-ID misses) → stored again → copied again … unbounded. Two shops pointing at each other = ping-pong.
- Why existing checks miss it: `cleanAddrPatch` only checks syntax/CRLF; `isSystemMailAddress` (`:424`) exists but is never applied to copy targets; `isAutoSubmitted` (`emails-shared.ts:182`) may flag the copy as auto (noreply local part) but the copyIn branch is not gated by `auto`, nor by "From is our own EMAIL_FROM"; no per-system inbound rate cap.
- Impact: unbounded rows/activities/events in one system + unbounded sends on the shared platform Resend account (suspension = every tenant's mail down). Deliberate by any self-signup shop owner.
- Fix: reject `copyToAddr`/`replyToAddr`/user `copyToAddr` when `isSystemMailAddress()` or `isCrmInboundAddress()`; in `ingestInbound` skip copyIn when `auto` or when From = platform/shop sender or the subject already carries the copy prefix; add `Auto-Submitted: auto-generated` + `X-SHARK-Loop: <systemId>` to the copy and drop inbound mail carrying our loop header; per-system inbound rate bucket.
- Caveat: assumes the platform's Resend sender can deliver to `@shark.in.th` (MX → inbound webhook) — that is the documented BCC-capture path. Code-read only.

### H55-2a-3 · HIGH (cross-lane MEMBER sink) / LOW for CRM inbound (sandboxed) · core `sanitizeHtml` passes any tag written `<tag/attr=…>` verbatim
- `src/lib/core/sanitize.ts:32` `TAG_RE = /<\/?([a-zA-Z][a-zA-Z0-9]*)(\s+[^>]*)?\s*\/?>/g` requires whitespace before attributes. `<svg/onload=alert(document.domain)>` (also `<a/href=javascript:…>`, `<div/onmouseover=…>`, and with `allowImages` `<img/src=x/onerror=…>`) matches none of steps 1-3 (svg is not in STRIP/VOID lists; TAG_RE fails on the `/`) ⇒ left in the output unchanged. Browsers treat `/` as attribute whitespace ⇒ live handler. Text outside matched tags is never escaped, so anything TAG_RE cannot parse survives.
- CRM inbound: `emails.ts:2104` stores it; staff view renders via `renderInboundHtml` (same function) into `<iframe sandbox="" srcDoc>` (`EmailThread.tsx:119-125`) ⇒ no script, no same-origin — holds as defense in depth. Residual: raw `bodyHtml` is returned by `getThread` (REST `/crm` thread read) to API/agent consumers that may render it, and the copyIn mail (`:2333`) forwards it to the copy mailbox.
- Real exploit (outside CRM): `member/privacy.ts:522` sanitizes the shop's privacy-policy body with this function, `member/join.ts:256` → `app/m/[slug]/join/page.tsx:63` → `JoinFlow.tsx:549` `dangerouslySetInnerHTML`. A shop staff/API key that can publish a policy version stores `<details/open/ontoggle=fetch('/api/…',{credentials:'include'})…>` (fires on innerHTML insertion; `<svg/onload>` is less reliable via innerHTML); every visitor of `/m/<slug>/join` on the platform origin runs it — including staff of OTHER tenants and platform admins (same origin as `/app` ⇒ session-riding / cross-tenant takeover).
- Fix: replace the regex sanitizer with a parser-based allowlist (or at minimum: escape every `<` that is not part of a rewritten allowlisted tag — build output from tokens instead of `replace` on the input; treat `[\s/]` as attribute separator); add `<svg/onload>`, `<img/src/onerror>`, `<a/href=javascript:>` to the sanitizer oracle; check `kanban/sanitize.ts` for the same pattern. Code-read only.

### H55-2a-4 · HIGH · unauthenticated ReDoS in the inbound path: `sanitizeHtml` on attacker HTML with no size cap
- `emails.ts:2104` `sanitizeHtml(str(payload?.html), …)` and `:2105` `htmlToText(str(payload?.html))` (when no text part) run on the raw inbound HTML; only cap is the route's 10 MB body (`api/email/inbound/route.ts:20`).
- (a) `sanitize.ts:32` `TAG_RE … (\s+[^>]*)?\s*\/?>`: three overlapping quantifiers over whitespace. Body `<a` + N spaces (no `>`) ⇒ every split of `\s+` / `[^>]*` / `\s*` is tried before failing: ~O(N^3) at that single start position (N=5 000 ≈ 10^11 steps). V8 irregexp has no default backtrack limit.
- (b) `sanitize.ts:115` `<script\b[^>]*>[\s\S]*?<\/script\s*>` (×6 tags): K openers `<script>` with no closer ⇒ each scans to end of input: O(K·n) (10 MB of `<style>` ≈ 10^12 steps).
- Sequence: anyone sends a 20 KB HTML mail `<p>hi</p><a` + 20 000 spaces to `crm+<key>@shark.in.th` (key public in every CRM Reply-To). The inbound function pins a CPU until the platform timeout; the provider sees a timeout and retries ⇒ repeats; on shared-instance compute other requests on that instance stall. No auth, no per-sender/per-system inbound rate limit, the `try` in `ingestInbound` does not help (no throw, just no return).
- Why existing checks miss it: size gate is 10 MB (way above the cubic threshold); sanitizer has no input-length cap and is regex-only by design (D12).
- Fix: cap stored inbound HTML before sanitising (e.g. 256 KB → drop HTML, keep text); rewrite TAG_RE without overlapping quantifiers (`<\/?([a-zA-Z][a-zA-Z0-9]*)([^>]*)>` then parse attrs from the captured group) and do the strip-with-content pass with a linear scanner (indexOf), or a real tokenizer (see H55-2a-3 — same rewrite fixes both). Add a timing oracle: `<a`+20k spaces and 50k `<style>` must sanitise in < 50 ms. Code-read only (complexity derived from the regex, not measured).

### H55-2a-5 · MEDIUM (after P14 sets `CRM_INBOUND_AUTHSERV_ID`; LOW before) · staff lookup by From uses `equals … mode:"insensitive"` (= ILIKE, `_`/`%` are wildcards)
- `emails.ts:2108-2113` `membership.findFirst({ user: { email: { equals: fromAddr, mode: "insensitive" } } })` and `:2117` (`crmEmailUserSetting.fromAddr` same form). The module itself documents that this Prisma form compiles to `ILIKE $1` with `_`/`%` live (`emails.ts:1791-1792`, C5.1-fix F7) — fixed for contacts, not here.
- Sequence: staff of shop S uses `somchai.k@hotmail.com` (public provider whose local part allows `_`). Attacker registers the real mailbox `somchai_k@hotmail.com` and sends genuinely (DMARC pass for hotmail.com) `From: somchai_k@hotmail.com`, `To: crm+<S key>@shark.in.th`, `Cc: <S's customer>`. ILIKE matches the staff row ⇒ `staffClaim` = that staff ⇒ `authResultPass(headers,"hotmail.com")` is TRUE (the A-R is genuine — it proves the attacker's mailbox, not the staff's) ⇒ `direction=OUT`, `sentById=<staff>` ⇒ a forged "sent by our salesperson" mail on the customer's timeline (if bccCaptureEnabled). Before P14: still IN but `staffClaim` set ⇒ `unverifiedShopFrom` + stranger-lead suppression for any `_`/`%` look-alike.
- Why existing checks miss it: C5.4-F's A-R proof binds the From DOMAIN, and the From→staff binding is a pattern match, not equality; `authResultPass` cannot catch it.
- Fix: exact compare — `$queryRaw … lower(u.email) = lower($1)` (as contactByAddress does) or `equals` without `mode` on a lower-cased stored column; same for `crmEmailUserSetting.fromAddr`; grep the CRM for remaining `mode: "insensitive"` equals on e-mail addresses (portal `contactsByTarget` `portal.ts:236` uses the same form ⇒ OTP `isKnown`/login resolution: `_` in a typed e-mail matches another contact's address — the OTP is still mailed only to the typed target, so no session leak, but `resolveAccess` may pick a different contact than the mailbox owner: see H55-2a-6). Code-read only; Prisma ILIKE behaviour taken from the module's own F7 note, not re-verified.

### H55-2a-6 · HIGH (conditional on the ILIKE behaviour above) · portal account takeover via look-alike e-mail (OTP and LINE)
- `portal.ts:236` `contactsByTarget(EMAIL)`: `crmContact.findMany({ email: { equals: target, mode: "insensitive" } })` — used by `requestOtp.isKnown` (`:255`), `verifyOtp.resolveAccess` (`:268`) and `loginWithLine` no-invite path (`:341` same form).
- Sequence (OTP): contact `somchai.k@hotmail.com` has portal access to company X at shop S. Attacker registers the real mailbox `somchai_k@hotmail.com`, opens `/b/<S slug>/login`, requests an OTP for `somchai_k@hotmail.com` → `isKnown` ILIKE-matches the victim ⇒ code is mailed to the TYPED address (attacker's inbox, `customer-session.ts:766-767`) → `portalVerifyOtpAction` → `resolveAccess(target)` ILIKE-matches again → `mintPortalSession(<victim access>)` ⇒ attacker holds the victim's portal session: quotes (accept/reject with any signer name), invoices/pay-links, slips, shared records + private files, company contact list with e-mails/phones (`listContacts`), requests. LINE path: a LINE account whose verified e-mail is the look-alike gets the same via `loginWithLine` (no invite).
- Why existing checks miss it: every gate (access usable, link live, portal enabled, OTP single-use, rate buckets) is about the ACCESS row; the binding "mailbox that received the code == contact's e-mail" is a pattern match, not equality. `_` matches any one char, so any victim address on a provider that lets users register `_` (hotmail/outlook/live/yahoo — very common for Thai SMB contacts) at a differing position is exposed; `%` is not registrable at mainstream providers.
- Fix: exact equality on lower-cased e-mail (`lower(email) = lower($1)` raw, like `contactByAddress`), and re-check in `resolveAccess` that `normEmail(contact.email) === target` before minting; same fix for `loginWithLine`. Oracle: contact `a.b@x.test` with access; OTP for `a_b@x.test` must yield the generic failure. Code-read only.
- Evidence for the ILIKE premise (not re-run by me): `ledger/wo-notes/crm-C5.1.md:54,131` (EXPLAIN showed `equals…insensitive` ⇒ `ILIKE`; "old ILIKE could attach mail to the wrong contact") and `wo-notes/9.2.md:37` (measured: Prisma does not escape `%`/`_`). Other remaining sites of the same form: `contacts.ts:648`, `service.ts:310` (dedupe keys), `emails.ts:610` (user-setting "is a contact" check), `companies.ts:2566` (inbound DOMAIN match — `_` in a registrable domain is not possible, low), `companies.ts:2625`.

### H55-2a-7 · LOW · no inbound rate cap per system / per sender

### H55-2a-8 · LOW · re-invite does not revoke the access's live sessions
