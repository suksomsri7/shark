## Findings
- R-1 MEDIUM src/lib/modules/hr/roster.ts:814-816 — the under-lock re-check of `publishRoster` is `count/updateMany({ id in ids, published:false })` only; it does not re-apply the date range or `entryScopeWhere(scope, unitId)`. A `moveEntry` that commits between the candidate select (:797) and the lock (:812) and moves a row to another unit or outside `[from,to]` keeps `published=false`, so the row is still flipped and its id goes into this publish's event payload. Why: R10 says "re-select under lock"; R2 says range ops by a branch viewer touch only in-scope rows — a unit-A manager can announce a row that is now unit B's (narrow race, no data shown to the viewer). Smallest fix: add `date: {gte,lte}` + `...entryScopeWhere(scope, unitId)` to the `where` of both :814 and :816 (mismatch then already throws `publishRace`).
- R-2 MEDIUM src/lib/modules/hr/roster.ts:517-525 — `moveEntry` reads the row outside the tx (:499), then under lock re-checks only `employeeId`/`date` (:519) and writes `shiftId`+times from the stale read when the shift is not in the patch (:510, :525). A concurrent move that changed only the shift (same employee/day, same lock) commits first and is silently reverted (lost update). Why: §C.8 "guarded updateMany with a count check" — the guard does not cover the fields being overwritten. Smallest fix: select `shiftId,startMin,endMin,breakMin,crossesMidnight` in `cur` and refuse `entryChanged` if any differs from `row` (or put them in the `updateMany` where and keep the count check).
- R-3 MEDIUM src/lib/modules/hr/roster.ts:747-753 + :803 — `unpublishedCount`'s "removed published rows" part resets at the last `hr.roster.publish` audit of the whole system, ignoring that publish's unit/range (R7 says "of that system/unit"); and a removal-only change can never be cleared, because a publish with zero candidates writes no audit (:803). Why: H2.2 board will show "แก้ N จุด" wrongly (publishing branch A hides branch B's pending removals; a lone removal of a published row stays flagged forever). No runtime consumer yet ⇒ not blocking for H2.1. Smallest fix: filter `last` by the publish audit's `after.unitId`/range overlap (already written at :830), and when `cand.length===0` but `removed>0` write the publish audit (or record in notes as H2.2 debt with a controller ruling).
