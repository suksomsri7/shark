**Verdict: MERGEABLE-AFTER-FIXES.** The design, pins and gates hold up. Two concurrency defects (F1, F2) and the open §10.3 p1.1 R.1 fix (CD 3) must land in fix round 1. F3–F5 are small.

## Findings
- **F1 (Medium) Lock-order inversion: daily counter vs MenuItem leads to deadlock.** `restaurant/kitchen.ts:117` upserts `RestaurantDailyCounter` first. The floor consume runs afterwards and takes `MenuItem … FOR UPDATE` (`pos/kds.ts:262` register, `:338` accept → `catalog-legacy.ts:224-226`). Legacy `writeOrderTx` locks in the opposite order: MenuItem (`restaurant/order.ts:229` consumeMenuStock) then the counter (`:241` → `:129`). Trigger: a counted menu item X (stockQty ≠ null) at unit U. A QR, staff or P2.4 table round containing X runs concurrently with a register ticket, or with an online accept containing X. Postgres aborts one transaction (40P01). Victims: `acceptOrder` (`runTx` retries only unique violations, so the user gets INTERNAL), `registerSendTableRound`, the guest QR order. A register ticket that loses is recovered by heal. Smallest fix: in `createKitchenRoundInTx`, after routing and before the counter upsert, run `SELECT id FROM "MenuItem" WHERE id = ANY(menuIds) ORDER BY id FOR UPDATE`. That is a lock only, so restaurant still writes no MenuItem. Alternative: split the function into plan and write so kds.ts consumes before the counter. Add a positive control: two parallel transactions, legacy createOrder against ticketForSale on the same counted item.
- **F2 (Medium) Online order can stall in PREPARING when two stations finish together.** `onlineProgressInTx` reads the round (`kds.ts:374-379`) before `kitchenProgressInTx` takes the PosOrder lock (`order.ts:391`), so `allReady` is computed from a pre-lock snapshot. Under READ COMMITTED: tablet A marks station 1 READY while tablet B marks station 2 READY. Neither sees the other's uncommitted rows, both pass `allReady:false`, both commit. Every item is READY, but PosOrder stays PREPARING and `pos.order.ready` never fires. It only recovers if someone taps served or presses 09 "พร้อม". Fix: take `PosOrder FOR UPDATE` first (e.g. `orders.lockForKitchenInTx` or a raw lock in kds.ts), then re-read the round. Lock order stays items → PosOrder, the same as every other path. The same race can leave `RestaurantOrder` CONFIRMED when the last two stations are served concurrently (`kitchen.ts:293-302`, unlocked read). Low severity, the legacy board has the same race; it can be noted rather than fixed.
- **F3 (Low) Floor-at-0 restore inflates the counter.** Consume clamps (`catalog-legacy.ts:229`), but restore adds the full item qty (`:250`). Example: ครัวซองต์ stockQty 1, register sells ×2 → counter 0 and 86. The sale is voided before cooking, so the counter becomes 2: one phantom unit, which leads to an oversell. Fix (needs a ruling, because the item field set is pinned): record the clamped quantity, or at minimum cap the restore at `dailyStockQty`. A restore also clears an `isOutOfStock` that KDS set while the counter was 0, which leaves a stale `PosAvailabilityMark` listed in the board's `eightySix`.
- **F4 (Low, perf) `ticketForSale` costs every POS sale.** It runs in every register submit, including units with no stations. Cost: the sale and its lines are read, `stationHints` runs, then a transaction opens with FOR SHARE, an advisory lock and a station query, and only then returns NO_STATIONS (`kds.ts:234-247`, `kitchen.ts:98-99`). That is about 6 round-trips added to submit latency in plain shops. Fix: check for non-archived stations before reading the sale and before opening the transaction.
- **F5 (Low) Midnight drop-off.** The board, expo and backlog read only today's Bangkok bizDate (`kds.ts:76, :205`; per R7). A round sent at 23:58 that is still COOKING disappears from the KDS at 00:00, and auto-accept stops counting it. This follows the spec, but it should be raised with the owner/P2.6U: include non-SERVED tickets of the previous bizDate.
