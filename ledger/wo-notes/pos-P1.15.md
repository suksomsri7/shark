## Contract summary for P1.15U
**Actions** (`staff-pin-actions.ts`, args always `{systemId, unitId, deviceId?}` + below; session must sell at the unit):
- `setStaffPinAction({userId, pin})` → `{ok:true}` | `VALIDATION` (not `/^[0-9]{4,6}$/`) · `WEAK_PIN` (0000 1234 1111 123456 000000) · `PIN_TAKEN` (same PIN at this unit; message names nobody) · `PERMISSION_DENIED` (not self and no `pos.staff.manage`) · `NOT_FOUND` (target cannot sell here).
- `verifyStaffPinAction({deviceId, pin, userId?})` → `{ok:true, userId, role, staffToken, expiresAt (ISO, +12 h)}` | `PIN_INVALID` · `PIN_LOCKED` · `DEVICE_REVOKED` · `VALIDATION`. Audit `pos.staff.pin_verified` (actorId = userId, after `{userId, unitId, deviceId}`) on success only.
- `unlockStaffPinAction({userId})` → `{ok:true}` | `PERMISSION_DENIED` · `NOT_FOUND`. Audit `pos.staff.pin_unlocked`.
- `listStaffForDeviceAction()` → `{ok:true, items:[{userId, name, role, hasPin, shift:{id, openedAt}|null}]}` (members with `pos.sale.create` at the unit, sorted by name) | `DEVICE_REVOKED`.
**New input keys:** submit `staffToken · managerPin · managerUserId · heldCartId` · `holdRegisterCartAction({cart,label,staffToken})` · `recallHeldCartAction({id,staffToken})` · `openShift({…, staffToken})` · `voidSaleAction({…, deviceId?, managerPin?, managerUserId?})` · `refundSaleAction({refund:{…, managerPin?, managerUserId?}})`.
**Results:** `{ok:false, code:"APPROVAL_REQUIRED"|"PENDING_APPROVAL", message, requestId}` from void/refund/submit (submit adds `heldCartId`) — type `PosApprovalRefusal` (register-shared); void/refund unions also carry `PIN_INVALID|PIN_LOCKED|DEVICE_REVOKED`. All refusals are data, Thai `message`; the screen maps codes with `refusalMessageKey` (keys above, under `pos.register`).
**Token lifecycle:** stateless `base64url({u, e, v}).HMAC-SHA256` keyed `pos-staff-token:v1:<SESSION_SECRET>` over `tenantId|unitId|deviceId|body`; 12 h; dead when expired, used on another device/unit/tenant, edited, after `setStaffPin` for that user, after the user loses `pos.sale.create` at the unit, or when the device is revoked. With a token, seller, held-by, recalled-by, shift-opener, permissions and the discount cap are the token user's (ruling 2); an invalid token never falls back to the session user.
**Lock-out:** with `userId` (or `managerUserId`) only that row is checked and a miss counts on it; 5 consecutive misses ⇒ `lockedUntil = now + 15 min`; success resets; an expired lock restarts the count at 1. Without an id, every row of the unit is matched and nothing is counted (ruling 1).
**Discount cap:** membership `pos._maxDiscountBp` wins (MANAGER/STAFF), else `maxBpByRole[role]` (STAFF canonical, CASHIER alias; defaults STAFF 1000, MANAGER/OWNER 10000 = no limit); invalid settings ⇒ defaults. `overrideRequiresPin` dropped (ruling 3). `registerSellerLimits(actor, unitId, caps?)` + new `registerDiscountCaps(ctx)` for the page.
**Over-cap order in submit:** ① `heldCartId` whose approval is APPROVED and unused, discount ≤ approved bp ⇒ passes, claimed atomically at submit (one sale); used/over/not approved ⇒ `DISCOUNT_EXCEEDS_LIMIT`, no new request (ruling 5) · ② `managerPin` ⇒ manager's cap must cover (else `DISCOUNT_EXCEEDS_LIMIT`), wrong ⇒ `PIN_INVALID` · ③ POS_DISCOUNT_OVER policy ⇒ held cart (label "รออนุมัติส่วนลด", heldBy = seller, quoted without cap) + request (entityId = heldCartId, amount = discount satang) ⇒ `APPROVAL_REQUIRED` · ④ `DISCOUNT_EXCEEDS_LIMIT`. Audit `pos.discount.override` `{saleId, byUserId, forUserId, discountBp, via, requestId?}` (actorId = approver) once per new sale.
**Approval (rulings 9–13):** one open request per bill/held cart (PENDING, or APPROVED not yet executed by the consumer). POS_VOID entityId = saleId, after a closed one `saleId:<n>`; POS_REFUND `<saleId>:<refund key>`; amount = bill total / refund total (computed by a dry-run "plan" pass of the refund tx). Snapshot `PosApprovalPayload.payload` = `{ref, entityId, requestedById, amountSatang, unitId, systemId, title, …}` (void: reason/key/receiptNo/deviceId; refund: lines/payMethods/reasonCode/reason/key/deviceId; discount: heldCartId/discountBp/discountSatang/subtotal/grand) + `outcome` once executed. Policies bind every role (ruling 10). Manager PIN (with `pos.sale.void`/`pos.sale.refund`) executes immediately even with a policy, also for a requester who only has `pos.sale.create` (ruling 11), cancels the open request of that bill and writes `pos.approval.pin_override {requestId|null, action, byUserId, forUserId}`; the void/refund audit has actorId = manager and `requestedByUserId`.
**Consumer:** approved POS_VOID ⇒ `voidSale(…, {actorUserId: decider, reason, idempotencyKey: cashier's key, via:"approval", requestId, requestedByUserId})`; POS_REFUND ⇒ `refundApproved` key `approval-<requestId>`, off-shift (`shiftId null`, ruling 13), doc soldBy = requester, audit actor = decider; POS_DISCOUNT_OVER ⇒ `PosHeldCart.approvedRequestId` set once (null-guarded). Rejected ⇒ nothing. Decider = requester ⇒ ops WARN `pos.approval.self_approved_blocked`, nothing executed, request untouched, snapshot closed `BLOCKED_SELF_APPROVAL`. Permanent failures ⇒ WARN + `FAILED:<code>`; only transient errors throw (first step of the chain).
**`voidSale` audit** — `VoidSaleAudit` gained optional `via`, `requestId`, `requestedByUserId` (additive; contract snapshot diff = one caller line, `pos-approval-consumer.ts`, regenerated with `--update-pos-contract`).

2. **`ORACLE-EDIT? P1.9-ST8`** — ST8 asserts "no model PosStaffPin (PIN belongs to HR)". P1.15 (brief R1/CD1, controller-approved) creates exactly that model, so ST8 is red by design on this branch. I did not edit qc-pos-p1.9. Proposed edit: drop the first condition of ST8 (keep "PosShift has no pin column" and "shift.ts does not read PIN/HrEmployee", both still green — shift.ts gets the token user through `staff-pin.ts`, no `pinHash` in shift.ts).
3. `pinVersion` = a hash of the PIN row's `pinHash` (salt changes on every `setStaffPin`), not `updatedAt` as CD2 wrote: Prisma bumps `updatedAt` on every failure count/unlock, so any wrong PIN typed for a user would log that user out. The effect CD2 wanted (a new PIN kills old tokens) is unchanged and tested by TK5.
4. A missing snapshot at approval time (crash between `submitForApproval` and the snapshot insert) ⇒ consumer WARN `pos.approval.payload_missing`, nothing executes; the next retry of the same action re-attaches a snapshot to the still-PENDING request.
