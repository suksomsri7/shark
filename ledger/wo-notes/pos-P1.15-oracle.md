## CONTROLLER-DECISION (read first — the oracle encodes my proposal for each; rule before the builder starts)
1. **Whose row counts a failed PIN?** R2 matches the PIN against *all* rows of the unit, so a wrong PIN matches no row and cannot be counted "per PIN row". Yet R2 (lock-out after 5) and DC3 (wrong `managerPin` ⇒ `+failedCount`) both need it. **Proposal:** `verifyStaffPin` takes an optional `userId` (13B: the staff member tapped in the right-hand list), and `managerPin` comes with `managerUserId` (the manager picked on the sheet). With an id, only that row is checked, and failures count on it. Without an id, all rows are matched and a miss counts on nothing (an unattributed brute-force throttle per device is out of scope here, so please confirm that is acceptable). The oracle always sends `managerUserId` and uses `userId` in PN6. If you rule "no ids", I will rewrite PN6/DC3/AP10 by ORACLE-EDIT.
2. **Discount cap with a staff token.** R4 does not say whose cap applies when the session is the owner but the token is a cashier's. Applying the owner's cap would let the lock-screen switch bypass the cap. **Proposal:** the cap (and `forUserId` in the override audit) follows the token's user. DC1(c) encodes this.
3. **`maxBpByRole` key `CASHIER`.** The `Role` enum is `OWNER | MANAGER | STAFF`, and no CASHIER role exists. **Proposal:** the canonical key is `STAFF`, and `CASHIER` is read as an alias. DC5 writes both keys, so either reading passes. DC6 sets `MANAGER` only. Also, `overrideRequiresPin` has no defined meaning when false, so the oracle never sets it to false. Please define it, or drop the key.
4. **Membership `pos._maxDiscountBp` vs settings.** Today `regMaxDiscountBp` reads the per-membership permission first. **Proposal:** the membership value still wins, and settings only replace the constant fallback. No check depends on this, because the fixture sets no such permission.
5. **Second use of a consumed approved cart ⇒ `DISCOUNT_EXCEEDS_LIMIT`, not a new auto-request.** With a `POS_DISCOUNT_OVER` policy, a plain over-cap submit auto-holds and returns `APPROVAL_REQUIRED` (AP8). A submit that carries a **consumed** `heldCartId` (AP9, the brief's "second use") must refuse with `DISCOUNT_EXCEEDS_LIMIT` and create no request. A submit with `heldCartId` and a **larger** discount than approved also gets `DISCOUNT_EXCEEDS_LIMIT` and does not consume the approval. AP9 also replays the approved event twice after consumption and requires that the replay does not re-arm the cart.
6. **Fitness edge `pos→approval`.** `scripts/fitness.mts` ALLOWED_EDGES has no `pos→approval` (inventory, hr, account, member, point, voucher, crm and kanban each have their own). `voidSaleByActor`, `refundSale` and `submitRegisterSale` live in `modules/pos` and must reach `submitForApproval`/`cancelRequest`/`requestStatuses`. **Proposal:** a one-line append of `"pos→approval"` (hot file, smallest hunk), with POS importing only the facade `@/lib/modules/approval`. AP0 checks both.
7. **`resolvePolicy` is not in the approval facade.** The facade exports `submitForApproval · cancelRequest · lastDecisionOf · requestStatuses`. `submitForApproval` already resolves the policy (it returns `autoApproved` when none matches), so void and refund can compose from it. Discount-over is harder: the held cart must exist before the request (entityId = heldCartId), so without `resolvePolicy` the builder must hold first and discard on `autoApproved`. **Proposal:** add `export { resolvePolicy } from "./service"` to `approval/index.ts` (index only — `service.ts` stays untouched per CD6). The oracle does not check this, so either approach passes.
8. **Register POS entity types in `approval/labels.ts` (+ the allowlist in `approval/actions.ts`).** Without them the owner cannot create a POS policy at `/app/settings/approval`, which makes R5 unreachable in the product (the same latent bug the file records for `AccountDocument`). Notifications would also show the raw `POS_VOID`. **Proposal:** add `POS_VOID` "ยกเลิกบิล (POS)", `POS_REFUND` "คืนเงิน (POS)" and `POS_DISCOUNT_OVER` "ส่วนลดเกินสิทธิ์ (POS)". AP0 checks the labels. Drop that sub-check if you rule labels are out of scope.
9. **Core idempotency = one request per entity *forever*.** `submitForApproval` uses `idempotencyKey = approval-<entityType>-<entityId>` and returns the existing row whatever its status. So (a) after a REJECTED or CANCELLED void, a retry gets the old closed request back, and (b) with `entityId = saleId`, a second partial refund of the same bill after the first was approved can never open a new request. **Proposal:** POS_VOID keeps `entityId = saleId`. On retry, the POS reads the status: PENDING ⇒ `PENDING_APPROVAL`, and closed ⇒ please rule between "refuse with `APPROVAL_REQUIRED` + new entityId `saleId:<n>`" and "manager PIN only". POS_REFUND uses `entityId = <saleId>:<refund idempotencyKey>`. The oracle accepts either for the refund: it finds requests by `entityId startsWith saleId` and requires exactly one open request per bill (AP7 retry ⇒ `PENDING_APPROVAL` with the same `requestId`).
10. **Does a policy also bind managers/owners voiding their own bill, and can a manager approve their own request?** The core does not look at the requester. This is not tested. Please rule on it (CRM C3.3 blocks self-approval for commissions with `lastDecisionOf`).
11. **Requester permission.** The oracle keeps R7 "callers unchanged". A requester without `pos.sale.void` gets `NO_PERMISSION` and no request (AP2). Whether a valid `managerPin` lets a requester without the permission void (a manager authorising at the cashier's device) is not tested. Please rule on it.
12. **Message keys (R9).** `refusalMessageKey()` returns keys relative to `pos.register` (`errors.*`), while R9 names `pos.staff.errors.*` and `pos.approval.errors.*`. next-intl cannot leave a namespace. PN8 accepts a key that resolves under either `pos.register.<key>` or `pos.<key>` in `src/messages/{th,en}/pos.json`, as long as all 7 are distinct and none is `errors.unknown`. `messages/*` counts as a hot file, so use the smallest hunk.
13. **Refund approval and the shift.** The approved refund runs later inside the consumer. The snapshot must carry the `deviceId`, so `refundSale` can find the open shift of that device. If that shift has closed by then, the result is undefined. The oracle approves immediately, so this is untested. Please rule on it (suggestion: drop `shiftId`, with the refund booked off-shift like other non-register refunds).

## Drift (brief vs code as built on e4d47b5b)
- `voidSale(tenantId, unitId, saleId, audit?: VoidSaleAudit)` with `VoidSaleAudit = { actorUserId, reason, idempotencyKey? }`. The brief writes `voidSale(…, { audit:{ byUserId, via, requestId } })`. Adding `via?` and `requestId?` to `VoidSaleAudit` is additive. The oracle checks only the AuditLog row: `action "pos.sale.void"`, `actorId = decider`, `after.via = "approval"`, `after.requestId`. The audit also needs a `reason` from somewhere, so the void snapshot should keep the cashier's reason (`PosApprovalPayload` kind `POS_VOID`).
- Held cart column is `heldByUserId` (the brief says held-cart `byUserId`). The oracle checks `heldByUserId` and, on recall, `recalledByUserId`.
- `ApprovalRequest` has **no payload and no title column**, so CD3 applies: `PosApprovalPayload` is required (AP7 checks the refund snapshot). The 21A title/subtitle ("ยกเลิกบิล R…", "<staff> · <device> · <n> นาทีที่แล้ว") can only be stored in `PosApprovalPayload.payload` (e.g. `{title, subtitle, …}`). It is untested and belongs to the UI half.
- `holdRegisterCart` and `recallHeldCart` call `quoteRegisterCart` with the actor's cap, so an over-cap cart cannot be held through the public path today. The auto-hold in R4 needs an internal hold that skips the cap, and the recall of an approved cart returns `ok:true` with a refused `quote` (the oracle checks only `ok`).
- `quoteRegisterCart` has no `managerPin`, so the register cannot show over-cap totals before the PIN. The oracle computes `expectedGrandTotalSatang` itself (VAT NONE). Flagging for the U half.
- R2 "DEVICE_REVOKED (P1.10 guard)" — `posDeviceRevoked` treats an unregistered device as allowed (same as `openShift`). The oracle registers all three devices.
- Role enum is `OWNER|MANAGER|STAFF`. `verifyStaffPin.role` is checked as `"STAFF"` / `"MANAGER"`.
- `refusalMessageKey` lives in `register-shared.ts` (pure); see CD-12.
