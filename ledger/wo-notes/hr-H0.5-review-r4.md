## Findings (ranked)

### R1 — MINOR — `above: limit` guard on the refused-call refund can leave a phantom slot (silent lock, no audit)
- `src/lib/modules/hr/pin.ts:195` (`refundRateLimitDb(callerBucket, vC.windowStart, { above: 10 })`) and `:201` (`{ above: 120 }`). Guard: `src/lib/core/rate-limit-db.ts:103` (`AND "count" > ${above}`).
- How it happens (caller bucket): 9 wrong slots are held. Correct call S consumes and gets 10, ok. Concurrent call R consumes and gets 11, refused. S refunds: 11 → 10. R refunds with `above: 10`: `10 > 10` is false, so it does nothing. The bucket stays at **10 with only 9 wrong attempts**, so the caller is locked for the rest of the 10-minute window. No call ever got `count === 10` on the failure path, so **no `hr.pin.locked` row** is written. The same interleaving on the tenant bucket (119 wrong + 1 pending success + 1 refused) blocks the shop for the rest of the 60 s window, with no `hr.pin.tenant_limited` row and no OpsEvent WARN. That is the silent tenant trip G3 asked to remove.
- Impact: the error is always on the strict side. No leak and no extra comparisons. It needs a correct and a refused call to overlap at the ceiling, so it is rare. It can also show up as an S10.2 flake (`callerBucket=10`, `lockedRows=0`).
- Why the guard isn't needed: every consume is matched by at most one refund of the same request, and the `windowStart` equality pins that refund to the same window. So `count` is always exactly the number of slots not yet refunded, which is ≥ 0. Neither refund can push the count below the true number of held wrong slots.
- Smallest fix: drop the `{ above: … }` argument at `pin.ts:195` and `:201` (use the default `above: 0`). Optionally drop the `above` option from `refundRateLimitDb` later. No oracle change is needed: S10.1/S10.2/S10.6 still hold, because they assert ≤ ceilings and "refused calls consume nothing".

### R2 — NOTE — a DB error during lookup keeps both slots (counted as a failure)
- `pin.ts:268-273` (`appSystem.findMany`), `:278-284` (`findRows`), `:311-322` (legacy upgrade `throw e`). None of these release before throwing. The exception leaves the slots counted as failures without the audit check. The error is on the strict side. Only `hashPin` errors release (`:262`).
- Optional fix: wrap the lookup section in `try { … } catch (e) { await release(); throw e; }`.

### R3 — NOTE — audit dedupe is check-then-write (not atomic)
- `pin.ts:212-233` / `:235-246`. Two failure-path calls can both see `count === limit` in one window only after a refund in between (the S10.2 shape). If their `auditedSince` lookups overlap, both write a row. This needs refund-reordering plus overlapping lookups. Acceptable: the audit is informational. The builder's documented converse case (a lock row written, then the count drops back to 9) is also acceptable. Together with R1, these are the only S10.2 flake sources.

### R4 — NOTE — refund matching relies on an exact `windowStart` round trip
- `rate-limit-db.ts:74,78` returns `row.windowStart` from `$queryRaw`. `:103` matches it with `"windowStart" = $ws`. The column is `DateTime` (timestamp(3) without time zone, `prisma/schema/core.prisma:484`), and it is written from a JS `Date` with ms precision. The value round-trips exactly while the session TimeZone is UTC (Neon default). The existing `<= ${now − windowMs}` comparison already depends on that. If it ever broke, refunds would match nothing. The failure is strict, with no leak, but successes would start consuming the limit. S10.3 green on QC4 proves the round trip there. Nothing to fix. This is a note for whoever changes the column type.

## What I verified and found correct
- **Count-first order.** Caller bucket first (`pin.ts:193`), then tenant (`:198`). Each is one atomic `INSERT … ON CONFLICT … RETURNING` (`rate-limit-db.ts:61-70`). The lookup runs only when both accept (`:194-205`). Refused at caller ⇒ refund caller only. Tenant untouched ⇒ returns `limitedText` (`:194-197`). Refused at tenant ⇒ refund tenant slot plus the caller slot (`:199-205`). Burst bound: wrong slots are never refunded, so at most `limit` wrong comparisons per window, regardless of concurrency. This closes G1.
- **Window rollover between consume and refund.** On reset, `windowStart` becomes the new `now`. That is ≥ the old start + `windowMs`, so it is never equal to the old value. A refund carrying the old `windowStart` matches 0 rows (`rate-limit-db.ts:103`) and **cannot decrement the next window's count**. A row deleted by sweep or reset also matches nothing.
- **Fail-open.** `windowStart` is undefined ⇒ `refundRateLimitDb` returns early (`rate-limit-db.ts:98`). `count` is undefined ⇒ `count === limit` is false, so no audit and `auditedSince` is never called with an undefined `since`. A refund DB error is swallowed, with a WARN (`:104-108`).
- **Success refund on every success path.** `okOf()` releases both buckets (`pin.ts:291-294`) and is the only way to return `ok:true`: hash hit (`:296`), re-check after an empty legacy read (`:303`), legacy upgrade including the "another request upgraded first" branch (`:315-319` → `:324`). `PinNotConfigured` releases (`:258-260`), as does any other `hashPin` error (`:262-263`). Bad format is a failure by design (`:250-253`). No `return` between consume and lookup skips a needed refund.
- **Audits.** `auditedSince` uses `tenantDb({tenantId}).auditLog` (AuditLog is tenant-scoped, `src/lib/core/scope.ts:46`) plus an explicit `tenantId`. `createdAt ≥ windowStart` is served by `@@index([tenantId, createdAt])` (`core.prisma:231`). It runs only on the failure path when `count === limit` (`pin.ts:224,235`). `hr.pin.locked` payload `{callerKey, count, windowSec}` (`:231`), `hr.pin.tenant_limited` `{count, windowSec}` (`:243`): no PIN, no hash, no employee id. `targetId` is unset and `actorType` is SYSTEM. The OpsEvent WARN carries `{ tenantId }` and a fixed Thai text containing only numbers (`:245`). `.catch` is used, and `writeAudit` never throws (`src/lib/core/audit.ts:39`).
- **callerKey.** `CALLER_KEY_RE = /^[A-Za-z0-9:_.-]{1,128}$/` (`pin.ts:45`) is byte-equal to the ruling and anchored (no `m` flag, so `$` does not accept a trailing `\n`). It is applied after `trim()` (`:188-189`), after the tenantId check and before any DB call. Key layout `hr-verifypin:<t>` / `hr-verifypin:<t>:<k>` (`:190-191`) cannot collide with another tenant (cuid has no `:`).
