## 4. ⚠️ บั๊กที่เจอระหว่างพัฒนา + วิธีแก้ (สำคัญ — ใช้เวลาไล่มากที่สุดของ WO นี้)

### 4.1 การ์ดที่ลากไปตกในวันที่มีการ์ดอยู่แล้ว "หาย" จากช่องปลายทาง (แต่ข้อมูลถูกต้อง)

**อาการ**: ลากการ์ดจากถาดไปวางบนวันที่ **มีการ์ดอยู่แล้ว 1 ใบ** → เห็นถาดลดจำนวนถูกต้อง (optimistic) แต่ช่องวัน
ปลายทางยังโชว์แค่การ์ดเดิม 1 ใบ ไม่เห็นใบใหม่ ทั้งที่ `setCardDueFromCalendar` เขียน DB ถูกต้อง (`dueAt` ตรงวัน
ที่ลาก, activity `CARD_DUE_SET` ถูกสร้าง) — ทดสอบลากลงวันที่ **ว่างเปล่า** (0→1) กลับเห็นถูกต้องทันที

**วิธีสืบ**: เขียนสคริปต์ debug ชั่วคราว (`scripts/pending/debug-k22-*.mts` — ลบทิ้งหมดแล้วก่อนส่งงาน) ทำ
1. ยืนยันด้วย `page.evaluate` อ่าน `innerHTML` ของช่องวันโดยตรง → **DOM มี `<div data-testid=calendar-card-chip>`
   ทั้งสองใบจริง** `opacity:1` ไม่ถูกซ่อน ไม่ dimmed
2. ใส่ `console.log` ใน state updater ของ React → ยืนยัน `days["2026-09-02"].cards.length` เป็น **2** ทั้งตอน
   optimistic update และหลัง `useEffect` sync กับ prop ใหม่
3. ทดสอบลากลงช่องว่างเปล่า (0→1) → ถูกต้องทันที พิสูจน์ว่า service/state ไม่ผิด ปัญหาอยู่ที่ **การ growing ของ
   ช่องที่มีเนื้อหาอยู่แล้ว (1→2) เท่านั้น**

**สาเหตุจริง**: ช่องวัน (`data-testid=calendar-day`) อยู่ใน CSS Grid แถวสูงแบบ "auto" (ไม่ตั้งสูงตายตัว) —
เมื่อ React แพตช์ children ของโหนดเดิม (เพิ่ม `<DayCardChip>` ใบที่ 2 เข้าไปในโหนด `<div>` เดิม) เบราว์เซอร์
(Chromium) ไม่คำนวณความสูงของแถวกริดใหม่ให้ถูกต้องในบางกรณี — องค์ประกอบมีอยู่จริงใน DOM แต่ไม่ถูกจัด
เลย์เอาต์/วาดใหม่จนกว่าจะมีการโหลดหน้าใหม่ทั้งหมด (SSR สด ๆ ไม่เจอปัญหานี้เพราะไม่มีการ "แพตช์ในที่")

**วิธีแก้ (2 จุด ใน `CalendarView.tsx`)**:
1. เอา `flex-1 overflow-hidden` ออกจาก div ที่ครอบรายการการ์ดในช่องวัน (ปล่อยให้สูงตามเนื้อหาไปเลย เหมือน
   มะ็อกอัพ 05 ที่แถวสูงไม่เท่ากันตามจำนวนการ์ด)
2. **(ตัวที่แก้ได้จริง)** ผูก `key` ของ `<div data-testid=calendar-day>` กับ `` `${dateKey}:${cardCount}:${externalCount}` `` แทนที่จะผูกแค่ `dateKey` เฉย ๆ — บังคับ React ถอด+สร้างโหนดใหม่ทั้งช่องทุกครั้งที่จำนวนการ์ด
   เปลี่ยน (ไม่ใช่แค่แพตช์ children ในโหนดเดิม) → Chromium คำนวณ layout ใหม่ทั้งหมดแน่นอน

ยืนยันด้วยภาพจริงแล้ว (`calendar-drag-from-tray-desktop.png` เห็น 2 บรรทัดถูกต้อง) — ตรวจซ้ำ 2 รอบติดกัน
(oracle + regressions รันซ้ำ) ไม่มีการถดถอย

### 4.2 ลากทับตัวหนังสือหัวข้อการ์ด → เบราว์เซอร์เลือกข้อความแทนที่จะลาก

**อาการ**: ภาพแรกที่ถ่ายตอนลาก เห็นทั้งแถบกลายเป็นพื้นฟ้า (เหมือนไฮไลต์เลือกข้อความ) ครอบทั้งหัวข้อ ป้าย และ
หัวคอลัมน์วันในแถวเดียวกัน — เป็นพฤติกรรม "text selection" ของเบราว์เซอร์ตอน mousedown+ลากบนก้อนข้อความ
โดยตรง ไม่ใช่บั๊ก React

**วิธีแก้**: เพิ่ม `e.preventDefault()` ที่ต้นฟังก์ชัน `onCardPointerDown` (ก่อนเช็ค threshold) + ใส่
`userSelect: "none"` (+ `WebkitUserSelect`) บนการ์ดที่ลากได้ทั้งสองจุด (ถาดและช่องวัน)

### 4.3 ถาดบนมือถือแคบ 230px เท่าเดสก์ท็อป ทำให้รายการวันต่อวันไม่ขึ้นเลย

**อาการ**: `UnscheduledTray` ฮาร์ดโค้ด `width: 230` ไว้ในสไตล์ตัวเอง โดยไม่แยกกรณีมือถือ — จอมือถือ (390px)
จึงเห็นถาดแคบ ๆ ชิดซ้าย ส่วนพื้นที่ที่เหลือ (และรายการวันต่อวันที่ควรอยู่ **ใต้** ถาด) ว่างเปล่าไปหมด

**วิธีแก้**: เพิ่ม prop `mobile?: boolean` ให้ `UnscheduledTray` — เมื่อ mobile ตัดทั้ง `width:230` และ `border-r`
ออก (ใช้ `border-bottom` แทนกั้นแนวนอน) + wrapper ของกิ่งมือถือใน `CalendarView` ระบุ `flex flex-col` ชัดเจน

## 5. deviation จากสัญญา (พร้อมเหตุผล)

1. **โหมดสัปดาห์ไม่มีปุ่มเลื่อนสัปดาห์แยก** — URL ตามสัญญามีแค่ `month=&mode=&ext=` (ไม่มีพารามิเตอร์ระบุ
   สัปดาห์/วันที่แยก) ⇒ เลือกให้สัปดาห์ที่แสดง = สัปดาห์ที่มี "วันนี้" อยู่ ถ้าวันนี้ตกอยู่ในเดือนที่กำลังดู
   ไม่งั้นใช้สัปดาห์แรกของเดือนนั้น · ปุ่ม `‹ ›` เลื่อนทีละเดือนเสมอ (ทั้งสองโหมด) — ถ้าต้องการเลื่อนทีละสัปดาห์
   จริง ต้องเพิ่มพารามิเตอร์ `week=`/`d=` ใน WO ถัดไป
2. **สีจุดหน้าการ์ด** ใช้ตามคำอธิบายสัญลักษณ์ 3 แบบตรงตัว (ดำ=การ์ดบอร์ดนี้ · แดง=เลยกำหนด · เทา=งานระบบอื่น)
   ไม่มีจุดเขียวสำหรับการ์ดที่เสร็จแล้ว (ต่างจาก `dueBadgeFrom`/`DUE_STYLE` ของบอร์ด/ตารางที่มี 4 โทนสี) — ยึด
   ตามข้อความสัญลักษณ์ในมะ็อกอัพ 05 ที่ระบุไว้แค่ 3 แบบเป๊ะ
3. **`href` ของงานระบบอื่นทุกชนิดชี้ไปที่ `/app/calendar?d=YYYY-MM-DD`** (หน้าปฏิทินกลางของร้าน) แทนที่จะแยก
   ไปหน้าเฉพาะของแต่ละโมดูล (เช่น หน้ารายละเอียดใบลา/นัดหมาย) — สัญญาอนุญาตทั้งสองทาง ("`/app/calendar?d=…`
   หรือหน้าระบบ") เลือกทางที่ใช้ได้กับทุกชนิด event เดียวกันหมด ไม่ต้องรู้จัก route ของแต่ละโมดูลปลายทาง
4. **ไม่เรียก `router.refresh()` เมื่อ `setCardDueFromCalendarAction` สำเร็จ** (เฉพาะตอนล้มเหลวถึงจะ rollback)
   — ตรงกับแพตเทิร์น `editDue`/`editColumn` ของ `TableView.tsx` (K2.1) ที่ปล่อยให้ optimistic state เป็นจริง
   โดยไม่ขอ RSC ใหม่ทั้งหน้า (ก่อนพบสาเหตุจริงของบั๊ก §4.1 เคยสงสัยว่า refresh() เป็นต้นเหตุ แต่พิสูจน์แล้วว่า
   ไม่ใช่ — คงพฤติกรรม "ไม่ refresh" ไว้ต่อเพราะสอดคล้องกับโมดูลอื่นอยู่แล้วและลดโหลดเซิร์ฟเวอร์)

## 6. หนี้ที่ฝากไว้

1. เลื่อนทีละสัปดาห์ในโหมดสัปดาห์ยังทำไม่ได้ตรง ๆ (deviation #1) — ต้องมีพารามิเตอร์ใหม่ถ้าต้องการ
2. บั๊กเลย์เอาต์ CSS Grid "auto" row ไม่คำนวณใหม่ตอน DOM ถูกแพตช์ในที่ (§4.1) แก้เฉพาะจุด (การ์ดในช่องวัน) ด้วย
   การผูก `key` กับจำนวนรายการ — ถ้ามีจุดอื่นในโมดูลที่ใช้ CSS Grid auto-row + เพิ่มลูกทีละใบแบบ in-place
   เดียวกัน (ยังไม่เจอที่อื่นตอนนี้) ควรระวังปัญหาเดียวกัน
3. ยังไม่มี event `kanban.card.due_changed` แยกสำหรับปฏิทินโดยเฉพาะ — ใช้ `CARD_DUE_SET` เดิมร่วมกับหลังการ์ด
   (ตรงตามสัญญาที่บอกให้ผ่าน `updateCardFields` เดิม ไม่ใช่หนี้จริง แต่บันทึกไว้เผื่อ K2.9 ต้องการแยก)

## 8. ไทม์ไลน์ที่ควรบันทึก (สำหรับ Fable ต่อ ledger)

- งานเริ่มแล้วสะดุดกลางคันเพราะ Claude API ล่มชั่วคราวคืนก่อน (403) — กลับมาต่อโดยพบว่าโค้ด/ภาพ/สคริปต์ค้างอยู่
  บนดิสก์ครบแล้ว (calendar.ts/CalendarView.tsx/spec 2.2/ภาพ 4 ใบ + ไฟล์ DEBUG ค้าง) — ตรวจ oracle ผ่าน 16/16
  ทันที (โค้ด service ไม่มีปัญหา) แต่พบว่าภาพที่ค้างไว้จากรอบก่อนโชว์บั๊ก UI จริง (§4.1) จึงไล่แก้ต่อจนจบ
- ใช้เวลาส่วนใหญ่ของ WO นี้ (>10 รอบ build ทดสอบ) กับบั๊ก CSS/React ใน §4.1 — ไม่ใช่บั๊กจากสถาปัตยกรรม/สัญญา
  แต่เป็นเรื่องเบราว์เซอร์เลย์เอาต์ล้วน ๆ ที่ oracle (ทดสอบผ่าน DB/regex เท่านั้น) ตรวจจับไม่ได้ ต้องอาศัย "ดู
  ภาพจริง" ตามกติกาข้อ 3/7 ของ run นี้ถึงเจอ — ยืนยันความสำคัญของด่านภาพอีกครั้ง
