## Findings
- **F6 (Medium, narrow) F1 still leaks for products with no base price.** `register.ts:1414–1415` refuses only when `priceOf` returns `CHANNEL_NOT_SOLD`. But `resolveUnitPrice` returns `PRICE_NOT_SET` at `price-shared.ts:270`, before it looks at the winning row at `:277`. A product with `basePriceSatang:null` (variant: parent null too) can still have a notSold row, because `cleanCpRow` (`catalog.ts:1917–1930`) and `setChannelPrices` never check base. Example: "ขนมชั่งกิโล" has base null and (LINEMAN, all) notSold. A LINEMAN cart line `{openPrice:true, unitPriceSatang:4000}` gets `PRICE_NOT_SET`, which is ignored, so the bill is written. This should be `CHANNEL_NOT_SOLD`. The same applies on STORE. The tile at `:773` sends `listPriceSatang:null` for this case, so P2.2U cannot show "ไม่ขายหน้าร้าน" and routes the cashier to the open-price dialog. Base-null products are exactly the ones sold by open price. Smallest fix: on the open-price branch, call `priceOf(book, row.basePriceSatang === null ? { ...row, basePriceSatang: 0 } : row, priceChannelCode)`, or export a `channelNotSold(book,row,code)` from `price.ts` that wraps `winningRow`. The normal path and Q7 are unchanged. Optionally add one assert inside Q8 (ORACLE-EDIT, count stays 42).
- **F7 (Low) Bulk keeps only a notSold row with the exact (code, unit) key.** It still writes a row that outranks a notSold row at another level: (a) `unitId:A` with (LINEMAN, all) notSold creates (LINEMAN, A) 8 300, which wins at A; (b) a variant with its own base under a parent with (LINEMAN, all) notSold gets its own (LINEMAN, all) row, and own beats parent at that level (`price-shared.ts:248`); (c) `unitId:null` writes a (LINEMAN, all) row, which outranks a (null, A) notSold row. This literally meets the ruling and the U copy at notes:73 is accurate. Smallest fix: skip a product when `winningRow` over its existing rows plus its parent's rows is notSold at the target (code, unit), or at any linked unit when unitId is null. Can go to P2.2U or P2.12.
