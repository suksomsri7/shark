## บั๊กที่เจอ (2 ตัว อยู่ในบล็อกเดียวกัน)

### 🐛 B-1 (ตัวที่สั่งให้แก้) — เดบิตด้วยยอด "รวม VAT" → ใบไม่สมดุล
`src/lib/modules/account/gl.ts` เคส `PURCHASE`/`EXPENSE` (เดิมบรรทัด 501):
```ts
for (const l of lines) b.dr(l.accountId ?? (await b.id(expKey, doc.docType)), l.amount);
```
`AccountDocumentLine.amount` = ฐานบรรทัด **ตามที่ป้อน** ⇒ โหมด `vatMode: "INCLUDE"` คือยอด *รวม VAT* แล้ว
แต่ขาเครดิตใช้ `doc.grandTotal` และ VAT ซื้อถูกเดบิตเพิ่มอีกขา ⇒ Σdebit เกิน Σcredit เท่ากับ VAT พอดี
⇒ `commitEntry` โยน "ลงบัญชีไม่สมดุล" ⇒ **ออกเอกสารซื้อ/ค่าใช้จ่ายโหมดราคารวม VAT ไม่ได้เลย**
(ฝั่งขายไม่พังเพราะใช้ `afterDiscount = subTotal − discountAmount` = ฐานสุทธิ)

### 🐛 B-2 (เจอระหว่างเขียนข้อสอบตาราง 6 คู่) — โหมด "รอใบกำกับ" ลง 1150 แทน 1155
```ts
const vatInKey = doc.status === "AWAITING_RECEIVE" ? "VAT_INPUT_UNDUE" : "VAT_INPUT";
```
`AWAITING_RECEIVE` เป็นสถานะของ **ใบกำกับภาษีซื้อ (PTX)** ไม่ใช่ของใบซื้อ —
`issueExpenseDoc` ตั้งใบซื้อเป็น `AWAITING_PAYMENT` ก่อนเรียก `postDocument` เสมอ
⇒ เงื่อนไขนี้เป็น **dead code**, โหมด `vatPurchaseMode: "AWAITING"` เลยเดบิต 1150 (เคลมได้ทันที)
ทั้งที่ยังไม่ได้รับใบกำกับ ⇒ ภาษีซื้อเข้า ภ.พ.30 เร็วเกินจริง
และเมื่อรับใบกำกับจริง `PURCHASE_TAX_INVOICE` โพสต์ Dr 1150 / Cr 1155 ⇒ **1150 เบิ้ล 2 เท่า · 1155 ติดลบ**
ขัดกับที่ `expense.ts` เขียนไว้เอง ("AWAITING = ยังไม่รับใบกำกับ → Dr 1155 รอ")

## สิ่งที่แก้ (ไฟล์เดียว: `src/lib/modules/account/gl.ts`)

1. `loadDocLines()` — select `vatRateBp` เพิ่ม (ต้องใช้ถอด VAT ตามอัตรารายบรรทัด)
2. `lineNetBase()` **ใหม่** — ฐานสุทธิของบรรทัดฝั่งซื้อ · โหมด INCLUDE ถอด VAT ด้วย **`depositSplit()` ตัวเดิม**
   (ตัวถอด VAT ออกจากยอด gross ที่ไฟล์นี้ใช้กับมัดจำอยู่แล้ว) ⇒ ไม่มีสูตร VAT ซ้ำใน gl.ts
3. `splitByWeight()` **ใหม่** — กระจาย `doc.subTotal` ลงแต่ละบรรทัดตามน้ำหนักฐานสุทธิ (largest remainder)
   ⇒ Σ เดบิต = `doc.subTotal` **เป๊ะเสมอ** ไม่ว่าปัดเศษยังไง (ยอด subTotal มาจาก `service.computeTotals`
   ที่เป็นเจ้าของสูตรอยู่แล้ว — gl ไม่คำนวณ VAT ซ้ำ)
   · มีทางลัด `sumW === total → คืน weights เดิม` ⇒ โหมด EXCLUDE/NONE ได้ผล **เท่าเดิมทุกสตางค์**
   (พิสูจน์: EXCLUDE ⇒ `subTotal = Σ base_i` เสมอตามนิยามใน `computeTotals`)
   · ไม่ import `service.allocateProportional` เพราะ service เป็นชั้นบนของ gl — import ขึ้นไปจะเป็นวงจร
4. `vatInKey` — เพิ่มเงื่อนไข `(doc.taxPointBasis ?? doc.vatTiming) === "ON_PAYMENT"` → 1155 (แก้ B-2)

**ไม่ได้แตะ**: ฝั่งขาย · `ASSET_PURCHASE` (ใช้ `afterDiscount` = ฐานสุทธิอยู่แล้ว ไม่มีบั๊ก) ·
`CREDIT_NOTE_RECEIVED`/`DEBIT_NOTE_RECEIVED` (ใช้ `afterDiscount` เช่นกัน) · `postPayment` (สมดุลโดยโครงสร้าง)

### หมายเหตุเรื่องส่วนลดท้ายบิลในโหมด INCLUDE
JV คงรูปเดิม: Dr ต้นทุน = `subTotal` (ก่อนหักส่วนลด) · Cr 5800 ส่วนลดรับ = `discountAmount`
⇒ ผลสุทธิต่อค่าใช้จ่าย = `subTotal − discountAmount` = ฐานสุทธิ ✅ (ตรงกับฝั่งขายเป๊ะ)
ส่วนลดถูกแสดงเป็นยอด "ตามที่ป้อน" ทั้งสองขาจึงหักล้างกันพอดี — ไม่มีผลต่อกำไรขาดทุน
