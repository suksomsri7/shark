## 2. Contract (controller rulings)
R1 **Schema + migration** (`prisma/schema/hr.prisma` `HrEmployee`): `pinHash String?`, `pinSetAt DateTime?`; keep `pinCode String?` (dropped in a later RUN, never here). Migration folder `prisma/migrations/20261201000000_hr_pin_hash/migration.sql`: `ALTER TABLE "HrEmployee" ADD COLUMN "pinHash" TEXT, ADD COLUMN "pinSetAt" TIMESTAMP(3);` + `CREATE UNIQUE INDEX "HrEmployee_tenantId_pinHash_active_key" ON "HrEmployee"("tenantId","pinHash") WHERE "active" = true AND "pinHash" IS NOT NULL;` (raw SQL; header comment in Thai explaining the partial unique and the rollout). Additive; old code keeps working (it never reads the new columns). Apply to **QC4 only** through `qc4.sh` + `prisma migrate deploy`; `prisma generate` in the lane worktree.
R2 **`src/lib/modules/hr/pin.ts` (new, server-only)** — the only file that reads `pinCode` or `pinHash` (F16.5):
  - `hashPin(tenantId, pin): string` = hex HMAC-SHA256(key = `HR_PIN_PEPPER`, message = `${tenantId}\u001f${pin}`), `pin` already validated `^\d{4,6}$`. Pepper read through `env` (R5); missing pepper ⇒ `PinNotConfiguredError` (fixed Thai text "ระบบยังไม่ได้ตั้งค่าความปลอดภัยของ PIN — แจ้งผู้ดูแลระบบ"), never a stack to the user.
  - `setPin(ctx, employeeId, pin)` (moved here from `service.ts`, which re-exports it): validate 4–6 digits (empty = clear: `pinHash = null, pinCode = null, pinSetAt = null`); employee must belong to `ctx.systemId` and be active (inactive ⇒ "ไม่พบพนักงาน" — same text as not found); write `pinHash`, `pinSetAt = now`, **`pinCode = null`** in one `updateMany` with count check; a unique-violation (P2002 on the partial index) ⇒ `{ ok:false, reason:"PIN นี้ใช้ไม่ได้ กรุณาเลือก PIN อื่น" }` (byte-identical to today's D8 text) — **no pre-check select by hash** (the index is the only arbiter; race-safe); audit `hr.pin.set` / `hr.pin.clear` (`writeAudit`, no PIN value, no hash). Uniqueness is **per tenant across all HR systems** (HQ3), which is what the index enforces.
  - `verifyPin({ tenantId, pin, unitId? , systemId? })` → `{ ok:true, employeeId, systemId, userId: string|null } | { ok:false, reason }`: validate format (bad format ⇒ same reason as wrong PIN); compute hash; `tenantDb({ tenantId }).hrEmployee.findFirst({ where: { tenantId, pinHash, active: true }, select: { id, systemId, linkedUserId, pinHash } })`; if found ⇒ `crypto.timingSafeEqual` on the hash buffers; if not found ⇒ run `timingSafeEqual` against a constant dummy of the same length (uniform work) and return the single fixed reason "PIN ไม่ถูกต้อง". `unitId` is accepted and ignored until H1.1 (document). Returns ids only — never name/position/hash. **Legacy fallback (HQ4 rollout, dead after backfill):** when no row matches by hash, look up `{ tenantId, pinCode: pin, active: true }`; if exactly one row ⇒ upgrade in place in one `updateMany` (`pinHash`, `pinSetAt`, `pinCode = null`, `where: { id, pinCode: pin }` count check; P2002 ⇒ treat as not verified) and return ok; if more than one ⇒ not verified (duplicates must set a new PIN). Rate limit inside the facade: `checkRateLimitDb('hr-verifypin:'+tenantId, { limit: 120, windowMs: 60_000 })` (tenant bucket; fail-open like H0.3) in addition to whatever the caller does; limited ⇒ `{ ok:false, reason:"ลองใหม่ในอีก N วินาที" }` (same style as kiosk).
  - `verifyPinForEmployee(ctx, employeeId, pin)` for the kiosk (name chosen on screen): hash compare on that row (+ legacy upgrade path), same uniform-work rule; used by `clockWithPin`.
  - `hasPin(row: { pinHash: string|null; pinCode: string|null }): boolean` = `!!pinHash || !!pinCode` (true during rollout for not-yet-backfilled rows).
R3 **Call sites** — `service.ts`: `createEmployee` takes `pin?: string|null` (rename of `pinCode` in `CreateEmployeeInput`; the action maps the form field) and calls `pin.setPin` after create (same tx not required: create then set; a P2002 on set ⇒ create still succeeds and the result carries `pinSet:false` + the D8 reason so the UI can say "สร้างแล้ว แต่ PIN นี้ใช้ไม่ได้"); `clockWithPin` uses `verifyPinForEmployee` (texts unchanged: "… ยังไม่มี PIN — ให้เจ้าของตั้งที่หน้าพนักงาน" when `!hasPin`, else "PIN ไม่ถูกต้อง"); `kioskRoster` selects `pinHash, pinCode` and maps through `hasPin`; `privacy.ts:78` through `hasPin` (select both columns); `ui.tsx:434` through the DTO/`hasPin` (no raw field); `actions.ts:57` passes `pin`. `hr/index.ts` re-exports `verifyPin` (+ its result type) with a C-8 comment. `scripts/seed-review-shop.mts` sets PINs through `setPin` (or `hashPin`) — no plain `pinCode` writes anywhere.
R4 **Deactivate / reactivate**: deactivating frees the PIN (the index is `WHERE active`). Reactivation (`service.ts` ~:663 and any other `active: true` writer) must survive a now-duplicate hash: do the update inside a tx; on P2002 retry once with `pinHash = null, pinSetAt = null` and return `{ ok:true, pinCleared:true }` so the UI can say "กลับมาทำงานแล้ว — ต้องตั้ง PIN ใหม่" (audit `hr.pin.clear` reason `REACTIVATE_DUPLICATE`).
R5 **Env**: `env.ts` adds `HR_PIN_PEPPER: z.string().min(32).optional()` (one marked line `// HR H0.5 ▸ … ◂`). Optional so that fitness/no-env and old deploys keep working; `pin.ts` is the only consumer and refuses when it is missing (R2). Export `hasPinPepper` boolean for the oracle/UI note.
R6 **Backfill `scripts/hr-backfill-pin-hash.mts`** — env through `acc-v2-env.loadQcEnv` by default; `--prod-ack <host>` is **not** offered (prod rollout is a controller runbook: run with the prod env file explicitly later; the script prints the host and refuses `ep-royal-night` unless `HR_BACKFILL_PROD=1` is set — document). Modes: default **dry-run** (prints per tenant: rows with plain PIN, duplicates (employee ids + name initials only, never the PIN), rows already hashed, rows to update; exits 0, writes nothing); `--apply`: per tenant, in one tx per tenant: for every active-or-inactive row with `pinCode` and no `pinHash`: if the `(tenantId, hash)` would collide among **active** rows (count the group first) ⇒ set `pinCode = null`, leave `pinHash = null`, add to the duplicates report; else set `pinHash`, `pinSetAt = now`, `pinCode = null`. Inactive rows are hashed too (no index constraint) so a later reactivation goes through R4. Second `--apply` run ⇒ 0 changes (idempotent). Audit one `hr.pin.backfill` row per tenant with counts. Missing pepper ⇒ exit 2 with the fixed text. `--tenant <id>` filter for the oracle.
R7 **Privacy / outputs**: no action, DTO, AI tool, event, log or oracle output ever contains `pinHash`, `pinCode` or the pepper. `qc-hf-hr-privacy` stays identical. Every refusal text is fixed Thai (never `e.message`). The kiosk's two limiters from H0.3 stay as they are (verifyPin's tenant bucket is additional).
R8 **Out of scope**: dropping `pinCode` · POS consumption (P1.15) · `unitId` semantics (H1.1) · PIN length policy per role (6 for void approvers = POS P3.5) · changing kiosk UX texts beyond the above · `hr.employee.offboarded` event (H4.4).

## 3. Oracle — `scripts/qc-hr-h0.5.mts` (~45 checks, ids `H0.5-S<g>.<n>` / `-X<k>.<n>`), house style of `qc-hr-h0.3.mts`

- **S1 hash**: `hashPin(t1, "1234") !== hashPin(t2, "1234")`; same input ⇒ same hash; 64 hex; changing the pepper (env override within the process) changes the hash; missing pepper ⇒ `PinNotConfiguredError` with the fixed text.
- **S2 setPin**: 4–6 digits ok, "123"/"1234567"/"12a4" refused with "PIN ต้องเป็นตัวเลข 4-6 หลัก"; after set: `pinHash` set, `pinSetAt` set, `pinCode` null; empty pin clears all three; inactive employee ⇒ "ไม่พบพนักงาน"; employee of the other HR system ⇒ "ไม่พบพนักงาน" (X2); audit rows `hr.pin.set` / `hr.pin.clear` exist and contain no digits of the PIN.
- **S3 uniqueness**: same PIN for two active employees in the **same** tenant (different HR systems) ⇒ second refused with the D8 text; **race**: 10 parallel `setPin` of the same PIN on 10 employees, 3 rounds ⇒ exactly 1 success per round; inactive employee's PIN can be reused by an active one; same PIN in another tenant ⇒ ok; DB shows exactly the partial unique index (query `pg_indexes`).
- **S4 verifyPin**: correct ⇒ `{ ok:true, employeeId, systemId, userId }` and **no other keys**; `userId` = linked user or null; wrong ⇒ "PIN ไม่ถูกต้อง"; bad format ⇒ same text; inactive holder ⇒ not verified; other tenant's PIN ⇒ not verified (X2); 121st call within 60 s on one tenant ⇒ "ลองใหม่ในอีก N วินาที" and a `ChatRateBucket` row `hr-verifypin:<tenantId>`; timing: median of 50 wrong-PIN calls vs 50 correct calls differ by < 3× (soft check, `[info]` not fail) — the hard check is `[static]`: `pin.ts` contains `timingSafeEqual` and a dummy compare on the miss path.
- **S5 legacy rollout (HQ4)**: row created with plain `pinCode` only (direct insert allowed in the fixture) ⇒ `verifyPin` ok AND afterwards `pinHash` set, `pinCode` null, `pinSetAt` set; second verify ok via hash; two plain rows with the same PIN in one tenant ⇒ verify not ok and both unchanged; `kioskRoster`/`hasPin` true for a plain-only row.
- **S6 backfill**: fixture 6 rows (2 duplicates active, 1 inactive plain, 1 already hashed, 1 unique plain, 1 no PIN) ⇒ dry-run changes nothing and reports counts {plain 4, duplicates 2, hashed 1, toUpdate 2 + 1 inactive}; `--apply` ⇒ unique plain + inactive plain hashed (`pinCode` null), duplicates `pinCode` null and `pinHash` null, hashed row unchanged; audit `hr.pin.backfill` with the counts; second `--apply` ⇒ 0 changes; output contains no 4–6 digit run equal to any fixture PIN; run as a child process through the same wrappers with `--tenant <id>`.
- **S7 kiosk + create + reactivate**: `clockWithPin` with the right PIN clocks IN (hash path) and with a wrong PIN refuses "PIN ไม่ถูกต้อง"; no-PIN employee text unchanged; `createEmployee` with `pin` ⇒ hashed, no plain; `createEmployee` with a duplicate pin ⇒ employee created, result says `pinSet:false`; deactivate A (PIN 2468) → set 2468 on B ok → reactivate A ⇒ A's `pinHash` null, result `pinCleared:true`, audit reason `REACTIVATE_DUPLICATE`.
- **S8 privacy/static**: `qc-hf-hr-privacy` viewer matrix unchanged (run it in COMMON §E); `[static]` no `pinCode`/`pinHash` outside `hr/pin.ts` + backfill script in `src/**` and `scripts/seed-review-shop.mts` (mirror of F16.5); `[static]` `hr/index.ts` exports `verifyPin`; `[static]` migration file exists with the `WHERE "active" = true AND "pinHash" IS NOT NULL` index; `env.ts` has the optional `HR_PIN_PEPPER`; DTO `privacy-shared.ts` still exposes only `hasPin`.
RED on the base: S1–S7 SKIP/RED for "module absent" or plain-text behaviour (S2 after-set state, S3 race ⇒ 10 successes, S4 facade missing, S5 no upgrade, S6 script missing), S8 statics red.
