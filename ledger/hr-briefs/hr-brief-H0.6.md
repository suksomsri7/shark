## 2. Contract (controller rulings)
R1 **Schema + migration** `20261202000000_hr_payroll_run_live_unique/migration.sql` (one file, Prisma runs it in one transaction): `DROP INDEX "HrPayrollRun_systemId_periodKey_key"; CREATE UNIQUE INDEX "HrPayrollRun_systemId_periodKey_live_key" ON "HrPayrollRun"("systemId","periodKey") WHERE "status" <> 'REVERSED'; CREATE INDEX "HrPayrollRun_systemId_periodKey_idx" ON "HrPayrollRun"("systemId","periodKey");` Schema: remove `@@unique([systemId, periodKey])`, add `@@index([systemId, periodKey])`, Thai comment pointing at the raw partial unique. Also add `reversedAt DateTime?` and `reversedById String?` to `HrPayrollRun` (additive, nullable) in the same migration. Prod order (runbook note): deploy code first (it is correct under both indexes), then migrate; QC4 in the lane: `migrate deploy` through `qc4.sh` after the `_prisma_migrations` check (COMMON §A.7; QC4 now also has `20261104000001-3`).
R2 **`reverseRun(ctx, runId, reason?, actor?)`** — keep the positional signature (qc-payroll-reverse) and add `actor?: PayrollActor` (H0.1 type); `reverseRunAction` passes the actor. One `tenantDb(ctx).$transaction`:
  1. `pg_advisory_xact_lock('hr:payroll:run:<systemId>:<periodKey>')` (same key as create/recompute/approve) after loading the run (`FOR UPDATE` re-read inside the lock).
  2. Guards with **fixed Thai texts** (never `e.message`): not found "ไม่พบรอบจ่าย" · already REVERSED "รอบนี้กลับรายการไปแล้ว" · no JV "รอบนี้ยังไม่ได้ลงบัญชี — ไม่มีรายการให้กลับ (รอบที่ยังเป็นร่างใช้ปุ่มลบร่าง)" · status not APPROVED/PAID "รอบนี้กลับรายการไม่ได้ในสถานะปัจจุบัน". Refusals write `auditRefusal`-style rows like H0.1 (`hr.payroll.reverse` with `refused.code`).
  3. Guarded `updateMany {status ∈ APPROVED/PAID, journalEntryId ≠ null} → {status: REVERSED, reversedAt: now, reversedById: actor?.userId ?? null, note}` with count check.
  4. `reverseEntry({tenantId, systemId: acct.id}, journalEntryId, why, tx)` **inside the tx** (the `tx?` parameter exists); if there is no ACCOUNT system, skip (X8) — the run still becomes REVERSED.
  5. Collect `adjustmentIds = select id from HrPayAdjustment where runId = run.id` (ordered), then `updateMany({ runId: run.id } → { runId: null })` with count = adjustmentIds.length. Adjustments keep status APPROVED ⇒ eligible for the next run of that period (COMMISSION rows included; `crmCommissionId` link untouched).
  6. `emitOutbox(tx, { type: "hr.payroll.reversed", idempotencyKey: "hr.payroll.reversed#<runId>", payload: { runId, periodKey, adjustmentIds } })` — ids only (X8). (Reason: after step 5 nothing links the adjustments to the run, so the consumer needs the ids; a run has at most hundreds.)
  7. `writeAudit` `hr.payroll.reverse` {runId, periodKey, adjustmentCount, journalEntryId, reversalEntryId} + actor.
  Items (`HrPayrollItem`) stay as history (slip of a reversed run shows the status label; no new UI).
