## 2. Contract (controller rulings — additive; no behaviour change for non-DRAFT runs)
R1 **Extract** the row-building part of `createPayrollRun` into an internal `buildRunRows(tx, ctx, periodKey)` that returns `{items, totals, adjustmentIds}`. `createPayrollRun` keeps its exported signature and its output byte for byte (same items, totals, snapshot keys). The duplicate check stays in `createPayrollRun` only.
R2 **`deleteDraftRun(ctx, runId, actor)`**: same advisory lock key as create (resolve `periodKey` from the run first, then lock, then re-read the run `FOR UPDATE` inside the tx) → refuse unless `status = DRAFT` and `journalEntryId IS NULL` → unbind its adjustments (`updateMany({runId} → {runId: null})`, statuses untouched) → delete the run (items cascade, `payroll.prisma:101`) → audit `hr.payroll.delete_draft` with `before {periodKey, totals, itemCount, adjustmentIds}`. The returned refusals are Thai and fixed: not found / "ลบได้เฉพาะรอบที่ยังเป็นร่าง" / "รอบนี้เปลี่ยนไปแล้ว กรุณาเปิดดูใหม่".
R3 **`recomputeDraftRun(ctx, runId, actor)`**: same lock + `FOR UPDATE` + DRAFT guard → unbind its adjustments → delete its items → `buildRunRows` again (it picks up the unbound APPROVED adjustments of the period, the current salary profiles and the current employee list) → create the items → update the run totals (and `note` = "คำนวณใหม่ <Bangkok time>") → rebind with a count check. The `payDate` is kept. Run `id` is kept, so links/slips stay valid. Audit `hr.payroll.recompute` with before/after totals and item count.
R4 **Approve only what you saw.** `approveRun(ctx, runId, expect?)` takes an optional `expect: {totalNetSatang: number; itemCount: number}`. When given, the claim refuses (no status change) unless the run still has exactly those values: "ตัวเลขของรอบนี้เปลี่ยนไปแล้ว (มีการคำนวณใหม่) — กรุณาเปิดดูและอนุมัติอีกครั้ง". Callers without `expect` behave as today (legacy/tests). The web approve form always sends `expect` (hidden fields from the rendered row). Implement the check atomically (the claim `updateMany` where includes `totalNetSatang`, and the item count is checked under the run row lock, or an equivalent single guarded statement — builder proposes, reviewer checks the race).
R5 **Races:** recompute ∥ approve, delete ∥ approve, recompute ∥ recompute, delete ∥ create (same period), recompute ∥ `decideAdjustment` of a row in that period. In every interleaving there is exactly one outcome, and no adjustment ends up bound to a deleted run or bound twice. An approve that waited behind a recompute must refuse when it carried `expect` from before the recompute.
R6 **Actions + UI:** `deleteDraftRunAction`, `recomputeDraftRunAction` with `hr.payroll.create` (+ `canViewPayroll` via `assertHrCan`), `systemId` + `runId` from the form, returning `{ok, reason}` (not void). Show the reason inline (pattern: `hr/PayAdjustRowActions.tsx` from the hotfix). DRAFT rows get two more buttons, "คำนวณใหม่" and "ลบร่าง" (danger), each in a `ConfirmDialog`. Fix the `reverseRun` hint text (:496) to name the real button ("ลบร่าง"). Thai strings follow the existing file's style (the HR module does not use `src/messages` yet — do not start that in this WO).
R7 **Out of scope:** reversed-month re-run and unbinding on reverse (H0.6) · excluding leavers / negative net / period validation (H0.2) · posting changes (H3.7) · any schema change.
