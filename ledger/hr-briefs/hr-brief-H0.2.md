## 2. Contract (controller rulings)
R1 **Who is in a run (D1)** — period = the Bangkok calendar month of `periodKey` (`firstDay`…`lastDay` as `@db.Date` values). An employee with a salary profile is included iff all three hold:
  (a) `startDate IS NULL OR startDate ≤ lastDay`;
  (b) `endDate IS NULL OR endDate ≥ firstDay`;
  (c) `active = true` OR `endDate IS NOT NULL` (someone removed with no end date has an unknown leaving date ⇒ excluded and **reported**, never silently paid).
  Included people with `startDate > firstDay` or `endDate < lastDay` keep **today's full-month amount** (no proration until HQ6) and get `snapshot.flags = ["PARTIAL_MONTH"]`. The UI shows "ต้องตรวจ · เข้า/ออกกลางเดือน — ยังไม่คิดตามสัดส่วน". Excluded people are returned by a reader `runExclusions(ctx, periodKey)` → `{employeeId, name, reason: "ENDED_BEFORE"|"STARTS_AFTER"|"REMOVED_NO_END_DATE"}` and shown above the run for payroll viewers only. Their adjustments stay unbound (same rule as CRM C3.3-fix H4). Implemented once, inside `buildRunRows`, so create and recompute agree.
R2 **Closed period for manual rows (D5)** — the manual path refuses `PERIOD_CLOSED` with the same Thai text as the CRM path (:620). An APPROVED decision on a manual row whose period already has a run moves it to the next run-less period exactly like CRM rows (generalise the `moveTo` block to every row; keep the returned `movedFrom/movedTo` and the action's audit). A new reader `strandedAdjustments(ctx)` (manual + CRM; PENDING/APPROVED, `runId IS NULL`, period has a run) is shown on the payroll page with a "ย้ายไปงวดถัดไป" action (reuse `moveCommissionAdjustmentPeriod` semantics for manual rows, or a sibling function — builder proposes). `strandedCommissionAdjustments` keeps its exact output (CRM consumer `crm/commissions.ts:1509`).
R3 **No negative net (D6)** — `computeItem` stays as is (frozen identities, oracle RN-*). `buildRunRows` adds `snapshot.flags += "NEGATIVE_NET"` to any item with `netSatang < 0`. `approveRun` refuses while any item of the run has `netSatang < 0`, with the message "มีพนักงาน N คนที่ยอดสุทธิติดลบ (รายการหักมากกว่าเงินได้) — แก้รายการหักแล้วกด 'คำนวณใหม่'". The check runs inside the same guarded claim, so a recompute cannot slip between them. The UI marks those rows red. The excess-deduction policy itself = HQ7 → H3.4.
R4 **Valid periods and dates (D12)** — `createPayrollRun` validates `PERIOD_RE` and a valid `payDate` (throws a Thai error the action turns into `{ok:false, reason}`). The action uses the same `PERIOD_RE`. `createPayrollRunAction` returns state like H0.1's actions (no 500 page on a duplicate or invalid period).
R5 **Unchanged:** the CRM C3.3 block's outputs, `payroll-rules.ts`, `computeItem` arithmetic, posting, `reverseRun`, and the `qc-hr-payadjust` RN-10 expectation (`ssoEligible:false` → gross 0, net 0).
