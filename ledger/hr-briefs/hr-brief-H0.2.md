## 2. Contract (controller rulings)
R1 **Who is in a run (D1)** — period = the Bangkok calendar month of `periodKey` (`firstDay`…`lastDay` as `@db.Date` values). An employee with a salary profile is included iff all three hold:
  (a) `startDate IS NULL OR startDate ≤ lastDay`;
  (b) `endDate IS NULL OR endDate ≥ firstDay`;
  (c) `active = true` OR `endDate IS NOT NULL` (someone removed with no end date has an unknown leaving date ⇒ excluded and **reported**, never silently paid).
  Included people with `startDate > firstDay` or `endDate < lastDay` keep **today's full-month amount** (no proration until HQ6) and get `snapshot.flags = ["PARTIAL_MONTH"]`. The UI shows "ต้องตรวจ · เข้า/ออกกลางเดือน — ยังไม่คิดตามสัดส่วน". Excluded people are returned by a reader `runExclusions(ctx, periodKey)` → `{employeeId, name, reason: "ENDED_BEFORE"|"STARTS_AFTER"|"REMOVED_NO_END_DATE"}` and shown above the run for payroll viewers only. Their adjustments stay unbound (same rule as CRM C3.3-fix H4). Implemented once, inside `buildRunRows`, so create and recompute agree.
R2 **Closed period for manual rows (D5)** — the manual path refuses `PERIOD_CLOSED` with the same Thai text as the CRM path (:620). An APPROVED decision on a manual row whose period already has a run moves it to the next run-less period exactly like CRM rows (generalise the `moveTo` block to every row; keep the returned `movedFrom/movedTo` and the action's audit). A new reader `strandedAdjustments(ctx)` (manual + CRM; PENDING/APPROVED, `runId IS NULL`, period has a run) is shown on the payroll page with a "ย้ายไปงวดถัดไป" action (reuse `moveCommissionAdjustmentPeriod` semantics for manual rows, or a sibling function — builder proposes). `strandedCommissionAdjustments` keeps its exact output (CRM consumer `crm/commissions.ts:1509`).
R3 **No negative net (D6)** — `computeItem` stays as is (frozen identities, oracle RN-*). `buildRunRows` adds `snapshot.flags += "NEGATIVE_NET"` to any item with `netSatang < 0`. `approveRun` refuses while any item of the run has `netSatang < 0`, with the message "มีพนักงาน N คนที่ยอดสุทธิติดลบ (รายการหักมากกว่าเงินได้) — แก้รายการหักแล้วกด 'คำนวณใหม่'". The check runs inside the same guarded claim, so a recompute cannot slip between them. The UI marks those rows red. The excess-deduction policy itself = HQ7 → H3.4.
R4 **Valid periods and dates (D12)** — `createPayrollRun` validates `PERIOD_RE` and a valid `payDate` (throws a Thai error the action turns into `{ok:false, reason}`). The action uses the same `PERIOD_RE`. `createPayrollRunAction` returns state like H0.1's actions (no 500 page on a duplicate or invalid period).
R5 **Unchanged:** the CRM C3.3 block's outputs, `payroll-rules.ts`, `computeItem` arithmetic, posting, `reverseRun`, and the `qc-hr-payadjust` RN-10 expectation (`ssoEligible:false` → gross 0, net 0).

## Oracle writer additions (7 Oct)
Written by the H0.2 oracle writer (`wip/pos-hr-h0.2-oracle`, base `origin/main` f85f5455). The brief file is copied verbatim from `session/pos` (this branch did not carry it) and this section is the only new text. These are the rulings the oracle `scripts/qc-hr-h0.2.mts` assumes; the controller can overrule any of them through an ORACLE-EDIT.
- **OW-1 (Q1, Q2 defaults):** `REMOVED_NO_END_DATE` people are excluded and listed (Q1 default). An APPROVED manual row whose period already has a run moves to the next run-less period and the result says so (`movedFrom`/`movedTo`, Q2 default). REJECTED rows never move (S2.12).
- **OW-2 flags:** a flagged item has `snapshotJson.flags` as a string array that contains `"PARTIAL_MONTH"` / `"NEGATIVE_NET"` (other flags may sit next to them). For an unflagged item, `flags` may be missing or `[]`. Boundaries: `startDate = firstDay` and `endDate = lastDay` → no `PARTIAL_MONTH`.
- **OW-3 payDate:** `createPayrollRun` refuses an `Invalid Date` with a Thai error (not a Prisma validation error). The action refuses a `payDate` string that is not a real calendar date: `2026-02-31` (JS would roll it over to 3 March) and `abc` → `{ok:false, reason}` (Thai), no row.
- **OW-4 `strandedAdjustments(ctx)`:** returns rows with at least `id`. Scope = this HR system: manual + CRM rows, status PENDING or APPROVED, `runId IS NULL`, period has a run of any status. The oracle only compares the ids of its own fixture rows.
- **OW-5 approve refusal:** the text is exactly `มีพนักงาน N คนที่ยอดสุทธิติดลบ (รายการหักมากกว่าเงินได้) — แก้รายการหักแล้วกด 'คำนวณใหม่'` (ASCII single quotes, N = number of items with `netSatang < 0`). It is returned in `note`, the existing field of `approveRun`; `reason` is also accepted. The refusal applies with and without `expect`, and the run stays DRAFT with no JV.
- **OW-6 `createPayrollRunAction`:** returns `{ok:true}` on success and `{ok:false, reason}` (Thai) for an invalid period, an invalid payDate and a duplicate period. It never throws. Both `(formData)` and `(prevState, formData)` signatures are accepted by the oracle.
- **OW-7 H0.1 `actor`:** the oracle passes `{ userId, isOwner: true }` (the shape `decideAdjustment`/`cancelAdjustment` use) to `recomputeDraftRun` / `deleteDraftRun`. If H0.1 settles on another shape, the oracle needs an ORACLE-EDIT at the 4 call sites.
- **OW-8:** S3.4 deletes the bound deduction directly, as a fixture (see OQ-1). S3.7 covers the product's own path: ลบร่าง → ลบรายการ → สร้างรอบใหม่ → อนุมัติ.
- **OW-9 race outcome (X6.3):** "never stranded unseen" means each row ends in one of three states: bound to the run of its period, moved to a run-less period, or listed by `strandedAdjustments`. For the employee, `addSatang` = Σ of the rows bound to the run.
- **OW-10 UI wiring (S5.5):** `runExclusions(` and `strandedAdjustments(` are called inside `PayrollSection`, after the `canViewPayroll` early return. The texts `ยังไม่คิดตามสัดส่วน`, `PARTIAL_MONTH` and `NEGATIVE_NET` appear in `payroll-ui.tsx` or `RunRowActions.tsx`. If the builder uses another file, ORACLE-EDIT.

### Open questions (controller; owner not needed)
- **OQ-1:** The approve refusal tells the user "แก้รายการหักแล้วกด 'คำนวณใหม่'", but `cancelAdjustment` refuses any row that has a `runId`, DRAFT-bound rows included. So on the product the only way out is ลบร่าง → ลบรายการ → สร้างรอบ, not "fix the deduction, then recompute". Options: (a) allow `cancelAdjustment` on rows bound to a DRAFT run (unbind + delete under the run lock), or (b) change the text so it names "ลบร่าง". The oracle tests the text as written, plus both paths (OW-8).
- **OQ-2:** Should `requestAdjustment` refuse new manual rows for an employee who is excluded from that period (ended or not started)? This is not in the contract, and the oracle does not test it.

## §8 Controller rulings (7 Oct)
- **CR-H0.2-1 (OQ-1)** `cancelAdjustment` on a row bound to a **DRAFT** run is allowed: one tx under the run's advisory lock (`hr:payroll:run:<systemId>:<periodKey>`), run re-read FOR UPDATE and must still be DRAFT with `journalEntryId NULL`; delete the row (guarded deleteMany, count check) then recompute the draft in the same tx (same internals as `recomputeDraftRun`, so Σ items = totals, the items digest changes, and the NEGATIVE_NET flag clears); audit `hr.payadjust.delete` + `hr.payroll.recompute`. Rows bound to APPROVED/PAID/REVERSED keep today's refusal, but its text changes to "รายการนี้อยู่ในรอบจ่ายที่อนุมัติแล้ว ลบไม่ได้ (ใช้กลับรายการรอบจ่ายแทน)". The old text that told the user to reverse a DRAFT is wrong (a draft cannot be reversed) — the H0.1 oracle S7.5 asserts the OLD literal "รายการนี้เข้ารอบจ่ายแล้ว ลบไม่ได้ (ใช้กลับรายการรอบจ่ายแทน)"; the controller will ORACLE-EDIT S7.5 to the new behaviour (DRAFT-bound cancel succeeds + recompute; APPROVED-bound refused with the new text). Report S7.5 red as expected, do not work around it.
- **CR-H0.2-2 (OQ-2)** no refusal of new manual adjustments for an employee excluded from that period; they stay unbound and appear in `strandedAdjustments` (visibility, not a block).
- OW-1…OW-10 of the oracle writer are accepted; OW-7 actor shape = H0.1 CR2 `{userId, isOwner}`.
- Every H0.1 invariant stays: approve requires expect (net, count, gross, digest) from the UI; `journalEntryId NULL` on claims; refusal audits; fixed Thai reasons; `payroll-rules.ts` / `computeItem` / CRM C3.3 block byte-identical.
