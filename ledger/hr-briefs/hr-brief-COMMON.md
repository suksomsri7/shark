## A. Machine, branches, database (a violation stops the WO)
1. **Base:** your branch is cut from a commit that contains `hotfix/hr-privacy` afcb9bc3 (check: `git merge-base --is-ancestor afcb9bc3 HEAD`). Without it you would re-open D3/D4/D9/D10. Accepted HR work lands on `session/hr`; each lane works on `wip/hr-<wo>` (oracle writer: `wip/hr-<wo>-oracle`).
2. **Never** push `main`, `session/pos`, `session/crm`, `rc/*` or `hotfix/*`. Never `git push --force`. Never merge into those branches.
3. **Worktree:** only the one the controller gives you (VPS, e.g. `/root/projects/shark-hr` / `shark-hr-b`). Never read-write, reset, clean or `cd` into `shark-pos*`, `shark-crm*`, `shark-hf*`, `shark-in-th`. Never sweep `/tmp`.
4. **Database = QC4 only** (`wo-pos-qc4`, host `ep-frosty-lab`), shared with the POS lanes. Every DB command goes through the wrapper that checks the host: `bash scripts/iso.sh bash scripts/qc4.sh bash scripts/with-gate-lock.sh pnpm exec tsx scripts/<file>.mts`. `qc4.sh` refuses any URL that is not `ep-frosty-lab` (and refuses production/QC1 hosts). Never use `qc2.sh`/`qc3.sh`, never export another `DATABASE_URL`, never `pnpm neon:gc`.
5. **Never read, edit, source or commit `.env`, `.env.*`, `scripts/qc4.sh` secrets, or `.qc-shots/`.** If a command needs a value you don't have, stop and report.
6. **Cloud containers cannot reach QC4** (TCP 5432 blocked). DB work (oracles, seed, migrations, server) runs on the VPS only. In a cloud session do only no-DB work and say so.
7. **Schema:** only a WO marked "Mig" in the plan may edit `prisma/` — and only its builder. `prisma migrate diff` → read the SQL → apply to QC4 only (`migrate deploy` through `qc4.sh`), after checking `_prisma_migrations` on QC4 for folders your branch lacks (QC4 already has `20261103000000_crm_perf_indexes`). HR migration folder timestamps are **≥ `20261201000000`**. `ALTER TYPE … ADD VALUE` gets its own migration file. Partial unique indexes = raw SQL in the migration. **`prisma generate` / `pnpm install` only if your worktree has its own `node_modules`** — if `node_modules` is a bind mount shared with another lane, stop and ask the controller.
8. **No build or server** unless the brief says "CONTROLLER-RUN" (then the controller does it on its own port, e.g. 3226; 3215 belongs to CRM, 3225 to POS).
9. **Heavy commands** (typecheck) queue behind the shared machine lock: `env NODE_OPTIONS=--max-old-space-size=5632 ISO_MEM=6500M bash scripts/iso.sh bash scripts/with-gate-lock.sh pnpm typecheck` — foreground, at most twice per WO. Wait in the shell; never kill another process to get the lock.
10. **Commits:** by explicit path only (`git add <path> …`, never `-A`/`.`), on your own `wip/hr-<wo>` branch, then push that branch. Message ends with the attribution lines the controller gives you. Pre-commit hook runs tsx outside iso.sh: if it OOMs, run `scripts/fitness.mts` + `scripts/fitness-hr.mts` through iso.sh in both modes and commit with `--no-verify`, noting it in your report (HF-HR-0 C4 precedent).

## B. Order of work (oracle-first, every WO)
1. **Oracle writer** writes `scripts/qc-hr-<wo>.mts` first, from the brief, and runs it on the base: it must be **RED for the right reason** (or SKIPPED with the right reason when a module is absent) and leave no residue. Save the output to `ledger/wo-notes/hr-<wo>-red.txt`. The oracle writer never edits product code.
2. **Builder** makes it green without editing the oracle. If a check is wrong, ask for an **ORACLE-EDIT** (check id · exact hunk · reason); the controller rules. Save the green output to `hr-<wo>-green.txt`.
3. Controller re-runs → **reviewer** (read-only, fresh agent) → **hunter** for money/privacy/PIN WOs → accept → merge into `session/hr`.
4. Checkpoint as you go in `ledger/wo-notes/hr-<wo>.md` (template `ledger/wo-notes/TEMPLATE-hr.md` after H0.4; before it, use the HF-HR-0 notes layout): done / next / commands + final summary lines, so a restart can continue from the files.

## C. HR code rules (in addition to crm-brief-COMMON "Code rules")
1. **Personal data first.** Any field, page, list, export, event payload, server-action return value or AI tool output that carries employee data goes through a whitelisted DTO (pattern `src/lib/modules/hr/privacy.ts` + `privacy-shared.ts`). Sensitive fields (national id, SSO number, house-registration address, bank, salary, payslip, leave reason, GPS, photo) only for the viewers the brief names. `pinCode`/`pinHash` never leave the server. Outbox payloads carry ids only.
2. **Viewer matrix in every oracle that adds a surface:** owner · payroll viewer (`hr.payroll.read`) · manager without payroll · staff with an HR key · plain member · the employee themself (linked user) · other tenant.
3. **Money = integer satang.** Per item `net = gross − ssoEmployee − wht`, and no item with `net < 0` can be approved. Σ items = run totals. JV Dr = Cr. Rounding is fixed by test vectors in the oracle.
4. **`payroll-rules.ts` stays byte-identical** (FREEZE, `qc-payroll.mts`). New rules = new functions + `engineVersion`. Never recompute an APPROVED/PAID/REVERSED run.
5. **The CRM block of `payroll.ts`** (`requestCommissionAdjustment`, `payrollEmployeeOfUser`, `withdrawCommissionAdjustment`, `moveCommissionAdjustmentPeriod`, `strandedCommissionAdjustments`, …) keeps its behaviour; `qc-crm-c3.3.mts` is a regression for every WO touching `payroll.ts`.
6. **Keep the hotfix rules:** leave transitions (PENDING→APPROVED/REJECTED, APPROVED→REJECTED revoke only with `from` and not for chain-approved leave), no self-decision (direct, chain, AI), no approve/reject-deduction/delete of one's own pay row unless OWNER, OT hours 0.25 steps for non-payroll viewers, cap 744 h, identical refusal bytes for non-viewers (no salary oracle), leave + approval request in one tx.
7. **Self-service code never accepts an `employeeId` from the client** — resolve it with `employeeOfUser(tenantId, userId)`.
8. **Transactions:** `hr/**` writes through `tenantDb(ctx)` (fitness F5.1 — no raw `prisma`, no new `$transaction` on the raw client); use `tenantDb(ctx).$transaction` like `payroll.ts`. Every statement inside a tx uses that tx client (HF-HR-0 round 5d lesson: a second connection under a lock deadlocks the pool). Serialise per entity with `pg_advisory_xact_lock(hashtextextended('<ns>:<id>',0))`, then a guarded `updateMany` with a `count` check.
9. **Rate limits** use `checkRateLimitDb` (`src/lib/core/rate-limit-db.ts:37`), never the in-memory `checkRateLimit`, for anything an attacker can repeat (PIN, verifyPin, kiosk).
10. **Events:** every new outbox event = consumer in `src/lib/outbox-consumers.ts` + exactly one label (automation or webhook) + replay-twice oracle; emitted inside the same tx as the state change unless the brief says the loss costs nothing.
11. **Time:** Asia/Bangkok via the explicit helpers (`bkkParts` `hr/service.ts:679` on the hotfix, `thaiDateKey` from `@/lib/ui/date`); never raw `getDay()/getDate()`. Oracles never depend on today's date.
12. **UI:** tokens only (`docs/UI_STANDARD.md`), strings in `src/messages/{th,en}.json` key `hr.*`, buttons ≥44 px, `data-testid` + row in `scripts/hr-ui-inventory.json` (after H0.4), match the mockup; screenshots via `scripts/visual-hr.mts <wo> --user owner|manager|staff` at 1440×900, 1024×768, 390×844 (CONTROLLER-RUN).
13. Thai comments in code (repo convention); Thai, non-blaming messages to users; reports to the controller in English.
