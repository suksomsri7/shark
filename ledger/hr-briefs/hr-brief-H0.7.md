## 1. Facts as built (verified on session/hr 527c155f)
- `hr/service.ts:473` `requestLeave(ctx, input)` → `:518` submits `ApprovalRequest { entityType: "HrLeave", requestedById: input.employeeId }` — an **employee** id where the approval core expects a **user** id (`approval/service.ts:53`, `:402-407` "my requests" filters `requestedById = userId`) ⇒ leave never appears in "my requests"; the requester cannot cancel.
- `hr/actions.ts:266` `requestLeaveAction`: key `hr.leave.request`, takes `employeeId` **from the form** (violates COMMON §C.7 for self-service); no "filed by".
- `hr/service.ts:543` `decideLeave`: self-decision check `leave.employee.linkedUserId === decidedById` (:27-28 of the function), fixed Thai texts, chain-approved leave cannot be revoked directly.
- `src/lib/staff/service.ts:437-444` link user↔employee: conditional `updateMany({ id, tenantId, OR: [{linkedUserId: null}, {linkedUserId: user.id}] })` inside the tx (R4.3) — app-level only; **no DB uniqueness** on `HrEmployee.linkedUserId` (`prisma/schema/hr.prisma:79`, only `@@index([tenantId])`); two different users linked to one employee is prevented, but **one user linked to two employees is not** (R4 1↔1 race).
- No `linkApprovedById` column; R4.7 ("link before salary") is open: an employee with a salary profile can be linked by anyone holding the staff-link key, exposing payslips to that account (`privacy.loadPayslipForViewer` trusts `linkedUserId`).
- `ai/plans.ts:86-140` `executePlan(m, ctx, id, { confirm2x, userId })` knows the confirmer (C5.5-G2) but `:140` `runKind(m, tenantId, kind, payload, key)` passes **no user id** to steps; `hr_decide_leave` / `approval_decide` are blocked in plans (R5.4, `:33-37`). Mobile route `api/mobile/plans/confirm/route.ts:24` passes `userId: g.user.id`.
- Oracles touching this area: `qc-hr-leave-booking.mts`, `qc-approval*.mts`, `qc-hf-hr-privacy.mts` (194), `qc-hr-h0.3.mts` (37, AI leave tools), `qc-crm-c3.3` / `qc-crm-c0.3` (HR→CRM readers `employeeOfUser`).
