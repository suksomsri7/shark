## Findings → acceptance criteria
- **H1** `memberToolAllowedForScopes`: a key with NO `member.*` scope must be denied every member-family tool (legacy ones included). Keys with member scopes keep today's behaviour.
- **H3** assistant read tools run with scopes = intersection(ASSISTANT_READ_SCOPES, what the human who opened the page can really do) and with THAT human's `unitAccess` (not `[]`). A single-branch STAFF holding only `member.loyalty.stamp` must not get member lists / reports of other branches through the assistant. OWNER behaviour unchanged.
- **L10** `cancelMemberProposalAction`: only proposals belonging to a conversation of this member system + this tenant, and the caller needs the same permission that confirming would need (or be the conversation owner).
- **H2** `exportMembers` and `listFields`/list columns: fields flagged `sensitive` are dropped (export: column omitted or cell blank) unless `canViewSensitive`/`evaluateSensitiveAccess` passes for that actor+field; every sensitive export writes `MemberAccessLog` via the existing `logAccess`. Unknown column keys are ignored, never echoed.
- **H4** customer OTP limiter: per-target and per-IP buckets move to the DB-backed limiter (`checkRateLimitDb`, same keys/limits) + a DB-backed "wrong code" bucket per target and per IP (e.g. 10 / 15 min) on verify. Join lane e-mail OTP obeys the same DB limits.
- **M3** `otpPreviewOn()`: `NODE_ENV==="production"` together with `APP_ENV==="production"` (the real prod) ⇒ always false, checked FIRST. The QC server (`next start` = NODE_ENV production, APP_ENV≠production, `QC_OTP_PREVIEW=1`) must keep working — read `scripts/acc-v2-serve.sh` and `.env.qc` var names (names only) to pick the right discriminator and explain it in the report.
- **L1** login OTP e-mail is sent outside the request path (`after()` or fire-and-forget with catch) so timing no longer reveals membership.
- **L5** customer cookie `secure` = true whenever the request is https / APP_ENV production, regardless of cookie name. **L7** `/m/[slug]/auth/line` gets the same DB rate-limit gate as `join-actions.gate()`.
